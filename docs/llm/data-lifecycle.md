# 영속 데이터 무결성과 수명주기 계약

이 문서는 모든 영속 데이터에 적용하는 **필수 설계 계약**이다. 구현 완료를 뜻하지 않는다.
2026-10-20 감사에서는 승인 상태 소실, RAG 원본 삭제, Session 삭제에 따른 Project 예산
초기화를 재현했다. 아래 미해결 항목을 먼저 보강하고 검증한 뒤 P1과 A–F를 이어간다.
이후 H1의 세 회귀 계약군은 보강·검증했다. 전체 영속 자료에 대한 H2–H5 완료를 뜻하지 않으며
현재 구현 범위·실패·통과·미검증 항목은 [단계별 검증 기록](lifecycle-verification.md)을 따른다.
2026-10-21 H2-a의 도메인 필수 필드·Completion quota·Memory identity·Conversation 끝줄·
Refinement 이력은 집중/전체 회귀를 통과했다. H2-b는 외부 작업 원장 파일/무효과 증거
소실 뒤의 실제 추가 효과 2개 실패를 보강하고 전체 LLM/Hub 회귀를 통과했다. H2-c도
Checkpoint 개별 기록 소실 후 중복 효과를 보강하고 집중/전체 검증을 통과했다. H2-d는
출력 원본·manifest의 필수 존재와 현재 출력 필드를 보강하고 집중/전체 회귀를 통과했다.
H2-e도 Component 저장소 이력·사용량 manifest·필수 영수증 필드를 보강하고 집중/전체 회귀를
통과했다. H2-f는 공통 JSON 기록·File 패키지의 존재 목록, Memory 캐시와 Vision 삭제 표식
소실 경로를 보강하고 집중/전체 회귀를 통과했다. Python Tool 패키지 소실의 별도 3개 실패와
나머지 owner 계약은 남아 있다. H2 전체는 미완료이며
이 차단 항목들을 해결하기 전 P1/A–F로 넘어가지 않는다.
기준 작업 트리는 `refactor/llm-clean`, HEAD `df6b50813eba11776282a3feed8a1abb26d49a7a`와
보존 중인 P1-c 변경이다. main이나 이전 backend 브랜치의 검증 결과를 승계하지 않는다.

## 책임과 단일 선언

| 주체 | 소유하는 계약 | 위임 경계 |
|---|---|---|
| 각 도메인·Repository·Component | 자기 영속 데이터의 생성·저장·조회·무결성·손상 처리·격리·복구·삭제·참조 보호. 필수 존재 조건, 형식·상태·식별자·경로·리비전과 상태별 증거 | 다른 도메인의 내부 형식을 해석하지 않고 해당 owner의 검증·참조 계약을 호출 |
| 공통 저장 인프라 | 바이트와 경로의 안전한 저장, 잠금, 트랜잭션, 준비·이동·격리·삭제의 기술 수단, 체크섬과 확정된 작업의 중단 복구 | 승인 의미, 사용량, 효과 발생 여부, 보존 가치나 삭제 대상 선정은 해석하지 않음 |
| Application | 보존 기간, 자동 삭제 여부, 삭제 대상 선정과 실행 시점 | Backend의 안전성 판정과 거부를 우회할 수 없음 |
| Backend의 해당 소유 구현체 | Application이 지정한 대상의 안전한 삭제 가능성 판단과 실행. 참조·활성 작업·증거·리비전의 최신 검증 | 기간·용량·완료 상태만으로 독립적인 자동 삭제 정책을 만들지 않음 |

Application의 자동화도 Backend에 명시적인 대상과 작업을 요청한다. 매번 사람이 선택해야
한다는 뜻은 아니다. 삭제 요청과 계획 조회는 삭제 허가 자체가 아니며 적용 시 다시 검증한다.
새 중앙 데이터 관리자, 모든 형식을 해석하는 공통 Reader, 전역 수명주기 상수 모음을 만들지 않는다.

공통 인프라가 자기 트랜잭션 저널·삭제 의도·백업 manifest의 형식을 검증하는 것은 그 인프라의
소유 계약이다. 그 안에 담긴 도메인 레코드의 의미 검증까지 맡는 것은 아니다.

## 소유자가 반드시 선언할 내용

각 데이터 유형의 저장 구현과 문서는 다음을 선언하고 같은 Reader/Writer·검증기로 집행한다.
지원하지 않는 동작과 삭제 금지인 증거도 명시한다. CRUD 대칭을 위해 삭제 기능을 추가하지 않는다.

- 생성 시점과 경로, 원본·파생 자료·증거의 구분, 소유자·참조·리비전의 근거.
- 필수 필드·필수 파일의 존재 조건과 Missing/Null/Value 의미, 허용 상태 전이와 원자 저장 범위.
- 생성·저장·조회·무결성 검증·손상 처리·격리·복구·삭제·참조 보호의 지원 여부와 거부 조건.
- 삭제가 보호할 승인, 논리 누적 예산, Project quota, 외부 효과, 재개 계보와 다른 owner의 참조.
- 중단 복구의 증거, 실패 시 원본 보존, 재시작 후 차단 유지 및 확인 가능한 검증 결과.

생성 초기값과 저장 Reader를 분리한다. 누락된 필수 상태를 생성자의 기본값으로 채우지 않으며,
조회 중 identity를 재발급하지 않는다. 명시적인 nullable 필드의 None과 필드 누락은 다르다.
선택 자료의 정상적인 부재는 owner가 선언한 존재 조건으로 판단한다. 모든 파일을 무조건
필수로 만들거나, 파일이 없다는 이유만으로 정상적인 미응답·빈 저장소라고 판단하지 않는다.

## 손상·격리·삭제의 판단

| 상황 | 허용되는 처리 | 필요한 근거 |
|---|---|---|
| 정상이고 아직 응답하지 않은 요청 | 미응답 상태 조회·정규 응답 절차 | 유효한 요청과 수명주기 증거가 미응답임을 뒷받침 |
| 필수 상태 누락·형식 손상·소유권 모순 | 해당 자료를 정상 조회·실행·재개·변경에 사용하지 않고 원본 보존. 안전한 진단은 제공 | 손상 필드로 권한·예산·효과 상태를 추론하지 않음 |
| 격리 요청 | owner가 안전성을 입증한 범위만 원본을 보존하며 격리 | 신뢰할 수 있는 경로·소유권, 최신 리비전·참조·활성 작업 검사, 원본 바이트 보존과 재사용 차단 |
| 물리적 삭제 요청 | 삭제 허용인 자료만 최신 검증 후 명시적으로 실행 | 살아 있는 참조·필수 증거를 잃지 않고 권한·예산·효과 상태를 초기화하지 않는다는 owner의 근거 |
| 손상 때문에 소유권·참조·필수 증거를 판단할 수 없음 | 이동·삭제 거부, 원위치 보존과 사용 차단 | “참조 없음”이나 “효과 없음”으로 간주하지 않음 |
| 삭제 금지인 증거 | 허용된 조회·진단·보존 기능만 제공; 격리도 별도 안전성 판단 필요 | Application의 삭제 요청이나 보존 기간 경과가 금지를 해제하지 않음 |

여기서 안전성 입증은 작업 시점에 검증 가능한 소유권·참조·상태·리비전 증거를 뜻한다.
원본 hash만 같거나 경로가 소유 루트 안에 있다는 사실만으로 삭제가 안전해지지 않는다.
내용을 읽을 수 없는 기록도 신뢰할 수 있는 주변 증거로 대상과 영향을 확인할 수 있을 때만
제한된 격리·삭제가 가능하다. 필요한 증거 자체가 손상됐다면 작업을 거부한다.

격리는 삭제나 복구와 별도 작업이다. 원본 바이트와 출처를 보존하고 일반 Reader가 새 자료나
미응답으로 오인하지 않게 해야 한다. 이동·차단 표식·참조 변경이 필요하면 owner가 한 저장
단위로 묶고 재시작 후에도 검증한다. 격리 사실만으로 승인 취소, 사용량 0, 외부 효과 없음이나
재실행 허가를 만들지 않는다. 진단 조회만으로 원본을 이동하거나 지우지 않는다.

손상된 하위 기록을 파싱할 수 없다는 이유로 상위 Session·Project·Component 삭제를 통해
보호를 우회할 수 없다. 직접 삭제·상위 트리 삭제·정리 계획·복원은 같은 owner의 보호 조건을
사용한다. 정상 도메인의 명시적 종료와 살아 있는 도메인의 예산 초기화를 구분한다.

## 승인·예산·외부 효과의 독립성

이 계약은 Resume뿐 아니라 **모든 승인 요청·응답·갱신·취소 기록**에 적용한다. 사람 응답과
정책 응답 모두 포함하며 Refinement 같은 별도 승인 도메인은 자기 owner가 상태 전이를 정의한다.

- 정상 미응답은 유효한 수명주기 상태다. 응답·취소·갱신 파일이나 필수 필드가 사라진 상태를
  미응답으로 복원하지 않는다. actor·만료·revision·후속 요청 연결도 필드 owner가 검증한다.
- 현재 실행 권한, 승인 결정, 남은 호출 예산, 외부 효과 상태를 각각 검증한다. 어느 하나를
  다른 판단의 대용으로 쓰지 않는다. Tool 사용량으로 승인이나 효과 발생 여부를 추론하지 않는다.
- 새 Run은 새 실행 상태와 소유권을 갖지만 Resume 계보의 논리 Tool 사용량·한도는 보존한다.
  Project quota의 유효한 사용량도 Session 삭제나 격리로 줄어들어서는 안 된다.
- 불확실한 효과 원장을 지우거나 완료 영수증을 버려 Tool을 다시 실행하지 않는다. 폐기·포기는
  실제 효과의 취소가 아니며, 기록을 읽을 수 없다는 사실은 효과 없음의 증거가 아니다.

응답·갱신·취소와 허용된 격리·삭제는 동일한 workspace 소유권 아래 최신 상태를 확인한다.
연결 기록·필수 존재 증거·리비전·차단 상태는 owner가 정한 트랜잭션 단위로 확정하며
알림은 commit 후에만 보낸다. stale 요청과 동시 Resume 접수도 재검증한다.
이미 확정된 실행을 승인 취소만으로 되돌렸다고 보고하지 않는다.

## 공통 구현 재사용과 복구 한계

| 기존 구현 | 재사용 범위 | 유지할 제한 |
|---|---|---|
| WorkspaceOwnership, StorageIO, TransactionManager와 공통 파일 함수 | 잠금·원자 저장·rollback·after_commit, owner가 정한 관련 기록 묶음 | 인프라에 승인·예산·효과 해석을 추가하지 않음 |
| revision_token/check_revision, tree_snapshot, generation/revision | 계획 이후 변경·ABA·stale 적용 검출 | 적용 시 최신 원본과 참조를 다시 확인; 동시 삭제 우회 금지 |
| Checkpoint/TurnDeletion/Job 계획 | 명시 대상·blockers·계보·lease 검증 | 정상 삭제와 손상 격리의 허용 조건을 혼합하지 않음 |
| DirectoryBackups, Repository.read_backup, Component.validate_backup | 체크섬·staging·owner 검증·새 대상 공개 | checksum 성공을 의미 무결성으로 보고하지 않음. 중앙에서 하위 형식 해석 금지 |
| Component.references/history_references | 소비 owner가 실제 참조를 제공 | 비활성 Component·상위 삭제도 확인. 모르는 참조를 임의로 없다고 판단하지 않음 |

트랜잭션의 삭제용 임시 rename은 지속적인 손상 격리가 아니다. 이미 안전성 검증과 삭제
확정을 마친 작업의 GC·중단 복구는 기존 결정의 기술적 완료다. 인프라는 새로운 대상을
선정하지 않는다. 손상된 삭제 의도는 임의 정리하지 않는다. 확정 전 실패의 rollback과
검증된 임시 staging 정리도 보존 기간에 따른 자동 삭제 정책과 구분한다.

JSONL 끝줄이나 identity·활성 포인터 소실을 근거 없이 미완성 쓰기로 간주하지 않는다.
트랜잭션으로 입증된 미확정 쓰기는 undo할 수 있지만, 확정 여부를 모르는 원본을 절단하거나
기본값으로 복원하지 않는다. 파생 인덱스의 재생성도 owner가 검증한 원본에서만 가능하다.
백업 복원은 필수 증거 검증을 우회하거나 현재 실행 계보를 과거 상태로 초기화하는 수단이 아니다.
자동 migration·구 형식 Reader·필수 상태의 추정 복구는 제공하지 않는다.

로컬 파일의 원자성은 [저장 트랜잭션](storage-transactions.md)의 파일시스템·잠금 범위다.
외부 Tool 효과, 외부 DB·SDK, 다른 workspace와 분산 원자성을 약속하지 않는다.
임의의 외부 작성자가 모든 증거를 함께 제거하는 상황까지 로컬 표식만으로 탐지한다고 주장하지 않는다.

## 감사에서 확인한 미해결 계약

원감사는 영속 자료 38개 그룹, llm Python 175개 AST·실제 호출·Schema·Reader/Writer와
관련 문서를 대조했다. 다음은 원감사의 요약이다. 문서 원칙만으로 해결된 것으로 처리하지 않으며,
실제 보강 범위와 결과는 [단계별 검증 기록](lifecycle-verification.md)을 따른다.
실행 결과와 원감사 산출물 위치는 [P1 검증 기록](p1-verification.md#영속-데이터-감사와-추가-원칙)을 따른다.

| 감사 ID | 소유 구현체·근거 | 보강할 계약 |
|---|---|---|
| L01 | InteractionRequest.from_dict, InteractionRepository.envelope/effective; 만료 누락 후 실제 효과, 응답 소실·취소 필드 누락 후 pending 재현 | 생성/Reader 분리, 필수 존재·상태 전이·원자 저장, 손상 사용 차단 |

## 후속 구현 게이트

| 순서 | 작업 | 필수 검증 |
|---|---|---|
| H1 | 승인 상태 소실·RAG 원본 삭제·Session 삭제의 예산 초기화 차단 | 실제 실패를 저장소 회귀로 편입. 손상 후 추가 Run·모델·Tool 효과 0, 원본 보존, R3 max_tool_calls=1 및 mutation 유지 |
| H2 | 모든 owner의 필수 필드·존재·상태 계약, 승인 전체와 Refinement 포함 | 정상 미응답·명시 None 구분, 필드/파일 소실·잘못된 타입·갱신 연결·리비전 오류 거부 |
| H3 | owner별 안전성 검증을 전제로 한 격리·명시 삭제 | 증거 불충분 시 원위치 보존, 허용된 격리의 바이트 보존·재시작 차단, 동시 응답/갱신/취소/Resume/삭제와 crash 원자성, 삭제 뒤 증거 초기화 없음 |
| H4 | 보존·선정·시점 정책을 Application으로 직접 이관 | Backend 자동 선정 없음, 요청에 대한 안전성 거부 유지, 기존 확정 삭제의 기술적 GC 유지 |
| H5 | 백업·참조·나머지 Component 계약 | owner별 검증, 직접/상위 삭제 보호 일치, 손상 백업 거부·원본과 대상 보존 |

H1도 승인·RAG·삭제/예산을 나누어 검증한다. [Level 1–3 검증 정책](verification-policy.md)에 따라
소단계는 모든 관련 계약·통합·핵심 안전성·정적 감사와 실제 효과/원본 보존을 검증한다. 범위가
입증되면 전체 회귀 없이 로컬 소단계 완료·독립 커밋할 수 있다. H1–H5 각각의 최종 완료와
관련 소단계 묶음 게이트에서는 전체 LLM/Hub를 검증한 뒤 작업 브랜치에 Push한다. 핵심 안전성 실패가
남으면 해당 보강을 계속하거나 차단 사유를 보고하며 A–F로 넘어가지 않는다. 실제 인증 모델,
커널 short-write·전원 손실·네트워크 파일시스템은 실행 증거가 확보되기 전까지 미검증이다.
