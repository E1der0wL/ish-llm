# 계약 선언과 의미 해석의 단일 소유

2026-10-22에 확정한 현행 설계 계약이다. [클린 리팩터링](clean-refactor.md)의 단일 선언과
[Schema 소유권](schema-ownership.md)을 보강한다. 구현의 적합성은 별도로 검증하며,
확인된 미완료와 조사 범위는 [후속 작업](ownership-refactor.md)에서 추적한다.

## 기본 규칙

프로그램의 구조·해석·검증·상태 전이·저장·통신·실행 판단을 결정하는 고정 문자열과 값에는
하나의 정규 Owner가 있어야 한다. 해당 계약은 Owner의 선언에서 정의하며, 다른 계층은
그 문자열이나 값을 다시 작성하지 않고 Owner의 타입·상수·속성·검증 함수·Projection·공개 API를
사용한다. 사용 횟수가 한 번이어도 적용한다.

Schema·Reader·Writer·검증기·소비자는 같은 선언에서 파생하거나 그 선언을 참조한다.
허용값 목록·필수 필드 집합·전이 규칙·기본값·수치 제약도 계약이다. 선언을 상수로 옮겼더라도
소비자가 의미나 검증을 독립적으로 재구현하면 책임 일원화가 완료된 것이 아니다.

각 계약의 의미 해석·검증·상태 전이에는 정규 Owner와 구현 경로를 둔다. 신규·중첩·재개 등
실제 소비 경로는 그 구현을 사용한다. 저장·실행·재개 경계에서는 최신 상태에 대해 Owner의
검증을 필요한 시점에 다시 수행한다. 검증 함수의 반복 호출과 검증 규칙의 중복 구현을 구분한다.

## 적용 대상과 소유 기준

아래 Owner는 역할 분류다. 실제 작업에서는 계약마다 구체적인 모듈·타입·심볼 하나를 정규
선언 위치로 지정한다. Record·Schema·Repository 모두를 동등한 원본으로 남기지 않는다.

| 종류 | 정규 소유 기준 |
|---|---|
| 상태·전이 | Run·Step·Message 등 해당 상태 Owner. 상태 값, 허용 전이와 전이 검증 포함 |
| 이벤트 이름·payload | 이벤트를 정의하는 도메인 또는 실행 Owner |
| 오류 코드·분류 | 해당 실패 경계 Owner. 표시 문구·오류 분류·실행 허가는 구분 |
| 영속 필드명 | 해당 Record·Schema·Repository 중 지정된 정규 선언 Owner |
| metadata의 계약 필드 | 해당 내부 metadata 구조를 정의하는 Owner |
| 설정·정책 키 | Project·Engine·Component·Adapter 등 실제 의미 Owner |
| 리소스 종류 | 공통 참조 형식은 ResourceRef, 구체적인 종류는 해당 도메인·확장 Owner |
| 파일명·저장 경로 | Paths·Repository·저장 형식 중 해당 구조의 Owner |
| 프로토콜·저장 버전 | 해당 프로토콜·Record·저장 Owner. 다른 형식의 버전을 하나로 합치지 않음 |
| 작업 명령·결정 종류 | 해당 동작·선택·판정을 정의하는 Owner |
| 출력 visibility·operation | 출력 계약 Owner |
| SDK wire 키·고정 값 | 해당 Provider Adapter의 인코더·디코더 또는 프로토콜 선언 |
| 허용값·판별자 | 저장 방식·메시지 역할·콘텐츠 종류·실행 모드 등 해당 의미 Owner |
| 기본값·수치 제약·단위 | 해당 설정·정책·인프라 Owner. 최소·최대·길이·시간 단위·캐시 크기·인덱스 간격 포함 |
| 공개 요청·응답·조회 필드 | 해당 API·Projection Owner. 비영속 설정 설명·조회 결과도 포함 |
| 권한·Capability·효과 분류 | 해당 권한·Tool 실행 계약 Owner. 승인 동작·격리·효과·권한 범위 포함 |
| 필드 집합·무결성 규칙 | 해당 Record·승인·Checkpoint Owner. 필수·불변·수정 가능·서명·지문 대상 필드 포함 |
| 등록 식별자·이름 공간 | Engine·Component·handler 등 등록 구현체 또는 등록 프로토콜 Owner |
| 특수값의 의미 | 해당 필드 Owner. all·unknown·비활성·무제한 및 Missing/Null/Value 구분 포함 |
| 외부 인터페이스 식별자 | 해당 경계 Owner. 환경 변수명·CLI 옵션·HTTP 헤더·미디어 타입 포함 |

## 선언과 참조의 표현

- dataclass 필드·Enum·Schema·속성·검증 함수도 선언이 될 수 있다. 필드별 문자열 상수를
  기계적으로 추가하지 않는다. 타입 선언이 원본이면 직렬화와 Schema가 그 선언을 활용한다.
- Owner의 경로 속성 안에서 파일명을 한 번 정의하고 소비자가 그 속성을 사용하는 방식도
  단일 소유다. 소비자가 경로 문자열을 재조합하거나 저장 파일을 직접 해석하지 않는다.
- 같은 철자라도 의미가 다르면 해당 도메인의 Owner를 유지한다. 값이 같다는 이유로 모든
  버전·상태·숫자를 합치지 않는다. 같은 계약을 다른 이름의 상수로 복제하는 것도 금지한다.
- 조회 Projection은 필요한 필드 선택과 변환을 소유할 수 있다. 원본 필드 의미·필수 증거·
  검증은 원본 Owner를 사용한다. 소비자마다 저장 형식의 부분 Reader를 만들지 않는다.
- 계약 값을 Owner 밖에 옮긴 뒤 alias·문자열 조합·동적 getattr로 감추지 않는다. 전역 상수
  파일이나 고정 helper만을 위한 registry·adapter를 추가하지 않는다.
- 상수 import만으로 계층 경계를 넘을 수 없다. Engine이 Adapter의 wire 상수를 import해
  SDK 응답을 해석하는 대신 Adapter가 반환한 공통 모델을 사용한다.
- 기본값·허용값을 일원화하는 작업은 새로운 실행 기본값을 만드는 허가가 아니다. 원본 요청과
  저장 설정, 명시적 재시도·Missing/Null/Value·정책 narrowing의 현재 의미를 보존한다.

## 선언 위치와 구현부 리터럴

2026-10-23 보강: 프로그램이 정한 문자열·값·필드 집합·제약은 해당 Owner의 명시적인 선언
영역에 둔다. 실행 로직에서 다시 정의하지 않는다. 같은 값을 한 번만 사용해도 적용하며,
사용 파일의 상단으로 옮기는 것만으로 다른 Owner의 계약을 소유할 수는 없다.

| 선언 종류 | 일관된 위치·표현 |
|---|---|
| 상태·종류·판별자 | Owner 모듈의 Enum 또는 해당 타입의 선언부 |
| 고정 필드·직렬화 이름·필수 여부 | Record·요청·응답 타입의 필드 또는 정규 Schema 선언. 직렬화 이름·제약은 해당 필드 metadata에 함께 둠 |
| 구현 기본값·한도·파일명·경로 요소 | 소유 클래스의 docstring 바로 아래, 메서드보다 앞 |
| 모듈 자체가 소유하는 값 | import 뒤, 함수·클래스보다 앞 |
| 표시·오류 문구·진단 이름 | 해당 UI·오류·관측 Owner의 선언 영역. 외부 동작을 결정하는 오류 코드와 표시 문구는 구분 |

기존 타입·Enum·Schema가 정규 선언이면 이를 재사용한다. 같은 필드의 문자열 상수 목록을
타입 옆에 다시 만들지 않는다. 선언부에서 구성한 Schema·전이표·문구 template의 리터럴은
선언 자체다. 실행부의 dict 조립·키 조회·수정·비교·기본값·경로 조합은 타입과 Owner API를
사용한다. 상수 키로 치환했더라도 고정 구조의 내부 소비를 dict로 유지하면 전환 완료가 아니다.

빈 컨테이너, 순회 인덱스 등 순수 언어·알고리즘 표현은 이름을 붙이기 위한 상수로 만들지
않는다. 다만 `0`·`False`·`None`도 사용량·재시도·상태·필수 여부·Missing/Null/Value를
결정하면 계약 선언 대상이다. 표시 문자열도 선언 영역으로 정리하되, 독립 wire 기대값·
오류 재현 fixture·문서 예제는 제품 선언을 가져와 독립 검증을 없애지 않는다.

## 고정 구조 데이터의 생성·조회·직렬화

프로그램이 고정된 의미로 해석하는 데이터 구조는 해당 Owner의 명시적 타입과 API로 제공한다.
소비자는 저장·전송용 딕셔너리의 필드 구조를 직접 조립하거나 해석하지 않는다. 딕셔너리와
내부 객체 사이의 변환은 지정된 Owner의 경계에서 수행한다. 사용 횟수와 관계없이 적용한다.

1. **단일 선언**: 필드명·타입·필수 여부·허용값·제약·직렬화 이름의 정규 선언을 하나로 둔다.
   Schema·Reader·Writer·검증기는 같은 선언을 사용한다. dataclass·Schema·상수 목록에 같은
   구조를 독립적으로 복제하지 않는다. 의미가 다른 조회 Projection은 별도 Owner를 명시한다.
2. **내부 소비**: 고정 구조의 기록·설정 snapshot·조회 결과·실행 판단은 Owner 타입의 속성·
   메서드로 소비한다. 상수 키로 치환하거나 TypedDict 주석만 추가한 것을 완료로 보지 않는다.
   공개 JSON을 받는 경계에는 Owner Reader를 사용하고 소비자별 부분 Reader를 만들지 않는다.
3. **검증된 읽기**: Reader는 필수 필드·타입·버전·identity·무결성을 검증한다. 필수 기록 누락을
   `.get(..., default)`로 정상 상태로 바꾸지 않는다. Missing/Null/명시값의 차이를 보존한다.
4. **응답과 Projection**: 반환 딕셔너리는 지정된 응답 Owner가 외부 경계에서 직렬화한다.
   서비스·Manager·Hub가 필드와 중첩 구조를 반복 조립하지 않는다. Projection은 원본 Owner의
   검증·정책을 재구현하지 않으며, 저장 레코드의 일부 필드만 읽어 검증을 우회하지 않는다.
5. **변경과 사본**: 고정 내부 구조는 Owner의 검증된 변경 API를 사용한다. 입력 patch도 Owner가
   해석·검증한다. 조회 결과의 중첩 dict/list를 수정해 원본이 바뀌지 않도록 사본·불변 경계를
   보장한다. frozen dataclass만으로 중첩 데이터의 불변성을 가정하지 않는다. 잠금·CAS·승인·
   예약·트랜잭션과 실제 쓰기 경계의 최신 검증을 유지한다.
6. **열린 데이터**: 사용자 metadata·동적 ID map·허용된 확장 옵션·JSON Schema 문법에는 dict를
   사용할 수 있다. 그 안에서 Backend가 고정 의미로 해석하는 부분은 Owner 계약으로 분리한다.
   독립적인 wire 기대값·음성 fixture·문서 예제의 리터럴은 계속 유지한다.
7. **외부 계약 보존**: 이 정리는 기존 저장 JSON·공개 응답·원본 요청의 모양이나 의미를 바꾸는
   허가가 아니다. 새 기본값·호환 Reader·이중 실행 경로를 도입하지 않는다. 파싱된 객체와
   Projection은 메모리 표현이며 별도 정규 정의로 저장하지 않는다.

완료 시 선언 → 검증된 읽기 → 내부 소비 → 명시 변경 → 직렬화를 연결해 확인한다.
Owner 밖에 남은 고정 키 조회·dict 조립은 각각 근거를 분류한다. 정적 검사와 기능 시험 통과만으로
전체 전환 완료를 선언하지 않는다. 기존 미전환 경로는 [후속 작업](ownership-refactor.md)에 남긴다.

## 책임 경계 점검

Owner는 책임 단위이며 여러 협력 객체로 구현할 수 있다. 클래스 길이·메서드 수·동사 개수보다
변경 이유, 보호하는 불변식, 공개 경계를 기준으로 나눈다. 여러 Owner를 호출하는 조율과 각
Owner의 판단을 직접 재구현하는 것을 구분한다. 같은 의미와 불변식을 공유하는 범위만 공통화한다.

| 점검 질문 | 요구하는 경계 |
|---|---|
| 한 클래스가 저장·검증·정책·실행·UI 책임을 함께 구현하는가? | 독립적인 변경 이유를 분리. 조율자는 공개 작업과 순서를 연결 |
| 여러 클래스가 같은 전이·검증을 구현하는가? | Owner의 규칙·검증을 공유하고 각 신뢰 경계에서 호출 |
| 서비스가 도메인 내부 구조에 접근하는가? | 내부 dict·필드를 직접 해석·수정하지 않고 명시적 조회·변경 API 사용 |
| Manager가 Repository 파일 구조를 해석하는가? | 경로·manifest·저장 키·Reader는 저장 Owner, 작업·트랜잭션 조율은 서비스 |
| Hub가 Backend 정책을 중복 계산하는가? | 합성·실행·승인·재개·삭제 판단은 Backend 공개 결과 사용. 앱 선택·표시·UX는 Hub |
| Adapter 밖에서 SDK별 필드를 분기하는가? | Adapter에서 공통 모델로 해석. opaque 운반과 해석은 구분 |
| 실행 경로마다 binding·승인을 복제하는가? | 신규·중첩·재개·다중 Agent가 동일 Owner 사용. 경로 차이는 명시 입력·계약으로 표현 |
| 원본과 변경 권한이 여러 곳에 있는가? | 원본·변경 API를 특정. 캐시·Projection·UI snapshot은 별도 원본이나 실행 권한이 아님 |
| 책임 분리로 검증과 쓰기가 떨어지는가? | 잠금·CAS·예약·영수증·확정 순서를 보존하고 최신 상태로 검증 |
| 의존성 방향이 뒤집히거나 순환하는가? | 도메인은 Hub/SDK 구현에, 공통 저장 인프라는 승인/예산 의미에 의존하지 않음 |
| 비동기 작업·자원 수명이 불분명한가? | 생성·취소·대기·종료·stream·lock·client 해제 Owner 지정. timeout/retry/cleanup 중첩 점검 |
| 오류·복구 가능성을 소비자가 재해석하는가? | 구조화된 오류·공개 복구 계약 사용. 문자열 파싱으로 실행 허가를 추론하지 않음 |
| 확장 구현이 내장 구현의 내부 구조를 요구하는가? | 주입 Repository·Engine·Component·Adapter도 공개 계약과 안전성 검증을 통과 |

UI 입력 검사는 Backend Schema·검증 계약을 활용할 수 있다. 입력 편의 검사를 이유로 Backend의
저장·실행 검증을 생략하지 않는다. 계획 조회와 실행 사이의 변경, 승인 만료·취소, revision/CAS,
현재 예산·효과·Checkpoint 증거는 실제 작업 경계에서 다시 확인한다. 한 작업 안의 읽기 재사용도
그 잠금·snapshot·revision 범위에 한정하며 전역 캐시로 최신 검증을 대체하지 않는다.

## 적용 경계와 독립 검증

- Application metadata·사용자 입력·동적 ID·선택 구현체의 확장 인자는 그 소유자의 데이터다.
  Backend가 고정 의미로 해석하는 필드가 되면 이 계약을 적용한다. ResourceRef의 확장 종류나
  미지의 SDK 옵션을 일괄 전역 Enum·닫힌 allow-list로 바꾸지 않는다.
- SDK의 고정 wire 키는 Adapter에서 소유한다. 허용된 열린 경계의 미래 옵션·opaque 데이터는
  현재 전달 계약을 유지한다. 외부 표준의 의미는 그 규격에 있으며 로컬 해석은 지정 경계에서 한다.
- 표시 문구·진단용 이름·단순 산술 초기값은 계약 여부를 의미로 판정한다. 프로그램의 분기·
  저장·통신·검증을 결정하면 대상이다. 기술 sizing·외부 규격이라는 이유로 소유권 없이 중복
  선언하는 예외를 두지 않는다. Owner 안의 실제 선언과 비계약 표현은 근거를 구분해 기록한다.
- 공개 JSON·wire·현재 저장 형식을 독립적으로 고정하는 시험과 Fixture는 기대 문자열·값을
  직접 기록할 수 있다. 기대값까지 제품 선언에서 생성하여 잘못된 변경을 함께 수용하지 않는다.
  내부 흐름 시험은 Owner를 참조한다. 잘못된 필드·중복 선언을 재현하는 음성 사례도 보존한다.
- 문서 예제와 과거 검증 Fixture는 설명·독립 증거이며 제품 선언의 두 번째 원본이 아니다.
  이 규칙을 맞추기 위해 과거 실패·통과 결과나 실제 효과 횟수 Assertion을 바꾸지 않는다.

## 검증과 완료 조건

계약별로 Owner → 선언 → Schema/검증/Reader/Writer → Projection/공개 API → 실제 소비자와
실행 경로를 연결해 확인한다. 사용 횟수나 정적 후보 0건만으로 완료를 선언하지 않는다.
정적 검사가 추적하지 못하는 동적 경로와 미분류 후보도 작업 목록에 남긴다.

완료에는 다음 증거가 필요하다.

1. 정규 선언·해석·변경 책임과 실제 소비자가 특정되고, 대상 범위의 독립 재선언·중복 해석이 해결됨.
2. Owner 계약 시험, 직접 소비자와 확장 구현 시험, 같은 계약을 지나는 실행 경로의 검증이 통과함.
3. 실패·중단·취소·재개 시 원본·예약·영수증·실제 효과와 원자성이 보존됨.
4. 기존 안전성 Assertion, 누락·중복·Skip 엄격 판정, R3 mutation과 원격 CI 필수 검증이 유지됨.
5. 변경 영향에 따른 [Level 1–3](verification-policy.md)을 통과하고, 조사·구현·로컬 검증·전체 게이트·
   정확한 SHA의 원격 CI 상태를 구분해 기록함.

문서 합의, 정적 개별 분류, 기능 회귀 통과는 각각의 증거다. 어느 하나도 전체 계약 소유권 감사의
완료를 자동으로 증명하지 않는다. 보강 작업은 [후속 작업 목록](ownership-refactor.md)을 따른다.

### 저장소 전체 완료 게이트

전체 범위는 `llm/`·`hub/`의 모든 제품 파일과 실제 실행에 쓰이는 assets다. 이미 수정한 파일도
포함한다. 파일 목록과 내용 hash를 고정하고 각 파일의 계약·비계약 분류를 연결한다. 기존
38개 데이터군 감사와 개별 검토는 재사용하되, 선언 위치·고정 구조 소비를 검사하지 않은
과거 근거를 이번 규칙의 통과 증거로 자동 승계하지 않는다.

감사는 dict 생성·반환·조회·갱신, `==`/`!=`/`in`/`match`, 기본값·허용값·필수 필드 집합,
경로·프로토콜·동적 속성 접근, 중복 검증·상태 전이·정책 해석을 포함한다. AST 후보 수는
계약 위반 수가 아니며 정적 도구가 보지 못하는 assets·동적 경로도 별도로 검토한다.

전체 완료에는 다음 잔여 항목이 모두 **0**이어야 한다.

- 검토하지 않은 제품 파일과 변경 후 근거가 무효화된 파일.
- 분류하지 않은 후보, 확인된 계약 위반과 미전환 실제 소비자.
- 소유·검증·변경 책임이 불분명한 계약과 해결되지 않은 중복 의미 해석.
- 근거 없는 제외, 검증되지 않은 예외, 동적 경로·assets의 미검토 항목.

계약별로 선언 → 생성/검증 → 읽기/비교 → 변경 → 직렬화 → 실제 소비 경로와 시험을 연결한다.
범위를 줄여 잔여 항목을 목록 밖으로 빼거나, 정적 규칙이 잡는 일부 사례만 0으로 만든 뒤
전체 완료라고 기록하지 않는다. 소단계의 구현·Level 1/2 통과와 전체 계약 완료는 별도 상태다.
이 잔여 조건과 현재 소스의 Level 3, 정적·문서·R3, 정확한 Push SHA의 원격 필수 CI가 모두
통과해야 전체 완료다. 취소된 CI·검증 중 상태는 통과가 아니다.
