# 요청 준비 비용 분해와 중복 조회 제거

Hub의 표시용 조회만 개선한다. llm 실행 코드, 승인·재개·저장·도구 검증, 실제
fsync와 사용자 설정은 유지한다. 이번 작업은 커밋·배포를 포함하지 않는다.

## 계측 경계

실제 ish Prompt/PTK Enter, Hub worker, 현재 llm 공개 서비스와 로컬 HTTP/SSE
응답 서버를 연결한다. 소스·실행 데이터·Python 3.12.14 환경은 WSL의 Linux
파일시스템에 둔다. 사용자 프로젝트 정책은 읽기만 하고 별도 workspace에서
실행한다. 외부 모델의 추론·네트워크 시간은 포함하지 않는다.
PTK는 132×40 검사용 출력 장치를 사용한다. 첫 답변 시점은 `after_render`에서
해당 답변이 화면 버퍼에 반영된 시각이며, 실제 터미널·SSH 전송 지연은 제외한다.

진단 실행에서는 실제 저장 잠금의 획득 대기와 점유를 구분하고, 점유 중
Hub 준비 콜백을 따로 기록한다. 중첩 호출은 구간 합집합으로 계산한다.
잠금 대기는 다른 작업의 점유와 겹치므로 소요 시간에 다시 더하지 않는다.
공개 API의 전체 await 시간을 순수 디스크 비용으로 표현하지 않는다.
CPU 프로파일링과 최종 지연 비교는 별도 실행이다.

## 변경과 계약

- `ObservationReads`: 동일 키·동일 무효화 세대의 진행 중 조회를 공유한다.
  대기자 취소는 소유자에 전파하지 않는다. 소유자 취소는 기존 저장 drain 후
  대기자를 풀어 새 공개 조회를 허용한다. 오류는 그대로 전달하고 실패 결과를
  캐시하지 않는다. 별도 Task/worker 수명이나 영구 캐시를 만들지 않는다.
- `SnapshotReader`: 알려진 최신 Run의 상태 변경에는 최신 목록을 다시 읽지
  않는다. paused 목록의 구성에 영향을 주지 않는 완료 이벤트도 목록을 보존한다.
  목록의 기존 만료 시점은 연장하지 않는다. 새 Run, interaction, 외부 변경,
  이벤트 유실, 삭제와 만료는 기존 공개 조회로 재조정한다.
- `HubRuntime`: QUEUED 접수로 바뀌지 않은 Run 표시 기록은 보존한다. 접수와
  실행 검증은 신선한 공개 API 경로를 그대로 사용한다. durable 접수 이전에
  성공을 표시하거나 재개를 새 submit으로 치환하지 않는다.

앞선 상세 화면 조회 일괄 지연 실험은 적용하지 않았다. UI 갱신 주기나 준비
상태를 인위적으로 지연하지 않으며 첫 답변 표시 시간도 함께 비교한다.
문맥 준비에는 Tool capability 구성·출력 저장소 검증이 포함된다. 이를 단순한
화면 조회로 취급하거나 Run 사이에서 검증 없이 재사용하지 않는다.

계측 원본, 소스 해시, 실패를 포함한 검사 기록은
`tests/hub/reports/preparation-ownership-20261101/`에 보존한다.

## 전후 비교

같은 백엔드·host 바이트를 확인한 고정 소스로 변경 전/후를 ABBAAB 순서로
각 3회 실행했다. 각 실행은 인사 두 번, 실제 file_read 두 번, 800행 답변,
그 이력을 가진 후속 요청을 포함한다. 네 세션, 자동 제목과 후처리를 유지하고,
전송되는 도구·메시지 개수 및 총 모델 호출 횟수가 같은지도 확인했다.
각 프로세스의 주 대화 호출 8회·보조 호출 4회, 총 36개 요청이 완료됐다.
서버는 loopback이며 실제 외부 모델 추론 시간은 측정하지 않는다.

중앙값, 단위 초:

| 조건 | HTTP 도착 전→후 | 첫 답변 표시 전→후 |
| --- | --- | --- |
| 첫 인사 | 1.353 → 1.357 | 1.863 → 1.851 |
| 후속 인사 | 1.461 → 1.207 | 1.860 → 1.492 |
| 첫 파일 읽기 | 1.972 → 1.954 | 4.647 → 4.479 |
| 반복 파일 읽기 | 1.897 → 2.194 | 5.334 → 4.846 |
| 긴 답변 | 2.235 → 2.288 | 2.555 → 2.624 |
| 긴 이력 후 인사 | 1.426 → 1.385 | 2.323 → 2.278 |

후속 인사는 준비가 약 0.25초 단축되지만 첫 요청은 사실상 같고, 반복 파일
읽기의 준비 시간은 늘었다. 모든 조건이 빨라졌거나 1초가 보장된다는 결과가
아니다. 화면 주기·본문 공개·완료 검증을 늦추는 처리는 추가하지 않았다.
긴 답변의 첫 표시 중앙값에는 0.069초 증가가 있어 절대적인 무지연도 주장하지
않는다. 세 번의 표본과 후처리·화면 재조정의 실행 시점에 따른 편차가 있다.
후속 요청은 보이는 완료와 등록된 보조 Task 종료 후 전송했으나 아직 예약되지
않은 콜백의 완전한 정지까지 증명한 것은 아니다.

## 남은 준비 비용

별도의 상세 진단 실행에서 첫 요청 1.374초를 중복 없이 분해하면 다음과 같다.

| 구간 | 초 |
| --- | ---: |
| Hub 공개 조회가 점유한 저장 잠금 | 0.403 |
| Hub 확장 콜백이 점유한 잠금(위임한 백엔드 작업 포함) | 0.168 |
| 나머지 백엔드 실행·검증·저장 잠금 점유 | 0.702 |
| 잠금 밖의 전송·스케줄링 등 | 0.101 |

fsync 약 0.238초는 위 구간에 이미 포함된다. 잠금 대기의 합 약 0.776초는
다른 작업과 겹치므로 추가 합산하지 않는다. Hub 공개 조회 비용도 순수 Hub
CPU가 아니라 백엔드 검증을 수행하는 공개 조회의 점유다. 나머지 백엔드 구간을
더는 줄일 수 없는 이론적 하한이라고 해석하지 않는다. 본 작업에서는 그
실행·저장·승인 계약을 변경하지 않는다.

## 채택하지 않은 실험

표시용 Session 레코드와 실행 상태를 분리하고 preflight 결과를 표시 캐시에
전달하는 실험도 수행했다. 첫 요청의 Session 조회는 3회에서 1회로 줄었으나
별도 ABBAAB 비교에서 첫 인사 준비는 1.348→1.375초, 후속 인사는
1.450→1.544초였다. 긴 답변의 첫 표시는 2.687→2.940초로 늦어졌다.
호출 감소만으로 실사용 개선이라고 판단할 수 없어 제품 코드에서 제외했다.
두 비교의 환경 편차가 있으므로 이 차이를 특정 코드 한 줄의 순수 비용으로
단정하지 않는다. 해당 실험·검사 기록은 `ready-*`, `comparison-ready`,
`results-ready.json`으로 남긴다. 최종 채택한 소스·성능 자료는 `final-source.json`,
`comparison`, `results.json`, `final-breakdown`이다.

## 검증 기록

- Linux Python 3.12.14, native filesystem의 `checked-source.json` 고정 소스에서
  전체 Hub 회귀 937/937 통과. 실패·오류·skip·누락·중복 0, 약 1,586초.
  명령은 `python -m tests.llm.run_regression --suite hub`이며, llm 전체 회귀를
  실행한 것은 아니다. 상세 결과는 이 작업 보고서 디렉터리의 `full/hub.json`.
- 최종 Hub 제품·테스트는 채택한 성능 계측 소스와 동일하다. llm/host 소스
  431개 파일은 작업 시작 당시 원본 바이트와 비교한다. 기존 미커밋 변경도 보존한다.
- 계약 검토는 변경한 Hub owner와 직접 테스트의 증거만 갱신한다. 정적 검사
  기록은 `gates/execution.json`, 코드·검토 범위 확인은 `guard.py`에 둔다.
- 제품 변경은 `observability/reads.py`, `observability/snapshot.py`, `runtime.py`.
  `tests/hub/test_observation_reads.py`는 공유 조회의 취소·오류·무효화 세대,
  최신·paused 목록의 구성 변화와 만료를 검증한다.

## 2026-11-01 추가 확인: 도구 스키마 파생

위 전체 회귀 기록과 별개의 작은 후속 변경이다. `tools/advice.py`와
`tools/resources.py`에서 새 `ToolRegistry`를 만드는 대신 공개 `derive()`를
사용한다. 이미 증명된 동일 스키마의 문법 검사만 재사용한다. 변경된 스키마,
handler binding, 실행 인자, 승인과 저장 확정은 기존 백엔드가 계속 검증한다.
새 프로세스 전역 캐시나 실행 권한 캐시를 추가하지 않는다.

검사용 기본 도구 구성으로 각 15회 측정한 결과, 승인 정보 부착의 스키마 문법
검사는 8→5회, 중앙값 31.46→20.43ms였다. RAG 도구 구성은 5→4회,
17.71→13.25ms였다. 이는 해당 구성 함수의 비용이며 요청 전체 절감량이 아니다.

실제 ish Prompt/Hub/backend와 로컬 HTTP/SSE를 연결한 ABBA 비교는 전후 각각
2회, 실행마다 인사·파일 읽기·긴 이력 등 6개 조건을 사용했다. 사용자 정책과
자동 제목·후처리를 유지하고 외부 모델 호출은 차단했다. 아래 값은 중앙값(초)이다.

| 조건 | 첫 HTTP 전→후 | 첫 본문 화면 반영 전→후 |
|---|---:|---:|
| 첫 인사 | 1.499→1.433 | 2.263→2.116 |
| 반복 인사 | 1.643→1.882 | 2.131→2.442 |
| 첫 파일 읽기 | 2.225→2.512 | 5.531→6.342 |
| 반복 파일 읽기 | 2.264→2.241 | 5.350→6.288 |
| 긴 입력 | 2.965→2.815 | 3.386→3.210 |
| 긴 이력 | 3.313→1.595 | 4.443→2.169 |

모든 실행에서 주 호출 8회·보조 호출 4회였고, 조건별 도구 수와 메시지 수도
동일했다. 개선과 악화가 섞이고 표본도 적으므로 전체 준비 시간이나 첫 본문
지연이 줄었다고 결론 내리지 않는다. 특히 긴 이력의 큰 차이를 이 변경의
효과로 단정하지 않는다. 재현 가능한 효과는 중복 스키마 검사 감소뿐이다.

Linux Python 3.12.14의 Hub 도구 승인·입력 진단·제약 집중 테스트 23개는
통과했다. 계약 검사 자체의 테스트는 14/16 통과, 감사 자료 불일치 2개 실패다.
변경 전 스냅샷에서도 같은 두 테스트가 실패하며, 오래된 검토 기록 16개와
누락된 `participant_manager.py` 인벤토리가 그대로 남아 있었다. 아키텍처의
개별 검토 근거도 변경 전후 동일하게 `tests/hub/test_settings.py` 해시가
불일치한다. 이번 두 도구 owner의 증거만 갱신했고 다른 감사 기록을 일괄
승인하지 않았다. 따라서 전체 계약 감사 통과나 전체 Hub 회귀 통과로 보고하지 않는다.

소스·비교·프로파일·검사 근거는
`tests/hub/reports/preparation-followup-20261101/`에 보관한다. llm 실행 코드와
사용자 workspace는 변경하지 않았다. 실제 원격 모델·사내 터미널 지연은 이번
비교에 포함되지 않는다. 적용 확인에는 해당 checkout의 Hub로 ish를 재시작해야 한다.

이후 감사 기록 갱신과 전체 Hub 재검증 결과는
[계약 감사 기록 갱신](contract-audit-refresh.md)에 별도로 기록했다.
