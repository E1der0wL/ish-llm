# llm 오류 처리와 체크포인트 공통 계약 작업 지침서

> **과거 요구·작업·검증 기록.** 본문과 당시 결과를 보존한다. “현재/최신/통과”는 작성 시점의 표현이며
> 새 구현의 호환성 의무나 오늘의 회귀 성공을 뜻하지 않는다. [문서 우선순위](../README.md)와
> [현행 검토 결과](../llm/documentation-review.md)를 먼저 확인한다.


> 이 문서는 백엔드 작업 전 전달한 요구사항 기록입니다. 아래의 당시 Hub 경로와 구현 상태는
> 현재 구조가 아닐 수 있습니다. 연결 완료 후의 동작은 [오류 계약](error-handling.md),
> [문맥 복구](provider-recovery.md), [RAG](rag.md)를 참고하세요.

`llm`을 사용하는 여러 애플리케이션이 오류와 체크포인트를 같은 의미로 해석하도록 백엔드의 공개 계약을 보강한다. 오류 원인과 실행 상태는 백엔드가 제공하고, 실행 가능 여부는 각 실행 서비스가 검증하며, 애플리케이션은 허용된 선택과 UI 표현을 담당한다.

이번 백엔드 작업의 수정 범위는 `llm/`, `tests/llm/`, `docs/llm/`이다. Hub 소스는 현재 요구사항과 사용 사례를 확인하는 참고 자료로 읽는다. Hub 연결 작업은 별도로 진행할 수 있도록 API와 변경 대응표를 제공한다. 이 문서는 백엔드 작업자에게 전달할 구현 요구사항이며, 아래의 추가 계약은 아직 구현된 API를 뜻하지 않는다.

이번 범위의 예제는 `docs/llm/`의 문서 예제와 `tests/llm/`의 공개 API 소비 테스트로 제공한다. 별도 예제 스크립트가 필요하면 `examples/llm/`을 추가 수정 범위로 명시한 뒤 진행하며, 배포 루트 `llm/` 안에 테스트나 예제 파일을 만들지 않는다.

## 1 작업 목표와 책임

다음 두 목표를 함께 달성한다.

1. 오류의 공통 데이터 계약과 근거 기반 분류를 백엔드에서 제공하고, 복구 선택과 실행 허용을 분리한다.
2. Run과 RAG Job의 체크포인트 조회·재개 판단·재개 포기·삭제를 공통 의미로 제공한다.

| 책임 | 소유자 |
| --- | --- |
| 오류 원문, 코드, 원인 체인, 발생 위치, 분류 근거 | 오류가 발생한 백엔드 경계 |
| 공통 오류 데이터 형식과 순수 분류 함수 | 백엔드 공통 모듈 |
| 부작용, 승인, 재시도 예산, 기한, 취소 여부 검증 | 해당 작업의 백엔드 실행 서비스 |
| 허용된 복구 후보 중 선택, 모델 분석 사용 여부, 제품 기본값 | 애플리케이션의 설정과 주입 콜백 |
| Run 체크포인트 내용·실행 의미·재개 검증 | 해당 Engine 및 선택된 handler |
| Run 체크포인트 저장·잠금·원본 연결·삭제 | RunRepository / CheckpointRepository 및 기존 수명 서비스 |
| RAG Job 체크포인트 의미·저장·잠금·검증·삭제 | RAGJobs / ComponentData 및 RAG 구현 |
| 번역, 사용자 설명, 알림, 버튼, 확인 창, 진행률 렌더링 | 애플리케이션 |

Core에 Hub, Prompt-Toolkit, Rich 의존성을 넣지 않는다. 모든 오류를 실행하는 범용 Manager나 `execute(action)` API를 추가하지 않는다. 공통 데이터와 순수 검증 규칙을 공유하고 실제 실행은 기존 서비스에 둔다.

Engine은 체크포인트 이벤트와 내용 검증을 제공하며 파일을 직접 쓰거나 삭제하지 않는다. 애플리케이션이 선택하는 실행 정책 값은 기존 Project의 해당 Engine·Component·서비스 정책 경로로 전달한다. Host 콜백은 구현과 선택 수단이며, Project의 실행 한도를 확대하는 별도 정책 권한이 아니다.

## 2 현재 구현에서 재사용할 부분

작업을 시작할 때 대상 저장소의 최신 구현과 아래 경로를 대조한다. 병행 작업으로 이미 추가된 기능은 재구현하지 않는다.

| 현재 경로 | 확인할 계약과 기능 |
| --- | --- |
| `llm/errors.py` | `CodedError`, `exception_chain`, `stable_error_code` |
| `llm/core/contracts.py` | `Diagnostic`, `ResourceRef`, `OperationProgress`, JSON 변환 |
| `llm/core/plans.py` | `CheckpointPlan`, `ResumePlan`, `TurnDeletionPlan`, 기존 복구·보관 계획 |
| `llm/core/checkpoints.py` | `ResumeAbandonment`, `require_checkpoint_plan` |
| `llm/policies/retry.py` | `RetryFailure`, `RetryDecision`, `RetryPolicy`, 수정 인자 검증 |
| `llm/providers/requests.py`, `retry.py`, `runtime.py` | Provider 오류 코드, 재시도, 상세 진단 |
| `llm/services/runtime/tools.py` | Tool 효과 정보, 재시도 허용, 승인과 실행 |
| `llm/services/runtime/runs.py`, `checkpoints.py` | Run 재개, 체크포인트와 효과 원장 |
| `llm/services/api.py`, `lifecycle/sessions.py` | 공개 조회·재개 포기·정리 API |
| `llm/components/rag/data.py`, `jobs.py` | Job 진행, 재시도, 취소, 체크포인트 정리 |

현재 `CheckpointPlan`은 Run과 RAG에서 이미 공유한다. 반면 `ResumePlan`은 Run 중심이며, Hub는 RAG의 상태값으로 재시도 가능 표시를 만들고 있다. Run의 체크포인트가 없을 때 처음부터 시작할 수 있는지도 Hub가 일부 판단한다. 이 판단을 백엔드의 공개 계약으로 옮기는 것이 핵심이다.

Hub 참고 자료는 다음과 같다. 해당 파일이 다른 작업 공간에 없다면 이 지침서의 의미와 테스트 조건을 기준으로 구현한다.

- `hub/errors/contracts.py`, `classification.py`, `adapters.py`, `policy.py`
- `hub/backend/execution/provider_recovery.py`, `recovery_input.py`, `recovery_model.py`
- `hub/backend/observability/failures.py`, `hub/ui/error_presentation.py`
- `hub/backend/history.py`의 `_unstarted_without_checkpoint`와 `retry`
- `hub/backend/project/rag_management.py`, `rag_progress.py`
- `tests/hub/test_error_contract.py`, `test_provider_recovery.py`, `test_rag_jobs.py`, `test_rag_extensions.py`
- `docs/hub/error-handling.md`, `provider-recovery.md`, `rag.md`

## 3 오류 계약 보강

### 3.1 하나의 정규 오류 표현

기존 `Diagnostic`과 명시적 오류 코드를 기준으로 오류 정보를 정규화한다. `Diagnostic`을 확장할지 별도의 오류 타입을 연결할지는 현재 구조에 맞춰 결정하되, 같은 실패에 서로 다른 코드·분류를 가진 두 개의 원본을 유지하지 않는다. Provider 진단은 세부 근거를 제공하고 공통 계약은 이를 투영하도록 한다.

`Diagnostic`은 정보·경고에도 사용된다. 오류 분류나 예외 체인 필드를 모든 진단에 의무화하지 않는다. 별도 오류 표현이 필요해도 기존 진단의 투영 또는 연결된 데이터로 제공하며 독립적인 오류 저장소나 실행 상태 원본을 만들지 않는다.

공개 계약은 다음 정보를 표현할 수 있어야 한다. 실제 공개 타입과 필드 이름은 구현 후 문서로 확정한다.

| 정보 | 요구사항 |
| --- | --- |
| 원래 코드와 메시지 | 정규 분류나 번역된 문구로 원래 오류를 덮어쓰지 않는다 |
| 발생 위치 | `ResourceRef` 기반 Project·Session·Run·Step·Component 참조와 필요한 호출 식별자 |
| 발생 경계 | Provider, Tool, Component, 환경, 백엔드, 애플리케이션 등을 구분한다. 책임 소재를 단정하는 필드가 아니다 |
| 작업과 단계 | 어느 호출의 어느 단계에서 발생했는지 식별한다 |
| 분류 | 큰 분류와 세부 원인, 확실성, 판단에 사용한 근거 |
| 원인 자료 | HTTP 상태, 예외 타입·체인, finish reason, 수집된 상세 메시지·traceback |
| 확장 자료 | 도메인별 JSON 정보. 분류와 재실행 허용의 의미를 임의로 바꾸지 않는다 |

Hub라는 제품 이름을 필수 enum 값으로 고정하지 않는다. 애플리케이션 오류도 같은 형식을 만들 수 있어야 하지만 백엔드가 Hub 렌더링 오류를 처리하거나 저장할 필요는 없다.

공개 객체는 JSON 왕복과 분리된 사본 전달을 지원한다. 예외, Task, 잠금, 연결 객체를 저장하지 않는다. 수집하지 않은 traceback이나 원인은 만들어내지 않는다. 이 작업에서 별도 비밀 저장소나 키 이름 차단 정책을 추가하지 않는다.

Provider의 상세 수집 여부·크기 제한은 기존 Provider 진단 설정을 존중하며, 그 설정은 Provider 진단에만 적용한다. Tool·Component·저장소 오류의 수집 설정으로 자동 상속하거나 전역 진단 정책으로 확대하지 않는다. 공통 오류 표현은 각 경계가 자신의 계약에 따라 제공한 정보를 정규화할 뿐, 추가 수집을 활성화하거나 누락된 자료를 채우거나 새로운 수집 한도를 만들지 않는다.

### 3.2 분류 규칙

Hub의 현재 큰 분류인 `service`, `access`, `contract`, `resource`, `execution`, `internal`, `unknown`을 출발점으로 검토한다. HTTP 4xx/5xx는 근거이며 전체 오류의 최상위 분류나 책임 구분을 대신하지 않는다.

SDK 예외·HTTP 응답·synthetic 500의 해석과 근거 추출은 계속 `providers/`가 소유한다. 공통 분류 함수는 각 경계가 제공한 정규화된 근거를 사용하며 SDK를 import하거나 Provider별 응답 구조를 복제하지 않는다. RunManager는 SDK 메시지를 해석하지 않는다. Tool·Component·저장 실패를 무조건 Provider 분류 함수에 넣어 `provider_failed`로 바꾸지 않는다.

- 구조화된 명시적 코드와 의미를 우선 보존한다. 안쪽 HTTP 원인 때문에 바깥쪽 승인 거절·예산 초과·취소 의미를 지우지 않는다.
- HTTP 상태와 상세 메시지는 같은 원인 항목에서 함께 읽는다. 상태가 있는 항목에 상세 메시지가 없으면 비어 있는 근거로 유지하고, 다른 원인의 메시지를 가져와 하나의 HTTP 오류처럼 판단하지 않는다. 다른 원인은 각각의 출처를 유지해 별도로 표현한다. 예외 체인을 여러 재시도 이력으로 해석하지 않는다.
- HTTP 400 중 문맥 길이 초과는 관련 오류 근거가 있을 때만 `resource/context`로 분류한다. 지원하지 않는 인자는 별도로 구분한다.
- 실제 5xx와 SDK가 잘못된 응답에 붙인 synthetic 500을 구분한다.
- 문자열 근거에 의한 판단은 추론임을 표시한다. 원문 요청, 일반 로그, 모델 설명에서 원인을 추측하지 않는다.
- `engine_failed`, `TypeError`, 파일 없음만으로 내부 버그나 모델의 잘못을 단정하지 않는다.
- 알 수 없는 오류 코드는 보존하고 `unknown`으로 전달한다. 분류를 추가했다고 자동 복구 권한이 생기지 않는다.

분류는 입력을 받아 결과를 돌려주는 순수 함수로 구현한다. I/O, 로그 기록, 모델 호출, 재시도를 수행하지 않는다.

Hub의 기존 분류·변환 코드는 사용 사례 참고용이다. 그대로 복사하지 말고 위 규칙에 맞춰 검증한다. 특히 상태와 메시지를 다른 원인에서 선택하는 fallback, 알 수 없는 코드의 의미를 안쪽 HTTP 오류로 덮는 처리를 가져오지 않는다.

### 3.3 진단의 저장과 조회

Run·Step·Component의 기존 저장 경로와 소유권을 유지한다. UI용 오류 파일이나 별도 로그 저장소를 만들지 않는다. 같은 실패가 계층을 통과할 때 중복 기록하지 않도록 기록 주체를 정한다.

중복 방지는 기존 Run/Step 결과와 Provider 운영 로그 중 하나를 제거한다는 뜻이 아니다. 같은 원인을 기존 호출·Step 식별자로 연결하고, 상위 계층이 새 원인이나 별도 복구 상태로 재생성하지 않도록 한다. 각 소유자의 기존 영속 결과와 진단 관찰 계약은 유지한다.

실패한 Step의 공개 진단과 Run 결과에서 같은 원인 정보를 조회할 수 있어야 한다. RAG처럼 독립 Job인 작업은 Job 소유 진단을 사용하고 관찰을 위해 Run을 만들지 않는다. 과거 로그를 파싱해 현재 실패 원인을 복원하는 호환 코드를 추가하지 않는다.

취소는 제어 흐름으로 유지하고 승인 대기·질문·일시정지는 기존 상태 및 interaction 계약으로 전달한다. 이를 일반 실패나 자동 복구 대상으로 바꾸지 않는다. 성공 결과가 `None`인 경우도 실패와 구분한다.

## 4 복구 선택과 실행 검증 분리

오류 계약은 원인을 설명한다. 복구 정책은 현재 실행 사실과 설정을 보고 허용 후보를 정한다. 애플리케이션 콜백이나 모델은 그 후보에서 선택하거나 수정안을 제안한다. 실제 실행 서비스는 직전에 다시 검증한다.

현재 Hub의 `RecoveryFacts.backend_admitted=True` 같은 내부 표시를 새 공개 API의 신뢰 근거로 삼지 않는다. 애플리케이션이 넘긴 `safe`, `retryable`, 부작용 없음 등의 값만으로 실행을 허용하지 않는다. 실행 서비스가 원래 작업과 효과 원장으로 확인한다.

검증에는 다음을 포함한다.

- 현재 호출의 부분 응답 수신 여부, 부작용 없음·발생·불명확 상태, 신뢰된 재시도 안전 선언
- 취소 여부, 시도 횟수, 기존 설정의 상한과 기한
- Tool이 명시한 수정 가능 인자, 전체 입력 검증, 승인 내용의 일치 여부
- 효과 원장과 operation key, 완료 영수증, 중복 요청과 동시 실행 여부

| 상황 | 유지할 동작 |
| --- | --- |
| 일시적 503·429·연결 실패 | 기존 Provider 정책의 예산과 대기 시간을 사용한다 |
| 확인된 문맥 초과, 축약 가능한 입력, 현재 호출에 응답·효과 없음 | 허용된 입력 축약 후 현재 Completion만 다시 시도할 수 있다 |
| 지원하지 않는 인자 또는 원인 불명 400 | 같은 요청을 무조건 반복하지 않는다. 지원되는 수정이 없으면 설명·중단한다 |
| Tool이 효과 없음과 수정 가능 필드를 명시 | 해당 필드만 수정한 후보를 검증하고 기존 승인 절차를 다시 적용한다 |
| 이미 완료한 Tool, 효과 불명확, 취소, 예산 소진 | 해당 사실을 무시한 자동 재실행을 허용하지 않는다 |
| 인증·권한 오류 | 모델 설명으로 권한을 바꾸거나 자동 재시도를 확대하지 않는다 |

### 4.1 문맥 축약 시 현재 요청과 지침 보존

축약은 모델에 전달할 입력 사본에 적용한다. 저장된 원본 대화, 사용자 요청, Run/Step 결과, 체크포인트, 승인과 효과 영수증을 축약 결과로 덮어쓰지 않는다. 요약이 의미를 완벽하게 보존한다고 가정하지 않으며, 허용된 자료의 원본과 출처를 다시 확인할 수 있어야 한다.

| 대상 | 보존·변경 계약 |
| --- | --- |
| 현재 사용자 요청 | 작업 지시 본문·대상·제약 조건과 메시지 식별자·역할을 보존한다. 복구 모델이 이를 삭제·대체하거나 새로운 작업으로 바꾸지 못한다 |
| 시스템·Agent 지침 | 현재 호출에 적용하기로 확정한 지침을 복구 과정에서 임의로 삭제·수정하지 않는다. 지침 안의 참고자료를 변환하려면 그 영역과 허용 범위가 별도로 명시되어야 한다 |
| 실행 중 추가 지시 | 적용 중인 지시를 누락하지 않는다. 미소비 지시를 소비한 것으로 만들거나 이미 소비한 지시를 다시 적용하지 않는다 |
| 이전 대화·참고 자료 | 애플리케이션이 선택하고 백엔드가 검증한 범위에서만 요약한다. 원본 출처와 변환 대상을 식별하며, 참고자료를 새 지시나 성공 증거로 승격하지 않는다 |
| 활성 Tool 호출·결과 | 호출 ID·인자·순서·결과의 대응 관계와 실행 사실을 보존한다. 결과 본문 축약 또는 완료 교환 묶음의 요약은 기존 입력 처리·완료 영수증 계약이 허용하는 경우에만 수행한다 |
| 승인·권한·정책 | Tool 정의·허용 범위·인자 제약·승인 binding·operation key·효과 영수증·실행 제한을 입력 축약으로 변경하지 않는다 |

예를 들어 현재 지시가 “A.py의 오류를 수정하되 공개 API는 변경하지 마”이고 긴 조사 로그가 함께 있다면, 허용된 로그를 요약하더라도 작업 대상과 공개 API 변경 금지 지시는 유지해야 한다.

현재 사용자 메시지에 큰 문서가 포함되어 있으면 작업 지시와 참고자료의 경계가 명시된 경우에만 해당 참고자료 부분을 변환할 수 있다. 명시적인 경계 없이 모델이나 백엔드가 임의로 지시와 자료를 나누지 않는다. 변환 가능한 자료가 없거나 보존 대상만으로도 예산을 초과하면 제한 사유를 반환하며, 현재 요청을 비우거나 시스템 프롬프트만 보내는 fallback을 만들지 않는다.

후보 적용 후 현재 요청·지침 보존, 메시지 역할·순서, Tool 대응 관계와 전체 입력 예산을 다시 검증한다. 입력 예산 처리를 다시 적용하더라도 보호된 현재 요청과 추가 지시가 제거되지 않아야 한다. 원본 출처 ID만 남고 지시 본문은 사라지는 후보도 거부한다.

Loop에서는 기존 CompletionPipeline과 입력 처리 경계가 이러한 검증을 소유한다. 현재 스트리밍 전송 재시도의 수정 가능 인자가 제한되어 있다는 이유로 일반 `RetryDecision.changes`에 `messages`를 추가하여 검증을 우회하지 않는다. 다른 Engine·Component가 축약 복구를 지원할 경우에도 해당 입력을 소유하는 구현체의 공개 계약으로 검증한다.

### 4.2 복구 예산과 관찰

Provider 전송 재시도, 인자 수정 재시도, 문맥 축약 복구, 체크포인트 재개를 각각 구분한다. 같은 호출을 SDK·Provider·Engine·Hub가 겹쳐 재시도하는 구조를 만들지 않는다. 횟수를 새 고정값으로 지정하거나 Loop 정책을 RAG·Vision·Memory 호출에 상속하지 않는다. 기존 정책 소유권과 Run 시작 시 스냅샷을 유지한다.

기존 계약에 따라 명시된 설정을 해석한 뒤에도 해당 재시도 정책이 없으면 ish-llm의 추가 시도를 수행하지 않는다. ish-llm 자체 timeout이 미설정이면 추가 기한을 만들지 않는다. SDK 옵션이 미설정이면 해당 인자를 생략하고 기존 compatibility invariant 외에는 SDK의 native behavior를 따른다. 콜백이 주입되어 있다는 이유만으로 모델·프롬프트·횟수·간격·기한·요약 목표량을 자동 생성하지 않는다. 선택한 요약 방식에 필요한 설정이나 입력이 없다면 명시적으로 요청된 요약은 설정·입력 오류를 반환하며, 요청되지 않은 요약은 실행하지 않는다.

인자 수정이나 축약 후에도 같은 논리 호출에서 이미 사용한 시도 횟수와 적용 중인 상위 기한을 초기화하지 않는다. Provider retry 루프를 새로 여는 방식으로 복구 횟수마다 전체 재시도 예산을 다시 받지 않는다. 전송 시도와 복구 시도의 계수 관계를 문서화하고, 그 조합이 기존 예산을 확대하지 않음을 검증한다. 명시적 체크포인트 재개는 별도의 새 Run 계약을 따르며 이 자동 복구 경로와 혼동하지 않는다.

예산 초기화 금지는 같은 복구 과정에서 기존 제한을 우회하지 말라는 계약이다. Provider 전송 재시도, 문맥 수정, 보조 요약 호출을 하나의 새 중앙 횟수 정책으로 합치거나 서로 다른 호출자의 설정을 상속시키지 않는다. 각 시도·호출은 자신을 소유하는 구현체의 명시적 정책을 따르고, 적용 중인 상위 Run·작업 제한도 함께 지킨다. 별도로 명시된 복구 예산이 있더라도 원래 호출의 남은 예산이나 상위 기한을 늘릴 수 없다.

추가 복구 한도가 필요하면 해당 Engine·Component의 명시적 정책으로 소유시킨다. 중앙 retry 정책, Host 콜백 내부의 숨은 한도, 애플리케이션 선택에 의한 Project 상한 확대를 추가하지 않는다.

모델 분석·요약 사용 여부와 프롬프트, 언어는 애플리케이션의 선택으로 둔다. 콜백이 없으면 추가 모델 호출을 하지 않는다. 실행할 경우 해당 작업의 취소·기한·사용량·Step 관찰 규칙을 적용한다. 분석 실패는 원래 오류를 지우지 않아야 하며, 모델의 제안은 원래 진단이나 실행 허용을 덮어쓰지 못한다.

분석·요약 호출은 별도 Provider 호출로 관찰하고 사용량에 포함한다. 이 호출과 대기 시간도 적용 중인 상위 작업 기한을 넘길 수 없다. 독립 Component Job은 자신의 관찰·사용량 계약을 따르며, Step을 만들기 위해 Run을 새로 생성하지 않는다.

재시도 관찰에는 실제 시도 번호, 상한, 적용된 대기 시간과 대기/실행/종료 상태를 제공한다. UI가 자체 타이머로 새 재시도를 만들지 않게 한다. 프로세스의 monotonic deadline을 재시작 후 유효한 영속 시각으로 저장하지 않는다.

## 5 체크포인트 계약 보강

### 5.1 조회와 실행 가능성

`CheckpointPlan`, `ResumePlan`, `ResumeAbandonment`를 재사용한다. Run 전용 필드를 RAG가 가짜 값으로 채우게 하지 않는다. 공통 의미를 갖는 부분을 공유하고 Engine·Component 전용 내용은 해당 소유자가 제공한다.

조회 결과에서 다음을 구분할 수 있어야 한다.

- 정상 체크포인트, 아직 생성되지 않은 상태, 명시적으로 삭제된 상태, 필요한 자료의 유실, 손상, 설정 불일치, 지원되지 않는 재개 방식
- 현재 실행 중 여부와 재개 포기 여부
- 이어서 실행 가능 여부, 처음부터 새 시도 가능 여부, 각 제한 사유
- 재사용할 결과, 재실행할 작업, 추가 응답·승인이 필요한 작업
- 삭제 범위·용량·보존 대상과 revision

미생성과 유실을 판별할 근거가 없으면 불명확 상태로 반환한다. 파일 없음만으로 처음부터 실행 가능하다고 판단하지 않는다. Run·Step·영수증·재개 계보 등 백엔드가 소유한 사실로 판단해야 한다. Hub가 Engine 내부 체크포인트 키나 파일 배치를 알아야만 판단할 수 있는 구조를 제거한다.

기존 `checkpoint_deletion` 표식은 명시적 삭제의 근거로 사용하고 미생성·유실과 구분한다. 표식과 실제 자료가 모순되면 정상 상태로 추측하지 않는다. 재개 포기와 삭제 표식은 재개나 새 시도 조회 과정에서 자동으로 제거하거나 되돌리지 않는다.

Run 또는 Job의 수명 상태, 체크포인트의 유효성, `OperationProgress`의 phase·처리량은 각각 구분한다. 진행률이 100%이거나 phase가 변경되었다는 이유로 작업 성공이나 재개 가능성을 추론하지 않는다.

조회는 실행하지 않으며 모델 호출, 원문 재수집, 임베딩, 인덱스 재생성을 발생시키지 않는다. 계획 객체를 편집하거나 예전 결과를 재사용해도 권한이나 삭제 대상을 늘릴 수 없어야 한다.

### 5.2 동작의 의미

| 동작 | 계약 |
| --- | --- |
| 이어서 실행 | 재사용 가능한 결과를 보존하고 미완료 부분부터 진행한다 |
| 처음부터 새 시도 | 체크포인트 재개와 별개다. 기존 실행 계약과 영속 근거로 실행 전 중단을 확인할 수 있는 경우와 기존 승인·효과 확인이 필요한 경우를 구분하며, 근거가 부족하면 불명확 사유로 차단한다 |
| 실행 취소 | 현재 실행을 중단하는 제어 동작이다. 파일 삭제나 영구적인 재개 포기와 같지 않다 |
| 재개 포기 | 향후 재개를 영구적으로 포기한다. 이전 외부 효과를 되돌리지 않는다 |
| 체크포인트 또는 Job 삭제 | 소유자가 명시한 자료만 제거한다. 완료 문서·대화·효과 원장을 함께 지우지 않는다 |

현재 Run 재개는 원본을 보존하고 연결된 새 Run을 만드는 계약을 유지한다. RAG 재시도는 같은 Job의 저장된 원문·완료 청크를 재사용한다. UI에서 같은 위치에 표시할지는 애플리케이션 책임이다.

체크포인트나 Step이 없다는 사실만으로 효과가 없었다고 확정하지 않는다. custom Engine을 포함해 해당 구현이 효과 전에 영속 실행 경계를 확정하는 계약을 제공하는지 확인해야 한다. 기존 계약과 기록으로 이를 증명할 수 없다면 안전한 새 시도를 허용하지 않는다. 새 범용 효과 보증이나 숨은 Engine별 예외 목록을 만들지 않는다.

명시적 재실행 승인은 불명확 효과 보호, 완료 영수증, operation key 충돌, 기존 승인 binding을 일괄 해제하는 허가가 아니다. 필요한 확인·재승인·reconciliation은 기존 소유자의 경로로 수행한다. 이 계획은 실패한 작업의 재개·복구 선택을 설명하며 일반 신규 요청 API를 새 전역 승인 체계로 바꾸지 않는다.

RAG의 실패 Job은 유지하고 명시적 재시도·삭제를 제공한다. 취소된 Job은 재개하지 않는다. 옛 직접 등록처럼 Job이 없는 작업의 재개를 새로 만들지 않는다. 프로세스 재시작 시 stale Run이나 RAG Job을 자동 실행하지 않는다.

### 5.3 동시성 및 정리

계획은 조회 시점의 정보다. 실행 시 소유자가 잠금 또는 lease와 최신 revision을 검증하고, 상태 변경은 구조화된 충돌·보호 사유로 반환한다. 현재 예외 문자열에 포함된 `checkpoint_conflict` 같은 텍스트를 UI가 파싱하지 않아도 되어야 한다.

현재 삭제 API의 `expected_revision`을 유지한다. 재개·처음부터 실행 선택에도 조회 후 변경을 탐지할 수 있는 검증 경계를 명시한다. 공개 계획의 원본 객체나 소유권 참조를 신뢰 토큰처럼 사용하지 않는다.

재개 포기 후 삭제가 별도 연산이면, 포기는 성공했지만 삭제는 실패한 상태도 정확하게 조회할 수 있어야 한다. 이를 완료로 표시하거나 재개 가능한 상태로 되돌리지 않는다. 단일 API가 필요하더라도 기존 소유자 내부에서 처리한다.

실행 중인 worker, 재개 참조, 완료된 Tool 영수증을 보호한다. RAG 정리는 활성 corpus·완료 문서·공유 벡터 캐시를 보존한다. Hub나 공통 계약 모듈이 컴포넌트 내부 디렉토리를 직접 삭제하지 않는다.

### 5.4 조회 비용

한 계획 조회 안에서는 기존 Run 목록·승인 자료·체크포인트 읽기 결과를 재사용한다. 공통 계약 추가 때문에 같은 파일을 계층마다 다시 읽거나 해시하지 않는다. 다음 실행·삭제 적용 시에는 잠금 안에서 최신 원본을 다시 검증하고, 전역 캐시로 승인·CAS 검증을 생략하지 않는다.

진행률·일반 상태 조회가 전체 체크포인트 해시나 재개 계보 검사를 매번 실행하게 연결하지 않는다. 상세 계획은 명시적 조회로 제공하고, 애플리케이션이 조회 시점을 선택한다. 문서에 상세 계획의 검사 범위와 비용을 설명하며 숨은 polling 주기나 캐시 용량 기본값을 추가하지 않는다.

## 6 구현 순서

1. 최신 백엔드의 공개 API와 설정·저장 계약을 조사하고 중복·부족한 지점을 정리한다.
2. 공통 오류 표현과 순수 분류를 정한다. 기존 Provider·Tool 코드와 우선순위가 어긋나지 않도록 테스트한다.
3. Provider·Tool·Component의 오류 경계와 공개 조회에 연결한다. 원래 코드, 예외 체인, Step 진단을 보존한다.
4. 복구 후보·콜백·입력 보존·최종 검증을 정리한다. 기존 재시도 실행 주체와 소비된 예산을 유지한다.
5. Run·RAG의 체크포인트 및 재개 계획을 보강하고 미생성·명시적 삭제·유실·손상·불일치를 구분한다.
6. 재개 포기·삭제·충돌·부분 완료의 공개 결과와 검증을 정리한다.
7. 공개 import, 문서, 예제를 갱신하고 Hub 이관 대응표를 제공한다.
8. 통합·전체 테스트를 실행하고 결과 및 남은 제한을 보고한다.

이번 백엔드 범위에서는 현재 공개 API의 의미를 유지하는 추가형 확장을 우선한다. 기존 호출자가 사용하는 필수 인자·반환 형식을 깨뜨려야 한다면 변경안과 호출자 대응을 먼저 명시하고, Hub 연결 작업이 함께 승인된 범위에서 진행한다. Hub 수정을 제외한 채 기존 소비자를 깨뜨리는 변경을 완료로 처리하지 않는다. 구버전 API 별칭, 옛 Task 기록 변환, 옛 로그 파싱, 저장 형식 자동 마이그레이션을 추가하지 않는다. 병행 작업자의 변경을 되돌리지 않는다.

실제 사내 모델 접속 없이 결정적인 가짜 Provider·Tool과 실제 저장소를 사용해 검증한다. 외부 연결 검증은 별도 결과로 구분한다.

저장소의 `AGENTS.md`를 우선한다. Python은 Linux 3.12.14를 사용하고, 시간에 민감한 테스트는 소스와 환경 모두 WSL Linux 파일시스템에 둔다. 기존 검증 도구로 소스 해시를 기록한다.

```bash
.venv-linux312/bin/python tests/llm/run_linux.py --full
```

직접 discovery를 실행한다면 `-s tests/llm -t .`를 사용한다. Hub가 같은 체크아웃에 있다면 공개 API 소비 회귀도 실행한다. 별도 작업 공간이라면 백엔드 테스트에서 동일 소비 계약을 검증하고 Hub 연결 테스트가 별도임을 명시한다. 테스트 수를 고정된 과거 수치에 맞추지 않는다.

## 8 산출물과 완료 기준

다음 산출물을 제공한다.

- 구현 코드와 공개 계약·정책·통합 테스트
- `docs/llm/data-contracts.md` 및 관련 API 문서의 현재 내용 갱신
- 책임 경계가 달라지면 `docs/llm/architecture.md` 갱신
- Hub 작업자가 사용할 공개 import, 메서드, 인자, 반환값, 오류 코드의 정확한 목록
- 기존 Hub 로직을 어떤 API로 대체할지 정리한 대응표와 실행 가능한 최소 예제
- 실제 테스트 명령·소스 스냅샷·결과·미해결 제한

Hub 대응표에는 최소한 아래 항목을 포함한다.

| 현재 Hub 책임 | 백엔드 제공 후 Hub가 할 일 |
| --- | --- |
| `ErrorInfo`와 Provider·Tool 분류 | 공개 오류 계약 수신, Hub 자체 오류만 현지 변환 |
| `RecoveryFacts`의 안전성 판단 | 백엔드 허용 후보 조회·선택, 실행 검증은 백엔드 호출 |
| `_unstarted_without_checkpoint` | 공개 재개·새 시도 계획 사용 |
| RAG 상태값 기반 `retryable` 계산 | RAG 공개 재개 가능성과 제한 사유 사용 |
| 체크포인트 예외 문자열 해석 | 구조화된 진단·충돌·보호 결과 표시 |
| 오류 알림·언어팩·진행 위젯 | 기존 Hub UI에서 유지 |

완료 시 애플리케이션이 로그나 내부 파일을 해석하지 않고도 오류 원인, 가능한 복구, 재개·삭제 제한을 표시할 수 있어야 한다. 실행 안전성 검증은 애플리케이션의 선택이나 모델 제안으로 우회되지 않아야 한다. 공통화하면서 기존 Run·Step·대화·RAG 데이터 소유권과 영속성 보장을 유지한다.

축약 복구는 현재 요청·적용 지침·추가 지시·Tool 실행 사실을 보존하고, 소비한 시도 예산과 상위 기한을 다시 시작시키지 않아야 한다. 판단할 근거가 없으면 불명확 상태와 차단 사유를 제공하며 자동 실행으로 추측을 보완하지 않는다.

미설정 값을 자동 생성하지 않고, 복구 종류별 설정 소유권과 적용 중인 상위 제한을 유지해야 한다. Provider 진단 설정은 Provider 경계에만 적용하며, 공통 오류 형식을 추가했다는 이유로 다른 경계의 수집 정책을 바꾸지 않는다.

이 작업은 오류·복구 판단과 체크포인트 공개 계약을 정리한다. 정상 스트리밍 응답의 사실성·지시 준수 여부를 자동 판정하거나, 모델이 “사용자 요청을 받지 못했다”고 생성한 문장만으로 실제 전송 누락을 확정하는 기능은 포함하지 않는다. 실제 입력 전달 여부의 확인은 별도의 요청 관찰·서버 검증으로 구분한다.

공개 계약의 설계와 구현에는 `llm/` 변경이 포함된다. 이 지침서를 받은 백엔드 작업자는 해당 범위에서 구현하고, Hub 변경은 별도 작업으로 남긴다. 커밋·원격 업로드·다른 작업에 메시지 전송은 별도 요청이 있을 때만 수행한다.
