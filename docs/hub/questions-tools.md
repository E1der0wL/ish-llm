# 입력창 질문과 내장 도구

Hub 기본 백엔드는 llm의 `BuiltinTools`를 `builtin_tools` Component로 등록합니다.
내장 파일·셸·프로세스·Git·진단 도구와 Hub의 `ask_user`를 처음에는 활성화합니다.
이미 저장된 `config.parameters.components.builtin_tools.config.enabled`는 빈 배열을 포함하여 유지합니다.
기존 Hub 프로젝트에 이 컴포넌트가 없으면 열 때 등록하며, 다른 컴포넌트의 설정은 보존합니다.
Python 패키지 `tools`와는 별도 저장소입니다. 가져온 Python 패키지를 자동 활성화하지 않습니다.

`/tools config`에서 내장 도구를 선택하고 Space로 활성/비활성을 바꿉니다.

중복 별칭 `/tool`은 제공하지 않습니다. 빈 대화 입력창에서 ↑/↓를 누르면
현재 세션에 보낸 사용자 요청을 이전/다음 순서로 불러옵니다. 최신 요청 다음은
빈 입력창으로 돌아갑니다. 불러온 내용을 수정하면 히스토리 탐색이 끝나고,
방향키는 일반 편집에 사용됩니다. 자동완성 목록과 질문 답변 중에는 히스토리를 탐색하지 않습니다.
출력창 스크롤은 Alt+이동키를 사용합니다. 마우스 휠 전달 계층과 출력창 휠 처리는
제거했으며, Hub 설치 시 ish의 마우스 모드를 변경하지 않습니다.

Hub의 `BackendServices.context_builder`는 실패한 사용자 요청·어시스턴트 응답 쌍을
다음 일반 Run의 모델 문맥에서 제외합니다. 저장 기록과 화면에는 그대로 남고,
최근 대화/문자 예산 정책은 실패한 쌍을 제외한 뒤 적용됩니다. 중단·일시 정지 기록은
기존 정책을 따르며, 명시적 Run 재개는 llm의 체크포인트 복원 방식을 유지합니다.

내장 도구의 검증된 런타임 목록은 프로젝트를 열 때 준비하고 재사용합니다.
활성화 항목·도구 정의·계약 변경 시 다시 구성하며, 각 호출에는 독립된 복사본을
제공합니다. 외부에서 가져온 Tool 패키지는 기존 llm 로더로 매번 확인합니다.
목록의 `[x]`가 활성입니다. 내장 도구는 삭제하거나 폴더를 열지 않습니다.
Python 패키지는 기존처럼 경로 입력 → Enter로 복사, 목록에서 Enter로 폴더 열기,
d로 확인 후 삭제합니다. 설정 변경은 ComponentData의 버전 검사를 거칩니다.
이미 시작된 Run은 시작 시 설정을 사용하므로, 토글 결과는 다음 Run부터 적용됩니다.

ish에 설치하면 요청을 보낼 때 캡처한 현재 디렉토리가 파일 작업 루트입니다.
독립 실행에서는 `HubConfig.file_root` 또는 각 프로젝트의 루트를 사용합니다.
셸은 `/bin/sh -c`를 사용합니다. 외부 웹·브라우저 도구는 실제 어댑터 없이 등록하지 않습니다.
내장 파일 변경·셸 도구의 승인 계약을 유지합니다. 도구 활성화는 실행 승인과 별개입니다.

테스트 Tool은 `.hub/test-workspaces/<project_id>`에 빈 공간 또는 선택 파일 사본을 만들고
Bubblewrap으로 명령을 실행합니다. `test_workspace_create/list/execute/delete`를 선택하며
기존 파일 Tool의 `workspace_id`로 산출물을 읽고 수정합니다. `execute`는 stdout/stderr와
종료 코드를 반환합니다. 네트워크 차단, 읽기 전용 Python runtime은 Hub가 명시한 preset입니다.
승인·중단·재개 UI는 그대로이고, 종료 후 파일은 명시적 삭제까지 유지됩니다.
기존 enabled 목록은 자동 변경하지 않습니다. [세부 계약](../llm/test-workspaces.md)을 참고하세요.
Bubblewrap이 없으면 새 Project의 최초 목록에서 `test_workspace_execute`를 제외합니다.
설치 후 `/tools config`에서 활성화합니다. 명시적으로 선택한 Tool이 사용할 수 없으면
기존 Backend 계약대로 Run 사전 검증에서 오류를 반환하며 호스트 실행으로 바꾸지 않습니다.

## 질문과 답변

모델이 `ask_user(question, description?, choices?)`를 호출하면 도구가 답변을 기다립니다.
입력창 위에 질문과 선택지가 표시되고, 기존 입력창에서 자유롭게 답하거나 선택지 번호를
입력한 뒤 Enter로 전송합니다. 응답용 포커스 영역이나 대화상자를 추가하지 않습니다.
질문 전 일반 대화 초안과 질문별 답변 초안은 분리하여 보관합니다.
폼은 `제목 → 본문 → 선택지 → 안내 → 기존 입력창` 순서입니다. 제목은 ` 승인 요청` 또는
` 질문`이며, 일반 아이콘 모드에서는 `?`를 사용합니다. 질문은 Markdown 본문과 번호가 붙은
RadioList 선택지로 표시합니다. 선택지가 없으면 선택지 대신 빈 줄 하나만 둡니다.
선택지 테두리는 최소 50칸에서 내용의 터미널 칸 수에 맞춰 늘어나며, 화면이 좁으면 화면에 맞춰
줄바꿈합니다. 선택지에는 별도 배경색을 적용하지 않습니다. 승인 카드는 도구, 경로·명령,
위험도·근거를 구분하여 표시하고 파일 본문 같은 큰 인자를 자동 펼치지 않습니다.
번호를 입력하면 해당 라디오 항목의 체크와 강조가 함께 바뀌며 Enter로 전송합니다.
목록 자체는 포커스를 받지 않고, 상세 내용은 실제 필요한 높이만 사용합니다. 긴 질문도 Ctrl+O로 전체를
확인할 수 있고, 상세 창을 닫으면 기존 답변 입력창으로 돌아갑니다.
Ctrl+C는 대화 입력창에서 아무 동작도 하지 않으며, Ctrl+X는 기존처럼 실행을 중단합니다.
Ctrl+X 또는 `/stop` 요청 시 출력의 어시스턴트 헤더에 즉시 `중단 중`을 표시합니다.
이 표시는 백엔드 저장을 기다리지 않는 UI 피드백이며, 본문·생각 과정·실행 기록을 바꾸지 않습니다.
중단 결과를 관찰하면 실제 상태로 바꾸고, 실패 또는 중단 대상이 없으면 표시를 해제합니다.
처리 중 반복 입력은 합치며, 세션 전환·새 Run 시작 시 다른 실행으로 표시가 이어지지 않습니다.

`backend/questions.py`가 Run/Session에 연결된 Future를 소유하고,
`widget/question.py`가 표시와 입력 전환을 맡습니다. 답변은 도구 결과로 엔진에 반환되어
**같은 Run**이 계속됩니다. 응답 ID·세션·Run·요청 지문을 검증하며 중복/오래된 답변은 거부합니다.
도구 호출과 결과의 영속 저장은 llm의 기존 실행 경로가 담당합니다.

질문 대기는 현재 프로세스의 실행 상태이며 종료·중단·실행 제한 시간 만료 시 해제됩니다.
프로세스 재시작 후 질문 Future를 복원하거나 중단된 작업을 자동 재실행하지 않습니다.
Run/Tool 시간 제한도 그대로 적용합니다. 일반 Markdown 문장으로 끝난 질문은 자동 변환하지 않습니다.
새 프로젝트의 기본 지침과 `ask_user` 도구 설명에서 질문 도구 사용을 안내하며,
기존 프로젝트의 사용자 시스템 프롬프트를 덮어쓰지 않습니다.

llm이 일시정지한 승인/입력 요청도 같은 입력창에 표시합니다. 선택지 번호 뒤에 필요한 값을
입력할 수 있습니다(문자열은 그대로, 그 외 타입은 JSON). 추천 항목을 자동 선택하지 않습니다.
승인 제목·도구·위험도·경로/명령 요약은 입력창 안의 답변 칸 위에 표시하며, 대화 출력에는
추가하지 않습니다. 긴 내용은 제한된 높이로 표시하고, 전체 인자와 파일 내용은 Ctrl+O로
검토할 수 있습니다. 선택지와 답변 칸은 상세 내용과 분리하여 계속 표시합니다.

승인이 필요한 내장 도구는 선택적 `_hub_risk` 인자(`level`, `reason`)를 제공합니다.
Hub의 Completion 지침은 호출할 경로·명령·코드의 삭제/덮어쓰기·외부 전송·가역성 등을
검토해 사용자 언어로 짧게 설명하도록 요청합니다. 별도 모델 호출은 추가하지 않습니다.
기본 Host 분류기는 모델 평가를 승인 요청의 실제 `risk`에 반영합니다.
`hub-model-risk-v1` 척도에서 low=20, medium=60, high=100이며 unknown/누락/잘못된
평가는 점수 없이 unknown입니다. 입력창에는 위험도와 모델 평가 근거를 표시합니다.
모델 평가는 객관적 안전성 보증이 아니며 사용자의 승인을 대신하지 않습니다.
기존 `hub-risk-v1` 자동 승인 프리셋과 척도가 달라 해당 프리셋으로 자동 승인되지 않습니다.
Hub는 모델 척도의 자동 승인 규칙을 등록하지 않습니다. 사용자가 Project 승인 정책에
이 척도를 직접 지정하면 백엔드의 일반 임계값 규칙이 적용되므로 수동 승인을 유지하려면
그런 규칙을 추가하지 않아야 합니다.
명시적인 `HubConfig.tool_classifier`는 기본 모델 분류기보다 우선하며 이 경우 모델 평가는
참고로 표시됩니다. 분류기 변경은 실행 계약 revision에도 반영되므로 변경 전 대기 중이던
승인 요청은 새 요청으로 다시 검토해야 합니다. `_hub_risk`는 실행 직전에 도구 인자에서 제거합니다.
승인 원본과 실행 기록에는 평가를 포함한 원래 호출이 남습니다. 모델이 생략하거나 효과를
판단할 근거가 없으면 확정 점수를 만들지 않습니다. 기존 Graph 호출은 이 인자 없이도
유효하며, 가져온 사용자 Tool의 스키마는 변경하지 않습니다.
응답은 `Run.arespond()`로 저장한 후 공개 `session.run.resume()`의 잠금 안에서 검증합니다.
모든 요청에 답했고 불확실한 작업의 재시도가 필요하지 않을 때에만 명시적 resume를 수행합니다.
이 경우에는 llm 계약에 따라 원본과 연결된 새 Run이 생깁니다.
새 Run은 완료된 Tool의 체크포인트 결과를 재사용하며 해당 핸들러를 다시 호출하지 않습니다.
백엔드의 `reused` Step은 조회용 기록이므로 Hub의 현재 작업과 생각 영역의 도구 목록에는
새 실행으로 추가하지 않습니다. 승인 전 `cancelled`/`waiting_approval` Step은 `승인 대기`로
표시하고, 동일한 호출의 재개 후 실행·완료는 한 항목에서 갱신합니다. 다른 호출 ID와
Graph 노드·반복 회차는 별개로 유지합니다. 새 작업이 시작되기 전에는 `이어서 실행`을 표시합니다.
생각 영역에는 모델이 공개한 생각 요약과 실제 Tool 호출을 발생 순서대로 표시합니다.
이전 도구를 최근 다섯 개로 줄이지 않으며, 완료 전까지 응답 본문 위에 유지합니다.
입력창 위의 별도 상태 줄은 사용하지 않습니다. 재시도 횟수·남은 시간은 출력의 어시스턴트
헤더에 표시합니다. 답변을 보내면 질문 카드를 즉시 닫고 일반 입력 초안을 복구합니다.
출력의 해당 Tool과 어시스턴트 헤더는 `답변 전달 중`으로 바꾸며, 영속 승인 저장 확인 직후
`승인 완료` 또는 `거절됨`으로 바꿉니다. 실제 Tool 실행·완료 상태와 구분합니다.
재개 준비가 끝날 때까지 새 초안은 작성할 수 있지만 Enter로 중복 전송하지 않습니다.
승인 저장과 재개 완료는 별도로 통지하므로 재개 준비 I/O가 승인 확인을 늦추지 않습니다.
저장 실패 시 질문과 답변을 복구하고 새 일반 초안도 보존합니다. 저장 후 재개만 실패했다면
같은 승인을 다시 요청하지 않습니다. 표시 상태는 영속 실행 기록을 변경하지 않습니다.
화면에서는 `resume` 연결을 따라 원래 사용자 요청과 응답에 이어 표시합니다. 재개용 사용자
요청 사본은 숨기고 승인 전에 나온 응답 본문은 유지합니다. 저장 기록과 모델 입력은 바꾸지
않습니다. 거절 응답은 저장만 하고 도구 실행을 재개하지 않습니다.

일반 요청과 승인·질문 답변은 Enter 처리 시 입력창에서 즉시 소비합니다. 저장 성공 표시는
백엔드의 영속 접수 확인 이후에만 표시합니다. 접수 실패나 전송 방식 선택 취소 시 입력을
복구하며, 그동안 새 입력을 작성했다면 덮어쓰지 않고 미전송 입력을 히스토리에 보관합니다.
이때 입력창을 비운 뒤 ↑로 복구할 수 있습니다. 이미 보낸 답변은 늦게 도착한 질문 화면으로
다시 활성화하지 않습니다.

검증: Linux Python 3.12.14에서 집중 26개·Hub 전체 208개 통과
(`tests/llm/reports/ish-provider-0r70drpl/{focused,hub}.txt`). llm 전체 1,374개도
통과했습니다 (`tests/llm/reports/ish-provider-8zvhc9c_/suite.txt`). 실제 PTK 승인 입력,
승인 전후 응답 유지, 체크포인트의 Tool 결과를 포함한 후속 모델 호출, 거절 시 실행 없음,
중복 Enter, 오래된 질문 화면, 접수 실패와 새 초안 보호를 검증했습니다. 실제 모델 API를
호출하거나 `llm/` 구현을 수정하지 않았습니다.

Hub는 질문을 기다리는 세션을 `답변 대기`, 승인 요청이 있는 세션을 `승인 대기`로
표시합니다. 세션 목록, 현재 작업 안내, 알림 팝업이 이 표시 상태를 공유합니다.
현재 세션·다른 세션·셸로 최소화한 상태 모두 질문 도착 시 세션 이름을 제목으로
경고 알림을 표시합니다. 알림은 포커스를 가져가지 않으며 일반 설정의 알림 종류와
표시 시간을 따릅니다. 질문 ID로 중복을 방지하고 답변·중단 후 대기 알림을 정리합니다.
이 상태는 Hub의 관찰용 상태입니다. `ask_user`의 실제 Run은 running을 유지하고,
승인 체크포인트의 실제 Run은 paused를 유지합니다.

## 로그 창과 설정 이동

`Ctrl+L`은 공개 `project.aactivity()`의 최근 활동 300건과 프로바이더 진단을 함께
표시합니다. 활동의 저장 순서는 유지하며, 세션·Run ID가 일치하는 프로바이더 기록을
`run.failed` 바로 아래에 연결합니다. Run 실패가 조회 범위에 없으면 `step.failed`에
Run 단위 진단으로 연결합니다. 진단에는 Step ID가 없으므로 특정 Step의 예외로 단정하지 않습니다.
연결되지 않은 프로바이더 기록은 뒤에 시간순으로 표시합니다.
실제 백엔드의 workspace를 기준으로 `<workspace>/projects/logs/providers-*.log`와
`<workspace>/logs/providers-*.log`를 함께 조회합니다. RunManager는 ProjectRepository의
루트인 `workspace/projects`에 로그 문맥을 연결하므로 첫 번째 경로가 일반 Run의 저장 위치입니다.
초기화·직접 호출은 두 번째 경로를 사용할 수 있습니다. 두 경로를 합쳐 최근 파일 최대 8개의
끝 128KiB씩에서 최대 300건을 읽습니다. 현재 프로젝트 ID가 있는 기록만 선택하고, 소유 프로젝트 정보가
없는 SDK 공통 로그는 `워크스페이스 공통`으로 표시합니다. 다른 프로젝트 기록은 제외합니다.
오류 코드·실패 단계·경과 시간 등의 진단 JSON과 로그 파일 경로를 표시합니다.
예외 체인은 HTTP 상태와 `파일:행 · 함수()` 형식의 읽기 쉬운 traceback으로 표시하며,
파일 읽기와 긴 로그 문자열 구성은 UI 스레드 밖에서 수행합니다. SDK가 기록하지 않은
원문 요청·응답이나 예외 메시지를 복원하지 않습니다. 새 로그는 창을 다시 열면 반영됩니다.

`tests/hub/test_provider_activity.py`는 실제 Loop의 스트림을 503으로 실패시켜,
RunManager가 생성한 로그를 발견하고 해당 실패에 traceback을 연결하는 경로를 검증합니다.

설정 메인 영역에서 편집 중이 아닐 때 `←`를 누르면 좌측 패널로 돌아갑니다.
Enter로 편집하는 동안에는 `←`가 텍스트 커서를 이동하며, 편집 종료 후 패널 이동으로
돌아갑니다. 하단 단축키 안내에도 이 구분을 반영합니다.

## UI 저장 지연 완화

요청을 전송하면 백엔드 접수가 끝나기 전부터 출력 영역 아래에 `어시스턴트 · 준비 중…`을
표시합니다. 이 표시는 로컬 진행 안내이며 저장된 Assistant 메시지가 아닙니다.
접수 실패 시 안내를 해제하고 초안을 보존하며, 접수 후에는 실제 Assistant가 관측되면 해제합니다.

출력 관측은 모양의 `output_refresh_interval`(기본 0.1초)로 반복합니다. 이전의 1초 이벤트
대기 시간을 없애고, 조회에 걸린 시간도 주기에서 차감합니다. 조회 자체가 주기보다 느리면
중복 조회를 쌓지 않습니다. 바뀌지 않은 대화의 Rich/Markdown 변환 결과는 재사용하고,
너비·테마·렌더러 변경 시 재생성합니다. 저장소나 모델 서버의 응답 시간까지 보장하는 값은 아닙니다.

`Ctrl+G` 요청 목록에서 예약 요청을 선택하고 **c** 또는 **예약 취소** 버튼으로 확인 후
취소합니다. 취소는 `RequestHandle.cancel()`로 저장됩니다. 실행이 이미 시작된 요청은
취소 대신 상태 변경을 알리며 실행 중인 Run을 임의로 중단하지 않습니다.

`Conversation turn is required by an unfinished resumable Run`은 실행 중 상태 오류가 아니라
실패·중단·일시 정지된 Run의 체크포인트 참조 보호입니다. Hub는 삭제 전에
`session.adelete_turn_plan()`으로 영향받는 Run들을 조회합니다. 보호된 턴은 작업 ID·Engine·상태를
보여주고 **재개 포기 후 삭제**를 확인받습니다. 취소하면 변경하지 않습니다.
확인한 Run ID 목록과 revision을 `adelete_turn()`에 전달하며, 확인 이후 참조/승인/체크포인트가
변하면 다시 조회·확인해야 합니다. 실행 중/예약 작업은 먼저 정리해야 합니다.
Run의 원래 실패·일시 정지 상태와 체크포인트·실행 증거는 유지하지만 이후 재개는 거부됩니다.
대화는 일반 조회와 향후 문맥에서 제외되는 논리 삭제이며, 이미 수행한 외부 효과를 되돌리지 않습니다.

읽기 위치 저장의 JSON 직렬화·fsync·원자 교체를 단일 백그라운드 작업자로 옮겼습니다.
프로젝트별 연속 갱신은 최신 상태로 합치고, 저장 중 프로젝트를 전환해도 최신 위치를 읽으며,
종료 시 남은 쓰기를 완료합니다. 실패는 UI 알림으로 전달합니다.

다른 세션의 상태 조회는 실행 수명 이벤트로 캐시를 무효화하고 최대 2초마다 재조정합니다.
현재 세션은 매 표시 주기마다 확인합니다. 놓친 이벤트가 감지되면 캐시를 비웁니다.
사용자 요청의 QUEUED 영속 저장, Run/Step 저장, 제공자 호출의 보장은 바꾸지 않습니다.
이 변경은 Hub의 UI 정지와 반복 조회 부담을 줄이며, 모델 서버 응답 지연 자체를 제거하지 않습니다.

검증은 `tests/hub/test_question_tools.py`와 `test_snapshot_projection.py`에 있습니다.
