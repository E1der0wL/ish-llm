# 대용량 명령 결과와 외부 파일 읽기

Hub는 llm의 파일 기반 출력 저장과 범위 조회를 사용한다. 명령 결과 전체를 모델에 넣은 뒤
압축을 시도하기보다, 먼저 원문을 저장하고 필요한 부분만 모델에 전달한다. 요약 모델을
설정하지 않아도 이 경로를 사용할 수 있다. 설정과 지침은 Hub가, 파일·참조·무결성·실행은
[백엔드의 공개 계약](../llm/large-data-files.md)이 소유한다.

## 새 프로젝트 기본값

`HubDefaults`가 다음 값을 선언하며 `ToolDataSetup`이 프로젝트 생성 시 저장한다.
명시한 사용자 값과 비활성화한 컴포넌트는 유지한다.

| 항목 | 기본값 |
|---|---|
| 원문 목적지 | Data 패키지 `hub_command_outputs` |
| 명령 결과 미리보기 | stdout·stderr 각각 2,000자 |
| `process_output` / `file_read` | 한 번에 각각 8,000자 |
| `file_search` | 20개 일치 결과, 각 줄 미리보기 400자 |
| `file_list` | 200개 항목 |
| 일반 파일 읽기 | OS가 허용하는 절대 경로와 심볼릭 링크 대상 |

페이지 값은 `config.policies.tools.argument_constraints`의 **bounded** 정책이다. 표의 값은
최대값이며 모델은 1부터 최대값까지 정수로 요청할 수 있다. 페이지 인자는 공개 스키마의
필수값이다. 0·음수·소수·잘못된 타입은 거부한다. 사용자는 이 정책을 설정에서 변경할 수 있다.
`file_read`와 `process_output`이 `max_chars` 상한보다 큰 정수를 요청하면 Hub는 실행 전에
현재 Run의 bounded 상한으로 페이지 크기를 줄이고, 원본 스키마와 정책을 다시 검증한다.
원문을 삭제하거나 명령을 다시 실행하지 않으며 반환된 다음 위치에서 계속 읽을 수 있다.
경로·offset·파일 해시·읽기 모드는 변경하지 않고, 다른 인자 오류와 fixed 정책은 그대로 거부한다.
`file_read`는 문자 페이지를 사용하므로 기본 정책과
`start_line/max_lines/tail_lines`를 섞지 않는다. 검색 결과의 줄 미리보기는 전체 줄이 아니다.
검색의 별도 `context_lines`를 크게 지정하면 결과량도 늘어나므로 필요한 문맥만 요청한다.

`limit: ... const` 또는 `max_chars: ... const` 오류는 이 **고정값과 다른 인자**를
모델이 보냈다는 뜻이다. 이전 Hub 기본값은 이 페이지 값을 `fixed`로 저장했지만, 새 프로젝트는
최대값 이하를 허용한다. 기존 프로젝트의 명시적 정책을 자동 변환하지 않으므로 아래 JSON의
범위 정책을 설정에 반영해야 한다. 사용자가 별도로 지정한 고정값은 계속 지원하며 모델용 필드에
`const`·단일 `enum`·설명으로 명시한다. 선택값과 범위 제약도 필드에 직접 표시하고,
원본 스키마와 백엔드의 `allOf` 제약은 그대로 유지한다.
`hub_help(tool_query="file_read")` 같은 도구 탐색도 현재 Run의 실제 제약을 반영한
동일한 스키마를 반환한다. Project 기본값을 다시 읽어 Agent의 더 좁은 제약을 덮어쓰지 않는다.

모델에 노출하는 스키마에도 상한을 유지한다. 위 두 읽기 도구의 초과 페이지 요청만
축소하며, 실제 실행·체크포인트에는 축소한 인자가 기록된다. 실행 전 검증은 Tool 실패의
재시도와 다르며 완료된 도구나 Run을 재실행하지 않는다. 고정 정책에서 더 작은 페이지도 허용하고 싶다면 사용자가
해당 정책을 `bounded`로 변경해야 한다. 예를 들어 `file_list.limit`의
`{"mode":"bounded","minimum":1,"maximum":200}`은 1~200을 허용한다.

명령 결과에는 미리보기, 문자 수, `process_id`, `output_sources`가 들어간다.
`process_output`의 stdout/stderr 커서로 저장 원문을 나눠 읽고, 파일은 `file_read`의
`next_offset`과 `sha256`을 다음 호출의 `expected_sha256`으로 전달해 변경을 확인한다.
저장된 출력은 같은 프로젝트에서 백엔드를 다시 시작해도 읽을 수 있다. 명령은 재실행하지 않는다.

수십만 줄 전체를 분석할 때는 승인된 명령에서 원문을 작업 파일에도 저장하고, 스트리밍
스크립트로 필터·집계·추출한 결과를 확인한다. 의미 분석이 필요하면 범위별 요약을 파일에
보관하고 단계적으로 합친다. 모든 페이지를 다시 모델 입력에 연결하거나 미리보기만 보고
전체 자료를 검토했다고 보고하지 않도록 기본 지침과 코딩·진단 스킬에 명시했다.

## 기존 프로젝트에서 켜기

기존 프로젝트를 열 때 설정·Agent·Skill을 자동으로 덮어쓰지 않는다. Data 컴포넌트가
선택된 상태에서 설정 화면의 **builtin_tools** 항목에 아래 두 값을 함께 저장한다.
기존 `enabled`와 다른 설정은 유지한다.

- 설정 탭 `output`: `{"component":"data","identifier":"hub_command_outputs"}`
- 정책 탭 `output_preview_chars`: `2000`

이 기본 목적지 패키지는 **명시적인 설정 저장 시** 공개 Data API로 준비된다. 다른 목적지를
지정하면 해당 패키지는 먼저 생성해야 한다. 프로젝트 정책의 `tools.argument_constraints`에
원하는 페이지 제약을 설정한다. 새 프로젝트와 같은 예시는 다음과 같다.

```json
{
  "process_output": {"max_chars": {"mode": "bounded", "minimum": 1, "maximum": 8000}},
  "file_read": {"max_chars": {"mode": "bounded", "minimum": 1, "maximum": 8000}},
  "file_search": {
    "max_chars": {"mode": "bounded", "minimum": 1, "maximum": 400},
    "limit": {"mode": "bounded", "minimum": 1, "maximum": 20}
  },
  "file_list": {"limit": {"mode": "bounded", "minimum": 1, "maximum": 200}}
}
```

이는 `argument_constraints` **값**이며 프로젝트 설정 전체를 대체하는 JSON이 아니다.
기존 제약이 있으면 필요한 항목만 합친다. Agent의 선택 도구에 `process_output`과 필요한
파일 도구가 포함되어 있어야 한다. 기존 Agent·Skill의 사용자 지침도 보존되므로 필요한
대용량 처리 지침은 직접 반영한다.

읽기 정책 미지정 시 Hub Toolkit은 외부 읽기를 허용한다. 명시한 `read_access`가 있으면
그 값이 우선한다. 외부/링크 읽기를 켜려면 builtin_tools 정책의 `read_access`를
`{"roots":["/"],"follow_symlinks":true}`로 설정하거나, roots를 필요한 디렉터리로 제한한다.
OS 권한과 정규 파일 검증은 유지한다. `write_access`·`cwd_access`는 별도 권한이며
기본적으로 작업 디렉터리 내부에 제한된다. 일반 셸 명령 자체를 격리하는 정책은 아니다.
테스트 공간의 파일·원본 복사·실행에는 그 공간의 독립된 제한이 적용된다.

## 소유권과 한계

- `HubBuiltinTools.resolve_runtime`이 lifecycle-bound ComponentData를 연결한다. Hub는
  백엔드 내부 디렉터리를 추측하거나 원문 저장·출력 레코드를 직접 쓰지 않는다.
- 승인과 실행 revision에 목적지·크기·경로 권한·ish 환경이 포함된다. 저장 실패를
  명령 재실행으로 처리하거나 기존 승인·체크포인트 제한을 우회하지 않는다.
- 원문에는 자동 삭제 기한을 두지 않았다. 백엔드의 참조 보호와 공개 삭제 API를 따른다.
- 저장·해시 확인에는 디스크 I/O가 필요하다. 모든 조회가 페이지 크기만큼의 I/O로 끝난다는
  보장은 없으며, 단일 출력이 무한히 커도 처리할 수 있다는 의미는 아니다.
- 외부 MCP·SDK 응답은 각 어댑터의 별도 streaming/paging이 필요하다. 사용자 입력, 많은
  도구 정의, 누적 대화 등 다른 원인으로 생기는 컨텍스트 초과까지 모두 방지하지는 않는다.

검증 코드는 `tests/hub/test_large_data_tools.py`에 있다. 실제 30만 줄 명령 실행, 작은 모델
입력, 승인 전 효과 없음·승인 후 1회 실행, 재시작 후 범위 조회, 외부/링크 읽기와 쓰기 권한
분리, 사용자 설정 보존을 확인한다. 모델 응답은 고정 테스트 데이터이며 외부 API를 호출하지 않는다.

## 문맥 관리 검토: 지침과 코드의 역할

프롬프트를 어겨도 모델 호출 크기를 지킬 책임은 코드에 있다. 분석 순서·집계 방식은 지침으로
안내하지만, 원문 저장·도구 결과 크기·전체 입력 예산·원문 보존은 코드로 집행해야 한다.

현재 백엔드에는 이미 다음 순서가 있다.

1. Builtin 출력은 지정된 Data에 저장되고 제한된 미리보기로 반환된다. ToolExecutor가
   공개 `argument_constraints`를 검증하므로 모델이 페이지 제한을 마음대로 늘릴 수 없다.
2. Loop의 CompletionPipeline이 요청 사본에 Memory 처리를 적용한다. Memory는 설정에 따라
   큰 Tool 결과의 저장 참조/요약, 이전 턴 요약, 현재 작업의 완료된 도구 교환 압축을 수행한다.
   이는 저장된 대화·도구 효과 영수증·승인 기록을 삭제하는 작업이 아니다.
3. 그 뒤 CompletionPolicy가 전체 모델 요청의 토큰 수를 검사한다. 입력·도구 정의와 출력
   여유를 계산하고 오래된 턴을 선택적으로 제외한다. 현재 요청과 도구 호출/결과 묶음까지
   줄여야 하는 상태면 API 호출 전에 거부한다.

이번 연결은 1번을 새 프로젝트의 명시 정책으로 보강했다. 2번의 요약 모델 설정 경로는
기존대로 유지한다. 3번은 Loop의 `policy.completion.max_tokens`, `reserve_tokens`, `counter`를
설정해야 활성화된다. 모델별 한도가 다르므로 204800을 모든 Agent에 고정하지 않는다.
사내 서버는 실제 tokenizer와 채팅 템플릿·도구 형식의 오버헤드까지 맞춰야 하며,
문자 수 제한이나 일반 토큰 추정치를 서버의 정확한 한도와 동일시하지 않는다.

후속 구현에서는 작은 Tool 결과의 누적과 요약 실패·부분 요약에 대한
[모델 입력 검증과 참조 전환](working-context.md)을 추가했다. Memory 이후에도 큰 본문이
남거나 현재 실행의 CompletionPolicy에 맞지 않으면, 저장된 Step 참조와 완료된 교환의
참조 색인으로 줄인 뒤 재검사한다. 승인·질문·steering·미완료 Tool 쌍과 원문은 보존한다.
보조 모델은 자신의 입력·재시도 정책을 계속 사용한다. 별도 대화 저장소나 Provider 재시도
루프를 추가한 것은 아니다.
