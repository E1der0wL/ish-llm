# 변경 신호 기반 갱신과 요청 준비 비용 검토

2026-10-31. 이번 검토는 `request-latency-handoff.md` 이후 작업 트리의
Hub 변경만 대상으로 한다. 이미 존재하던 llm 개선과 Hub의 `ToolRegistry.derive`
전환은 비교 기준에도 포함했다. llm 구현·저장 계약·사용자 작업 공간은 변경하지 않았다.

## 변경한 경로

- `BackendWorker`는 변경 신호가 있을 때 관측한다. 기존 출력 간격은 조회 시작
  사이의 최소 간격이며, 변경이 없는 실행을 10Hz로 조회하는 타이머가 아니다.
  연속 신호는 합치고, 조회 도중 들어온 변경은 다음 조회까지 보존한다.
- 처음 게시한 스냅샷을 다시 읽지 않는다. Checkpoint 저장 통지만으로 대화·Step을
  다시 조립하지 않는다. 실행·질문·승인·출력 이벤트와 공개 재개 계획 조회는 유지한다.
- Provider 재시도 관측이 변경되면 직접 신호를 보낸다. 숨긴 화면의 긴급 알림,
  foreground 작업의 조회 선점, 취소된 저장 작업의 drain 계약도 유지한다.
- 기존 출력 간격과 별개로 2초 안전 재조회가 남는다. Hub 밖의 공개 API 변경이나
  이벤트 손실을 보정하며, 같은 스냅샷은 게시하지 않는다.
- 경과 시간은 실제로 표시되는 다음 초에만 갱신한다. 여러 Agent의 경과 시간도
  관측 시점으로부터 로컬 계산한다. 시계 때문에 대화 이력을 읽지 않는다.
  진행 바는 기존의 활성 작업 타이머·변경 병합을 유지한다.
- 같은 Run의 환경 바인딩·도구 탐색·호출별 선택이 이미 구성한 카탈로그를 공유한다.
  각 detached Tool 정의는 카탈로그에서 한 번만 읽는다. 원래 BindingCache의
  Project·환경·권한 제약·실행 binding 검사를 통과한 같은 registry만 재사용한다.
  다른 registry나 변경된 설정은 다시 구성한다. 승인 결과를 캐시하지 않는다.

입력·포커스·진행 시작/종료의 즉시 반응까지 주사율 제한으로 지연시키지 않는다.
QUEUED 저장, Run/Step 저장, 승인, 완료 검증, fsync를 생략하지 않았다.
“생각 중”을 실제 실행보다 먼저 표시하는 방식으로 준비 시간을 숨기지 않는다.

## 측정 방법과 범위

Linux 파일 시스템의 해시 검증 소스와 Python 3.12.14를 사용했다. reference ish의
실제 Prompt에서 Enter를 보내 Hub worker와 native 저장 경로를 거친다. Provider만
loopback HTTP SSE fixture이며 외부 모델 호출은 없다. 실제 fsync를 그대로 실행한다.
전후 모두 auto-title, 후처리, final_review를 fixture에서만 꺼서 비교했다.
따라서 사내 모델의 추론 시간이나 사용자의 설치된 WSL 환경을 측정한 결과는 아니다.

실행 시점은 입력 접수, native LLM Step 시작, 첫 HTTP 수신, 실제 PTK 본문 표시로
구분한다. 함수 경계 타이머의 중첩 시간은 더하지 않는다. 시간과 함께 실제 공개 API
조회 횟수·카탈로그 구성 횟수·신호 병합·상태 전달을 확인한다.

## 요청 준비 시간

같은 작업 트리의 backend로 순서대로 측정한 첫 HTTP 수신 시간(초)이다.
이전 반복 계측도 원자료에 남겼고, 아래는 최종 제품 코드의 비교 실행이다.

| 요청 | 변경 전 | 변경 후 | 변경 후 반복 |
| --- | ---: | ---: | ---: |
| 첫 인사 | 2.606 | 2.543 | 3.507 |
| 다음 인사 | 2.449 | 2.537 | 2.179 |
| 첫 파일 조회 | 2.805 | 4.008 | 3.043 |
| 다음 파일 조회 | 3.167 | 4.534 | 3.204 |
| 긴 입력 | 3.902 | 4.629 | 4.053 |
| 긴 이력 뒤 인사 | 3.318 | 3.265 | 2.425 |

**3초 이하를 일괄 달성하지 못했다.** 실행 간 편차와 더 느려진 표본도 있으므로
전체 준비 시간이 확실히 단축되었다고 결론 내리지 않는다. 변경 후 입력 소비는
0.029–0.046초, 저장 후 접수 전달은 0.208–0.425초, 실제 LLM Step 시작은
1.954–4.182초였다. 초기 백엔드 연결은 이 표에 포함하지 않는다.

명확하게 줄어든 것은 호출별 선택기 구성이다. `routed_engine` 경계는 변경 전
16–33ms에서 변경 후 2.5–4.7ms였다. Run 문맥 구성은 0.384–1.630초,
최초 환경 도구 구성은 0.133–0.503초로 편차가 컸다. 준비에는 이 밖의 Memory
단계, 실행 기록 저장, provider 준비도 포함된다. 중첩되는 함수 시간을 더해서
전체 지연의 원인으로 단정하지 않는다. 저장·검증을 건너뛰지 않는 현재 범위에서
남은 시간을 단순한 Hub 렌더링 비용으로 없앨 수 있다고 주장하지 않는다.

여기서 첫 요청의 `_create`는 백엔드 SDK 사전 준비가 다시 느려진 것이 아니다.
`prepare_backend()`의 Provider 초기화는 유지된다. 기존 Hub `resolve_environment()`는
`(project.id, hash(cwd/env))` 조합이 없을 때 `BuiltinTools`, 셸 실행 handler와
테스트 작업 공간 도구를 만든다. 최초 요청에 환경별 객체를 만들고 이후 재사용하는
Hub 경로가 남아 있는 것이다. 현재 공개 toolkit에는 다른 root/env로 기존 객체를
재바인딩하는 API가 없으며, handler가 파일 루트와 process 수명을 캡처한다.
다른 환경의 handler나 승인 binding을 공유해 없애지 않았다. 이 초기화는 후속 요청의
지속 지연이나 모델 추론 시간 전체를 설명하지 않는다.

신호 방식은 조용한 실행의 10Hz 조회를 없애지만, 변경이 연속되는 실행에서 모든
조회 횟수를 줄이는 방식은 아니다. 실제 조회 시작 간격을 지키며 상태 변경을
빠르게 반영하므로, 일부 표본의 첫 호출 전 스냅샷은 기존 4회보다 많은 6회였다.
원래 느린 조회 완료 뒤 다시 간격을 기다리던 동작은 제거했다. 이벤트 없는 구간,
신호 폭주, 진행 중 변경, 숨김/복귀와 취소는 시간 표본 외에 결정적 검사로 검증한다.

## 검증

최적화 중에는 집중 검사와 계측만 실행했다. 이전 폴링 기대를 남긴 검사 한 개를
변경 신호·최대 갱신율 계약으로 수정했고, 해당 모듈과 신호 검사는 13개 통과했다.
그 뒤 실행한 전체 Hub 회귀는 **917개 모두 통과**, 실패·오류·skip·누락·중복 0개였다
(Linux Python 3.12.14, 1,685.923초). 소스는
`/home/user/.cache/ish-hub-latency-signal-final-pkpj_3u7`, 결과는
`tests/hub/reports/signal-refresh-20261031/full/hub.json`이다. private X11 검사도
포함했다. llm 전체 회귀를 다시 실행하지는 않았다.

S1–S7 아키텍처 검사는 통과했다. 문서 링크 검사는 실제 작업 트리에서 오류 0개다.
소스 스냅샷에서는 배포에서 제외되는 기존 llm 보고서 링크 한 개가 없었으므로,
원문을 바꾸거나 가짜 보고서를 넣지 않고 해당 경로가 존재하는 작업 트리에서 검사했다.
계약 검사에는 stale·violation·issue가 없으며, 기존 미검토 67개 파일/미분류
4,736개 후보는 남아 있다. 계약 검토 전체 완료를 주장하지 않는다.

변경한 Hub 행의 검토 증거와 인덱스만 갱신했다. 해시 비교에서 llm 및 reference
host 431개 파일이 기준선과 같고, Hub 및 테스트 464개 파일이 최종 검증 복사본과 같다.
상세 원자료와 검증 스크립트는 `tests/hub/reports/signal-refresh-20261031/` 아래에
보관하며 자동 테스트·배포 대상이 아니다.
