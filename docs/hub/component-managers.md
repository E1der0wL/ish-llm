# 컴포넌트 관리 팝업

프로젝트에서 선택한 tools·skills·mcp·rag·agents·workflows만 명령과 자동완성에 나타납니다.
등록된 컴포넌트 이름을 그대로 사용하며 단수 별칭은 제공하지 않습니다.
명령은 `config`와 `help`만 지원하며 나머지 데이터 작업은 관리 창 또는 모델 도구를 사용합니다.

| 명령 | 가져오기 |
| --- | --- |
| `/tools config` | 기존 Python Tool 패키지 디렉토리 |
| `/skills config` | Markdown·텍스트 지침 또는 Skill JSON 파일 |
| `/mcp config` | transport와 command 또는 url을 포함한 MCP 서버 JSON 파일 |
| `/rag config` | UTF-8 텍스트 문서, Markdown 포함 |
| `/agents config` | Agent JSON 파일 |
| `/workflows config` | schema_version 1 Workflow JSON 파일 |

위쪽 경로에 파일/디렉토리를 입력하고 Enter를 누르면 가져옵니다. 상대 경로는
ish의 현재 작업 디렉토리를 기준으로 합니다. 원본 파일은 변경하지 않으며 동일한 ID가
이미 있으면 덮어쓰지 않습니다. 파일 이름에서 ID를 만들고, `SKILL.md`는 부모 폴더 이름을
사용합니다. 경로 자동완성과 가져오기는 UI 스레드를 막지 않습니다.

Tab으로 목록에 이동하고 방향키로 선택합니다. Tool은 Enter로 기존처럼 파일 탐색기를
엽니다. Skill·MCP·Workflow·Agent·RAG는 Enter로 일반 설정의 에디터에서 JSON을 수정합니다.
저장 시 컴포넌트의 스키마와 읽어 온 버전을 검증합니다. 실패한 수정 초안은 팝업을
닫기 전까지 유지합니다. RAG는 title/content/metadata만 편집하며 문서와 검색 색인을
함께 갱신합니다. RAG 등록·수정에는 임베딩 모델이 필요하며 추출 모델은 추출 활성화 시 필요합니다.
MCP 관리 창은 서버 정의를 저장·편집합니다. 가져오기만으로 서버를 실행하거나 연결하지 않습니다.

`d`는 삭제 확인 창을 엽니다. 참조 중인 Skill 등 백엔드에서 삭제를 금지한 항목은
오류 알림으로 이유를 표시하고 유지합니다. 내장 Tool은 Space 활성/비활성 조작을 유지합니다.
항목이 수정 시각을 제공하지 않으면 날짜 칸에 `—`를 표시합니다.

공통 구조는 `hub/widget/forms/component_manager.py`의 `ComponentManager`가 소유합니다.
`ToolManager`와 `RecordManager`는 항목 활성화/편집을 확장합니다.
`RAGManager`는 같은 경로 입력·목록·버튼 레이아웃에 등록 작업 관찰과 재시도를 추가합니다.
Hub의 `RecordManagement`는 공개 ComponentData의 CRUD를, `DocumentManagement`는
RAG의 문서 전용 API를 사용합니다. `AgentManagement`는 snapshot/revise의 revision을 사용합니다.
컴포넌트 내부 저장 파일을 직접 수정하지 않습니다.
관리 작업은 프로젝트 핸들을 고정해 실행하며 다른 세션의 스트리밍을 잠그지 않습니다.

## RAG 등록 작업

`/rag config`의 새 파일 등록은 `aenqueue_document` → `arun_job`을 사용합니다.
완료한 문서와 별도로 대기·취소·실행 상태 확인이 필요한 작업이 목록에 나타납니다.
실패한 작업은 오류를 안내한 뒤 목록에서 숨기며, 다시 열어도 표시하지 않습니다.
실패 작업의 저장된 원문·청크 체크포인트는 삭제하지 않습니다. 같은 파일을 다시 가져오면
새 등록 작업을 시작하며, 숨겨진 실패 기록이 새 등록을 막지 않습니다.
작업을 선택하면 임베딩 완료/전체 청크, 체크포인트 재사용 청크, 이번 시도의 관계 추출 배치 수,
임베딩·관계 추출 소요 시간과 이번 시도 경과 시간을 표시합니다. 임베딩 진행 바의 퍼센트는
임베딩 단계에만 해당하며, 이후 관계 추출·색인 저장에는 불확정 진행 바를 사용합니다.

백엔드 공개 API는 관계 추출과 저장 사이의 독립적인 시작 이벤트를 제공하지 않습니다.
따라서 추출이 활성화된 경우 단계 이름은 `관계 추출·색인 저장`으로 묶어 표시합니다.
관계 추출 시간은 완료된 호출의 누적 값이며 호출이 끝날 때 갱신됩니다. 별도의 저장 시간이나
전체 진행률을 추정하지 않습니다. 재개 시 이미 저장된 그래프 배치는 새 호출 수에 포함되지 않습니다.

하단 **재시도**는 선택한 대기 작업 또는 비정상 종료 후 남은 running 작업을 같은 Job ID로
명시적으로 실행합니다. 원본 파일을 다시 읽지 않고 저장된 입력과 검증된 청크 체크포인트를
재사용합니다. 실제 실행 중인 작업은 Hub 상태와 백엔드의 작업 잠금으로 중복 실행을 막습니다.
실행 여부를 확인할 수 없는 running 기록을 임의로 실패/중단 상태로 덮어쓰지 않습니다.
공개 API에서 생성한 일괄 등록 Job도 목록에 문서 ID들을 함께 표시하고 같은 Job으로 재시도합니다.
해당 일괄 Job에 포함된 문서를 중복 등록하지 않습니다. 재개를 명시적으로 포기한 Job은
재시도할 수 없으며, 같은 문서의 새 등록을 막지도 않습니다.
취소된 작업과 완료된 작업은 재시도할 수 없습니다. 기존 직접 등록 방식의 실패에는 Job이나
체크포인트가 없으므로 목록 복구·재개 대상이 아닙니다. 모델/분할 등 준비 설정이 달라져
백엔드가 재개를 거부하면 기존 체크포인트를 변경하거나 강제로 재사용하지 않습니다.

팝업을 닫거나 최소화해도 실행 중인 등록을 취소하지 않습니다. 다시 열면 공개 Job 조회와
Hub의 실행 관찰을 통해 진행 상태를 복구합니다. 열려 있는 관리 창만 1초 간격으로 작업 목록을
조회하며, 최초 등록 창의 진행 알림은 0.25초 간격으로 전달합니다. 조회할 때마다 전체 문서
코퍼스를 읽지 않으며 작업이 끝나 목록에서 빠졌을 때 문서 목록을 다시 읽습니다.
작업 기록은 편집/삭제하지 않습니다. 완료한 문서의 편집·삭제는 기존 문서 API를 유지합니다.
