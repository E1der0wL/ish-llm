# 코딩 스킬과 응답 UX

## 사용

새 프로젝트에는 Graph 에이전트 `planner`와 `hub-code-workflow`도 제공됩니다.
`/agent`에서 `assistant`의 모델/연결을 설정하고, 대화 상대 목록에 `planner`를
추가하여 수신 대상으로 선택하세요. `planner`는 별도 모델 설정 없이 같은 프로젝트의
`assistant`를 각 단계에서 사용합니다. 다른 기본 Agent ID를 명시했다면 그 Agent를 참조합니다.
단계는 요청·환경 확인 → 실제 파일 수정·디버깅 → 테스트·보완 → 결과 정리입니다.
앞 단계의 결과를 다음 단계에 전달하고, 최종 단계의 답변을 출력합니다.
각 단계의 진행·체크포인트·도구 승인·재개는 llm의 Graph/Agent 계약을 그대로 사용합니다.

Python, Perl, C, C++, C#, Java, Rust, JavaScript, TypeScript, bash, csh, zsh, tcsh의
기존 빌드·테스트 도구를 먼저 확인하도록 안내합니다. 언어 도구를 자동 설치하지 않으며,
없는 도구나 실행하지 못한 검사는 결과에 구분해서 보고합니다. 검증 단계에는 최대 3회의
수정·재검증을 지시하지만, 지침만으로 모델의 작업 성공을 보장하지는 않습니다.
`/workflow`에서 기본 흐름을 수정할 수 있습니다. 기존 프로젝트에는 자동 추가하지 않습니다.
참조 보호도 유지됩니다. `planner`가 사용하는 Workflow 컴포넌트를 끄거나 그 Workflow가
참조하는 `assistant`를 삭제하려면 먼저 해당 참조를 수정하거나 제거해야 합니다.

새 프로젝트에는 `hub-code-change` 스킬이 등록됩니다. 지침 원본은
`hub/asset/skills/coding.md`입니다. 문맥 확인 → 구현·재현 → 필요한 격리 실험 → 검증 →
요청한 파일 반영을 안내합니다. 스킬은 모델에 주는 지침이며 도구 권한이나 실행 보장은 아닙니다.

기본 지침 버전 4는 프롬프트와 스킬의 제목·설명·본문을 모두 영어로 제공합니다.
답변 언어는 사용자의 언어를 따릅니다. 파일·스크립트·기능을 “작성해줘”라고 요청한 경우 실제 파일 생성·수정과
저장 확인을 완료 조건으로 둡니다. 코드 블록만 답하거나 다음에 작업하겠다는 제안으로 끝내지
않도록 합니다. 설명·예시·검토·대화용 초안 요청은 문맥에 따라 답변으로 처리합니다.
사용자가 지정한 경로와 ish에서 전달한 작업 디렉터리를 사용하며, Hub 내부 저장소나 테스트
복사본을 최종 산출물로 혼동하지 않도록 안내합니다. 승인 절차와 검토만 하라는 요청은 유지합니다.

[Karpathy-inspired guidelines](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md)의
가정 확인·단순성·변경 범위·검증 원칙을 참고해 기존 지침에 통합했습니다. 공통 작업 수행·
권한·완료 보고는 시스템 프롬프트에, 코드의 구체적인 설계·테스트·diff 검토는 코딩 스킬에 둡니다.
새 설정이나 기능을 미리 추가하지 않되 책임 분리·테스트·실제 재사용을 위한 추상화와 사용자가
요청한 구조 정리는 허용합니다. 중요한 결정만 질문하고, 사소한 선택은 합리적인 기본값으로
진행하며, 필요한 검증이 끝나면 이유 없이 반복하지 않도록 합니다.

기존 프로젝트의 사용자 스킬은 자동 덮어쓰지 않습니다. 현재 버전을 별도 ID로 가져오려면
`hub/asset/skills/coding.md`를 `coding-tested.md`라는 이름으로 복사하고 다음 관리 창을 엽니다.

```text
/skill
```

상단 경로 입력창에 복사한 파일의 경로를 입력하고 Enter를 누릅니다. 목록에서
`coding-tested` 항목을 확인한 뒤 다음처럼 요청할 수 있습니다.

> coding-tested 스킬을 읽고 calculator.py의 덧셈 오류를 재현해줘.
> 필요한 파일만 테스트 공간에 복사해서 테스트를 작성하고, 수정 후 다시 검사해줘.
> 원본 반영 전에는 변경 내용을 보여줘.

동일한 ID가 이미 있으면 가져오기가 실패하며 기존 항목은 유지됩니다. `/skill`에서
도움말 버튼으로 관리 창 사용법을 볼 수 있습니다. 컴포넌트 명령은 인자 없이 관리 창을 엽니다.
시스템 프롬프트도 새 프로젝트 생성 시에만 기본값을 복사합니다. 기존 프로젝트에는 `/agent`의 Agent 편집 화면에서
`system_prompt`에 `hub/asset/prompts/system.md`의 필요한
내용을 기존 사용자 지침과 합쳐 저장하세요. 템플릿 버전은 출처 정보이며 자동 갱신 지시가 아닙니다.
기존 프로젝트에는 `/tool`에서
필요한 `test_workspace_*` 및 파일 도구가 활성화되어 있는지도 확인하세요.
파일 도구의 기준 경로는 요청 시 전달된 ish 작업 디렉터리입니다. 호스트 환경이 전달되지 않은
호출은 `HubConfig.file_root`를 사용하고, 그것도 없으면 프로젝트 저장 경로를 사용합니다.
`file_root=None`만 경로 미지정을 뜻합니다. 명시된 값은 Path 입력으로 검증하고 파일 도구,
가져오기, 화면과 재시도 근거에 전달합니다. 빈 문자열은 CLI의 `Path("")`와 같이 현재 디렉터리를
가리킵니다. HubConfig는 상대 경로의 값을 바꾸지 않으며 실제 사용 시점의 경로 해석을 유지합니다.

격리 실행에는 Bubblewrap과 사용할 Python 런타임이 필요합니다. 가상환경 실행 파일의
심볼릭 링크가 샌드박스에서 보이지 않는 위치를 가리킬 수 있으므로, 마운트된 실제 실행
경로를 사용해야 합니다. 사용할 환경이 없으면 호스트 명령으로 우회하지 않습니다.
[테스트 공간 계약](../llm/test-workspaces.md)의 격리 범위와 승인 절차를 따릅니다.

## 화면 동작

- Enter 직후 출력창에 `어시스턴트 · 준비 중 · 소요 시간`이 나타납니다.
  이 항목은 UI의 임시 표시이며 사용자 입력의 저장 완료를 의미하지 않습니다.
  저장 실패 시 사라지고 입력 초안은 유지됩니다.
- 초기 준비 시간은 UI 단조 시계로 표시하고, 응답 항목은 Hub가 요청을 받은 시각부터
  종료 시각까지 표시합니다. 재시작 후에는 저장된 사용자 메시지 생성 시각을 사용합니다.
  Run 자체의 실행 시간은 변경하지 않습니다.
- 완료 응답 끝의 `<hub-next>추천 요청</hub-next>`는 본문에서 숨기고 입력창의 흐린
  미리보기로 표시합니다. 입력 끝에서 **→**로 전체 문구를 채우고, **Enter**로 전송합니다.
  사용자가 일치하지 않는 내용을 입력하거나 다른 세션·질문 입력으로 이동하면 적용하지 않습니다.
- 추천은 별도 모델 호출 없이 같은 응답에 포함하도록 요청합니다. 모델이 태그를 보내지 않거나
  적절한 후속 작업이 없으면 추천을 표시하지 않습니다. 코드 블록 안의 태그는 그대로 보입니다.

## 구현 경계와 검증

`HubSkillComponent`는 llm의 SkillComponent를 상속하여 읽기 전용 스냅샷 핸들러만 작업
스레드에서 실행합니다. 임의의 비동기 도구나 부작용이 있는 도구는 이 방식으로 옮기지 않습니다.
컴포넌트 명령·Tool 관리·실행 목록·로그 조회는 명시적인 프로젝트 핸들과 서비스의
수명·버전 잠금을 사용하고 화면 선택 잠금을 오래 점유하지 않습니다. RAG 등록처럼 긴
작업도 출력 관측을 막지 않습니다. UI의 프로젝트 선택·변경 명령은 계속 직렬화합니다.

렌더 작업은 실행 중인 프레임을 표시한 뒤 대기 중인 최신 프레임으로 진행합니다. 크기·테마·
세션이 달라진 결과는 버리고, 세션 변경 및 취소 세대 검사는 전달 시에도 유지합니다.
따라서 0.1초보다 오래 걸리는 렌더가 새 요청 때문에 무한히 폐기되지 않습니다.

추천 지침은 공개 `CompletionProcessor` 계약으로 모델 입력에만 추가합니다. 저장된 대화
메시지 ID를 추가하지 않으므로 도구 승인 체크포인트와 재개 경로를 유지합니다.

`tests/hub/test_coding_skill.py`는 고정된 모델 응답과 실제 도구 실행을 사용합니다. 임시 원본의
버그를 복사하고, 테스트 파일을 작성하고, 실제 Bubblewrap/Python 실행 실패를 확인하고,
해시를 확인한 파일 패치 후 성공을 검증합니다. 승인·재개 API를 실제로 거치고 격리 실험 중
원본이 유지되는지 확인합니다. 검증된 패치와 새 테스트를 원본에 반영하고 원본에서 재검증한
뒤 작업 공간 삭제도 확인합니다.
별도 전달 테스트는 새 지침을 실제 모델 입력에 넣고, 승인 전 파일 미생성, 승인 후 ish 작업
디렉터리에 생성·읽기 확인, 기존 사용자 파일 보존 및 예시 전용 응답의 파일 무변경을 검사합니다.
외부 모델의 스킬 준수 품질을 평가하는 테스트는 아닙니다.

Linux Python 3.12.14에서 전체 검사를 실행하려면:

```sh
.venv-linux312/bin/python tests/llm/run_linux.py --hub --full \
  --modules tests.hub.test_coding_skill tests.hub.test_followup \
  tests.hub.test_render_pipeline tests.hub.test_responsiveness
```

실제 검사는 Linux 파일시스템의 해시 기록된 복사본에서 실행됩니다. `llm/` 구현은 수정하지 않습니다.

  하지 않았습니다. `llm/` 소스 변경은 없습니다.
