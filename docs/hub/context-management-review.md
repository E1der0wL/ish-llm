# 누적 컨텍스트와 UI 보강 검토

## 구현 경계

`WorkingContext`는 Memory 다음에 실행되는 Hub completion processor에서 모델에
전달할 복사본만 다룬다. 사용자가 지정한 Memory 우선순위도 따라가며, 저장 설정을
바꾸지 않는다. 요약 실패 시 사용 가능한 Step 참조로 Tool 본문을 줄이고, 필요하면
완료된 앞부분 교환만 참조 목록으로 바꾼다. 현재 요청·추가 지시·미완료 Tool 교환은
제거하지 않는다. 전체 모델 입력의 판단은 실행에 주입된 CompletionPolicy를 쓴다.

원문 저장·승인·체크포인트·효과 영수증은 Backend가 계속 소유한다. Hub는 요약을
위해 Tool을 재실행하지 않으며, 참조 목록을 의미 요약이나 작업 성공 증거로 표시하지
않는다. `compact_active: false`, `active_keep_iterations`, 요약 실패 시 `raise` 등
명시적 선택은 유지한다. 자세한 순서와 한계는 [컨텍스트 처리](working-context.md)에 있다.

## UI 변경

- 검색 팝업의 공통 불투명 배경과 내용을 같은 렌더링 작업으로 그린다. 중첩 Float의
  레이어 순서 때문에 본문이 지워지는 문제와 ScrollablePane의 즉시 복사 동작을 함께
  고려했다. 팝업 자동완성의 별도 최상위 레이어는 유지한다.
- 읽기 전용 로그 뷰어는 기록 유무와 관계없이 강조 색 5 배경을 사용한다.
- 일반 버튼 포커스 글자와 하단 `<키>`는 강조 색 2다. 하단 이동키 표시는
  `←↓↑→`이며 실제 Home/End/PageUp/PageDown 조작은 유지한다.
- 일반·보조 버튼은 공통 Button에서 눌림을 처리한다. Enter·Space·마우스 클릭 시
  글자가 강조 색 1로 0.15초간 바뀐다. 실제 작업은 즉시 실행하며, 배경색이나
  정렬을 바꾸지 않는다. 닫히는 팝업을 효과 표시 때문에 지연시키지 않는다.

## 검증 방식

Linux Python 3.12.14와 WSL Linux 파일시스템의 소스 복사본을 사용했다. 복사본의
파일 해시와 실행 로그는 `tests/hub/reports/context-management/`에 기록한다.
외부 모델이나 사내 서버에 요청하지 않고, 결정적인 Provider 대역으로 입력 예산과
Tool 효과 횟수를 확인한다. UI는 PTK 실제 Renderer와 키·마우스 경로로 검증한다.

S1–S7 검사는 `architecture-button-final.json`에서 새 후보·낡은 근거·미해결 항목·검토 오류
없이 통과했다. 개별 소유권 근거만 갱신했으며 전체 계약 목록을 자동 승인하지 않았다.
`llm/`은 작업 시작 시 기록한 385개 파일의 해시로 변경하지 않았음을 확인한다.

전체 저장소 검사의 의존성 잠금 입력과 전체 계약 목록 검사는 별도 결과로 취급한다.
정적 검사에 필요한 Git·lock·공통 문서가 빠진 실행 복사본에서 생긴 오류를 제품
회귀로 분류하지 않으며, 원본 저장소에서도 확인한 불일치는 통과로 덮지 않는다.

## 사전 축소와 오류 후 복구의 구분

사전 축소가 이미 끝난 참조 요청에 Provider가 계속 400을 반환하더라도 같은 요청을
무조건 반복하지 않는다. 기존 복구 정책이 실제로 줄일 내용이 없다고 판단하면
`no_correction`으로 종료한다. 재시도 횟수는 상한이며 반드시 채워야 하는 횟수가 아니다.

기존 Provider 복구 시험은 사전 참조 임계값 이하의 입력으로 요약·재시도·취소·예산을
계속 검증한다. 별도 시험은 큰 입력이 먼저 참조로 바뀌고, 실제 서버 오류가 계속될 때
원문과 Tool 효과 1회를 보존하며 동일 요청을 재전송하지 않는지 확인한다.

검증 중 발견한 버튼 콜백 비교 실패는 제품에서 기존 `handler`를 보존하는 방식으로
수정했다. 하단 이동키 표시 검사는 새 `←↓↑→` 기대값으로 갱신했다. 최초 실패 로그는
삭제하거나 통과 기록으로 덮어쓰지 않았다.

## 실행 결과

서로 겹치는 집중 검사의 수를 합쳐 전체 통과 개수로 표현하지 않는다.

- `final-order.txt`: 컨텍스트·Memory 우선순위·질문/승인·관련 UI 38개 통과.
- `button-contract-final.txt`: 최종 버튼 동작과 콜백 보존, 검색·로그·팝업·마우스
  회귀 45개 통과.
- `input-contract-final.txt`: 변경한 키 안내와 셸/공통 팝업 조작 4개 통과.
- `provider-recovery-final.txt`: 복구 검사 20개 통과. 함께 실행한 다중 Agent UI
  1개는 reasoning 표시 대기 제한에 걸렸다. 동일 사례의 단독 재현
  `probe_ui.py`는 39.644초에 통과했다. 대기 제한이나 제품 동작을 완화하지 않았다.
- `hub-final-full.txt`: 중간 소스의 전체 Hub 검사. 버튼 콜백, 옛 이동키 문구,
  사전 축소와 충돌한 복구 fixture 실패는 위 집중 검사로 수정 후 재검증했다.
  질문 UI에서 진행이 멈춰 해당 실행은 중단했으므로 전체 통과 기록이 아니다.
- `hub-remaining-final.txt`: 질문 UI부터 재개한 분리 검사도 질문 대기 오류를
  기록했고, RAG 팝업 검사 중 traceback 기록에서 끝났다. 이후 미실행 검사를
  통과로 간주하지 않는다.
- `popup-question-isolated.txt`: 위 질문 응답·중단·동일 Run 이어가기와 RAG 팝업
  닫기/재열기 4개를 최종 소스로 단독 실행해 46.488초에 모두 통과했다. 기존
  대기 제한과 제품 동작은 그대로다. 전체 실행의 시간 민감성은 별도 한계로 남긴다.
- `tests/llm/reports/ish-provider-8mj_vjka/suite.txt`: Backend 전체 2,577개 실행,
  실패 4건·오류 7건. 스냅샷의 Git/lock/공통 문서 누락, 수정 전 감사 해시,
  색상 선택 필드에 대한 옛 기대값 및 host loader의 제거된 private API 참조가
  포함된다. 마지막 Hub 자동 재실행은 별도 최신 실행과 중복되어 중단했다.
- 원본 저장소에서 정적 검사를 다시 실행해 문서 검사는 통과했고, lock 입력과
  전체 계약 목록·해시 불일치는 남아 있음을 확인했다. `llm/`과 기존 감사 목록을
  임의 변경해 이 결과를 숨기지 않았다.

따라서 이번 범위의 집중 검증과 S1–S7 통과를 전체 저장소의 완전한 통과로
표현하지 않는다. 문서 링크·예제 검사는 `docs-final.json`, 실제 소스 해시는
각 `*-snapshot.json`에 있다.
