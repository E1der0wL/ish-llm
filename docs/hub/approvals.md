# 승인 범위와 기억 규칙

UI를 확정했으며 최종 작업본의 Hub 전체 회귀 테스트가 통과했다.
llm 구현은 변경하지 않았다. 이전 실행과 최종 재검증 결과는 아래 기록과 같다.

## 사용자 경로

기존 승인 대상 Tool의 요청은 입력창에서 처리한다. 이번만 허용, 동일 작업 허용,
명령 범위 허용, 거절을 표시한다. 기억하는 허용은 조건을 확인하는 팝업을 열고
세션/프로젝트를 선택한 뒤 **적용**으로 확정한다. 팝업 취소는 승인하지 않는다.
추가 입력값이 없는 승인(선택지 9개 이하)은 입력창에서 번호 키만 눌러 선택한다.
이번만 허용·거절은 바로 응답을 전달하고, 동일/명령 범위 허용은 먼저 조건 확인 팝업을 연다.
질문·추가 값이 필요한 승인·두 자리 번호 선택지는 기존 Enter 전송을 유지한다.
Hub의 붙여넣기와 터미널 bracketed paste는 번호 키 선택으로 해석하지 않으며
별도 Enter 없이 승인하지 않는다. 붙여넣기 구분 없이 일반 키로 보내는 터미널 입력은
실제 번호 키와 구분할 수 없다.
단순 셸 구문으로 해석할 수 있는 `shell_execute`에서 명령 범위 허용을 제공하며,
다른 도구나 해석할 수 없는 셸 구문은 동일 작업 허용을 사용한다. 일반 질문과
불확실한 실행 효과에 대한 재시도 승인은 기존 선택지를 유지하며 기억 규칙을 만들지 않는다.

승인 폼의 보조 버튼 또는 설정 → 프로젝트 → 일반 → **승인 규칙 관리**에서 같은
관리 팝업을 연다. 승인 입력 중 Ctrl+S로 관리 보조 버튼, Enter로 팝업에 진입한다.
추가 전역 단축키나 slash 명령은 없다. 설정에 저장하지 않은 변경이 있으면 먼저
저장/취소해야 하며, 팝업에서 돌아올 때 해당 프로젝트 설정을 다시 조회한다.

* **규칙**: 범위·위험도·버전·조건을 조회하고, 전체 인자와 알려진 위험도의
  상한을 수정하거나 철회한다. 명령 범위 규칙은 명령 앞부분 목록을 편집한다.
  세션/프로젝트 범위, Tool 실행 계약과 환경, 생성 증거는 바꾸지 않는다.
  다른 평가기에서 만든 조건은 상세 조회·철회만 지원한다.
* **승인**: 일시 정지된 Run의 승인 상태를 조회하고 개별 승인을 취소한다.
  위험도 지정은 사용자 판단을 명시적으로 저장한다. 숫자를 입력하지 않으면 저장하지
  않는다. **적용·재개**는 별도 동작이다. 재분류 자체로 승인하거나 실행하지 않는다.
  새로고침 버튼은 없다. 팝업 진입·탭 전환·변경 완료 시 공개 API로 다시 조회한다.
  승인 탭의 버튼은 보통 크기에서 상세·위험도·적용·재개·취소·닫기를
  한 줄에 배치한다(적용·재개는 하나의 버튼). 좁은 터미널은 공통 버튼 줄바꿈을 따른다.

규칙 탭의 버튼은 상세·편집·철회·닫기다. 탭 아래 고정 설명은 제거하고,
하단 요약 영역에 **규칙 정보 / 요청 정보**를 공통 카테고리 스타일(강조 색 1·볼드체)로
표시한다. 철회와 개별 승인 취소의 차이는 각 확인 팝업의 설명에 유지한다.

Tab/Shift+Tab으로 영역을 이동하고 탭 목록과 버튼 영역에서는 좌우 방향키를 쓴다.
목록은 위아래 방향키, Enter/Space는 버튼 실행이다. 편집·상세·확인 팝업은 부모
관리 화면을 유지한다. 목록 조회나 저장은 렌더링 경로 밖에서 수행하고 진행/상태는
활성 팝업 하단 한 줄에 표시한다.

## 소유권과 허용 조건

Hub의 `ToolApprovalConditions`가 조건 생성과 평가기 등록을 소유한다.
`hub-exact-tool-action`, revision `1` 구현은
llm의 `SchemaApprovalEvaluator`를 사용하고, 조건은 public ToolApprovalAction의
Tool 이름·전체 인자·실행 계약·Tool 정책의 정확한 일치를 요구한다. cwd/env는 명시
인자와 Hub 환경 Tool 계약 revision에 결합된다. 파이프라인의 앞부분만 비교하거나
환경을 무시하지 않는다. Tool 인자에 포함된 평가 보조 데이터도 임의로 제거하지 않는다.

`hub-shell-command-range`, revision `1`은 공개 `ApprovalEvaluator` 계약을 구현한다.
명령을 셸로 실행하지 않고 단어와 `|`, `&&`, `||`, `;`로만 분리한다. 각 명령의
인자 목록이 사용자가 확인한 접두사와 일치해야 하며 명령 수와 연결 연산자도 같아야 한다.
예를 들어 `git status` / `head`를 확인한 `git status --short | head -n 30` 규칙은
각 접두사 뒤의 인자 변경을 허용한다. `git log`, 추가 명령, 연결 연산자 변경은 불일치다.
접두사는 위험도나 읽기 전용 보장이 아니다. 뒤의 인자가 바뀔 수 있음을 명시하고
사용자가 좁히거나 취소할 수 있게 한다. cwd/env·명령 외의 모든 인자·실행 계약·정책은
정확히 비교한다. 리다이렉션, 변수/명령 치환, 글롭, 백그라운드 실행, 제어문,
해석할 수 없는 따옴표 등은 범위 규칙으로 허용하지 않는다. 별도 모델 유사도 판단은 없다.

이 방식은 Claude Code의 명령 패턴, Codex의 argv 접두사와 하위 명령별 검토를 참고한다.
두 제품의 전체 셸 분석기를 복제하거나 모든 셸 문법을 지원한다고 주장하지 않는다.
참고: https://code.claude.com/docs/en/permissions 및
https://developers.openai.com/codex/rules

위험도·분류는 조건 평가와 별도로 llm이 검사한다. unknown 요청은
`basis="explicit_unknown"`으로 기억하며 임의의 숫자로 바꾸지 않는다. 알려진 위험도는
현재 프로젝트 척도와 일치해야 하며 승인한 요청의 위험도를 상한으로 전달한다.
정책 enabled 값은 자동 변경하지 않는다. 규칙은 새 Run의 정책 스냅샷부터 적용된다.

응답은 `arespond(..., remember=..., request_key=...)`로 원자 저장한다. 동일 요청의
재전송은 같은 receipt key와 규칙 ID를 사용한다. UI는 저장 확인 직후 답변 처리를
완료하고 명시적 `resume()`를 진행한다. 수동 응답은 중복 `resume_plan()` 조회 없이
백엔드가 저장된 결정을 검증하게 한다. 정책 재개는 불확실한 효과를 제외하기 위해
`resume_plan()`과 revision을 확인한다. 수동/정책
승인의 재개 경로는 같은 런타임 잠금을 사용하고 백엔드의 revision/CAS 검사를 유지한다.
Hub가 `retry_nodes`를 만들어 불확실한 Tool을 재실행시키지 않는다.
최근 재개 접수의 공개 RequestHandle은 최대 128개만 보관하여 중복 접수·조회 작업을 억제한다.
권한이나 영속 상태의 대체 저장소가 아니며, 요청 상태를 공개 API로 확인하고 예약 취소·실패 시
해당 관측을 버린다. 실행 전 목록 조회도 같은 Run 단위 잠금으로 재개 접수와 경합하지 않는다.
수동 결정은 중단·실패 후 명시적으로 다시 열린 승인도 처리한다. 자동 재개는 일시 정지된
정책 승인에만 적용하고, 사용자가 중단한 실행과 불확실한 Tool 재실행은 포함하지 않는다.

규칙 조회·수정·철회는 `project.approvals`만 사용하며 변경에는 관측한 revision을
전달한다. 개별 취소는 `cancel_interaction()`, 위험도 변경은 `reclassify()`를 사용한다.
규칙 철회는 이미 발급된 승인을 취소하지 않고, 개별 취소는 규칙을 철회하지 않는다.
resume admission 이후 취소나 재분류는 백엔드가 거부한다. UI 관측 상태는 권한 근거가 아니다.

프리셋은 발급된 승인 증거를 다른 프로젝트에 복제하지 않는다. 내보낼 때 기억 규칙은
제외하고, 적용할 때 대상 프로젝트의 기억 규칙을 보존한다. 증거가 포함된 수동 프리셋은
거부한다. 일반 설정 JSON으로 증거를 생성·삭제하거나 별도 Hub 승인 저장소를 만들지 않는다.

## UI 확정 후 검증 범위

1. 이번만/동일/명령 범위와 세션/프로젝트, unknown 유지, 전체 파이프라인·인자·환경 차이의 재승인.
2. 동일 응답 재전송, 중복 재개 방지, 이미 수행한 Tool 결과 재사용, 명시 중단 유지.
3. 규칙 수정·철회 CAS, 개별 승인 취소, 재분류 후 이전 승인 무효화, 정책 적용과 재개 분리.
4. 프리셋에서 증거 이동 방지, 설정 초안 보존, UI 영역/하위 팝업/최소화 복구.
5. 일반 질문·거절·불확실 효과 승인·Loop/Graph의 기존 흐름 및 Hub 전체 회귀.
6. 범위 규칙의 단어 경계, 파이프 각 명령·연결 연산자, 접두사 편집, 특수 셸 구문 거부.
7. 번호 즉시 선택, 입력값이 필요한 질문/승인의 Enter 유지, bracketed paste 무승인.

## 2026-11-02 검증 기록

WSL Linux Python 3.12.14에서 해시를 확인한 Linux 파일시스템 사본을 사용했다.
X11/네트워크 테스트는 별도 namespace와 loopback에서 실행했으며 실제 사용자 ish,
프로젝트 데이터, 외부 모델 API는 사용하지 않았다.

* 전체 Hub 회귀: 1,036개 실행, 1,033개 통과, 실패 1개·오류 2개, skip/missing 0개.
  실패는 제거한 세 번째 입력 선택지를 기대하던 테스트였고, 오류 둘은 승인 공통화 후
  공개 Session/Run 식별자가 없는 테스트 대역이었다. 함께 확인한 수동 승인 경로의
  불필요한 재개 사전 조회도 제거하여 기존 지연 계약을 유지했다.
* 최종 영향 범위 재검증: 승인·정책·재개·질문·대화 상대·설정·프리셋·팝업·출력·오류
  21개 모듈, **146개 모두 통과**, 실패·오류·skip·missing 0개. 앞선 3개와 새로 추가한
  기존 사용자 승인 보존/재개 테스트를 포함한다. 수정 뒤 전체 1,037개를 다시 실행한
  결과로 해석하지 않는다.
* 로컬 증거: `tests/hub/reports/approval-validation-20261102/`의
  `full-final.json`, `focused-verified.json`, `verified-source.json`.
  테스트·제품 소스가 검증 사본과 일치하며 최초 llm 해시와 변경이 없음을 확인했다.
* 상태 문구는 헤더에만 남기고 실제 본문과 오류 해결 안내를 보존하는 테스트 및
  숫자 키/추가 입력/붙여넣기를 구분하는 실제 PTK 입력 테스트를 포함한다.

`python -m tests.llm.run_regression --suite hub`를 모듈 제한 없이 실행했다.

* 발견·실행·통과 **1,037개**, 실패·오류·skip·missing·중복 0개, 종료 코드 0.
* 소요 시간 1,494.8초(약 24분 55초).
* 승인·정책·재개, 실제 저장·Tool 실행, RAG, Memory, Graph Workflow,
  로컬 HTTP 제공자 연동, 스트리밍·설정·팝업·클립보드를 포함한다.
  외부 모델 API나 실제 사용자 프로젝트 데이터는 사용하지 않았다.
* 검증 중 제품·테스트 코드를 변경하지 않았다. 현재 Hub·Hub 테스트·llm의

전체 통과는 아래에 기록한 별도 백엔드 조회 API 결함까지 수정했다는 뜻은 아니다.

이후 버튼 이름·카테고리 제목·상단 설명만 정리한 UI 변경은 승인 UI, 언어팩,
팝업 버튼 이동·상태 복원 4개 모듈 27개 검사로 확인했고 모두 통과했다.

반복하지는 않았다. 증거와 화면은 `tests/hub/reports/approval-manager-ui-20261102/`에
보관하며 실행·승인 로직과 llm은 변경하지 않았다.

## 검증에서 확인한 백엔드 경계

사용자가 변경한 현재 llm의 `InteractionRepository.views()`는 재개 요청 Message가 이미
예약되었지만 새 Run이 아직 생성되지 않은 짧은 구간에서 존재하지 않는
`RunStatus.QUEUED`를 참조한다. 직접 `ainteraction_views()` 조회 시 AttributeError가
발생할 수 있음을 동시 재개 테스트에서 확인했다. llm 파일은 수정하지 않았다.
Hub의 공통 승인 흐름은 성공한 재개 접수의 공개 핸들로 중복 작업을 억제하고,
관리 목록 역시 접수가 완료된 원본 승인을 다시 조회하지 않는다. 이는 중복 UI 작업을
정리한 것이며, 백엔드 공개 조회 API 자체의 결함까지 수정한 것으로 간주하지 않는다.

## 출력 상태

빈 에이전트 본문에 일시 정지·중단·취소·대기 상태 문구를 추가하지 않는다.
상태는 기존 응답 헤더에 남기고 실제 본문·도구 기록은 보존한다. 최종 본문이 없는
완료 응답의 안내와 시스템 오류 원인·해결 안내는 단순 상태 중복이 아니므로 유지한다.

## 실행 중 입력

실행 중 Enter 전송 팝업은 **추가 지시**와 **예약(현재 작업 이후 새 요청)**만 제공한다.
추가 지시가 첫 항목이자 기본 선택이며, 접수된 지시는 원래 요청 말풍선 하단에 표시한다.
영속 지시 기록과 대상별 반영 상태는 그대로 유지한다. 장시간 명령의 처리 경계는
[명령 실행 중 추가 지시](command-steering.md)를 참고한다.
Graph의 노드 지시 예약을 이 선택지에서 제거했으며 기존 공개 백엔드 예약 API는 유지한다.
닫기/취소 시 입력 초안을 복구하고, 추가 지시는 실행 대상 선택과 기존 steering 경로를 따른다.
