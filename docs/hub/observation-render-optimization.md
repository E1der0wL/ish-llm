# 조회·렌더링 3단계 최적화

`llm/`과 host 소스는 변경하지 않는다. 요청의 durable QUEUED, 실행·승인·재개,
기존 키·스크롤·태그·최종 Markdown 결과는 유지한다. 화면 캐시는 실행 권한이 아니다.

| 단계 | 개선 |
|---|---|
| 1 | 실행 상태 변경마다 조회를 취소·반복하던 비용 제거; 선택 세션 우선 표시와 다른 세션 갱신 분리 |
| 2 | 실행 기록의 표시 전용 투영과 동일 값 재사용; 대화·생각 기록의 변경 구간만 준비 |
| 3 | Rich Console·스타일 자원 재사용; 검색·팝업·표 준비가 공유 렌더 경로를 장시간 독점하지 않도록 분할 |

## 계약과 소유자

- `SnapshotReader`와 `BackgroundObservations`는 공개 API 관찰만 담당한다.
  비선택 세션의 오래된 행은 표시 전용이고 알림·제목 판단에는 최신 조회만 전달한다.
  실행과 상호작용은 기존 공개 API로 다시 검증한다.
- `RunDisplay`는 선언된 표시 필드만 분리한다. Completion·Agent·Resume 원본 계약의
  필드를 임의로 축약하거나 새 실행 기록으로 만들지 않는다.
- `unchanged_prefix`는 불변 표시 객체를 비교한다. 삭제·재정렬·폭·테마·동적 렌더러
  변경 시 영향을 받는 영역을 다시 준비한다. 수신하지 못한 delta는 기존 조회로 복원한다.
- `RenderResources`는 각 렌더 소유자의 제한된 Console·스타일 캐시다.
- `RenderWork`는 기존 4개 슬롯 안에서 작업을 나누며 스레드나 대기열을 추가하지 않는다.
  세대/닫힘 검사는 결과 전달 시에도 유지한다. Markdown 최종 의미를 바꾸는 줄 단위
  임의 파싱은 사용하지 않는다.

## 측정 조건

Linux Python 3.12.14, 해시로 확인한 WSL Linux 파일시스템 소스·작업 공간을 사용한다.
사용자 WSL 프로젝트의 정책을 읽어 격리된 측정 공간에 적용하며 원본은 수정하지 않는다.
비밀 값은 출력/보고서에 기록하지 않고 모델 연결만 합성 HTTP/SSE 응답으로 바꾼다.
실제 ish Prompt, PTK Enter·화면, Hub worker, 공개 backend API, 실제 fsync를 사용한다.
세션 4개, 인사·파일 조회·긴 입력·이력 뒤 요청을 변경 전/후/전/후 순서로 실행한다.
제목 생성·후처리·완료 검증을 측정 편의를 위해 끄지 않는다.

별도로 대화 1,000개, Tool 이력 500개, 긴 코드 블록의 변경 렌더링과
검색·팝업 중 실제 PTK 화면 표시 지연을 비교한다. 테스트/감사 실행과 시간 계측을
동시에 돌리지 않는다. 서버의 실제 추론·네트워크 시간은 이 측정에 포함되지 않는다.
전역 설정 파일이 없는 현재 WSL 환경의 UI 주기는 기본값 0.1초이다.

원본 자료·실패한 검사·수정 후 재검사는
`tests/hub/reports/six-stage-20261101/`에 각각 보존한다.

## 검증 결과

- 1단계 집중 검사: 73개 통과.
- 2단계 집중 검사: 94개 통과.
- 3단계 집중 검사: 77개 통과.
- 구조 S1~S7, 계약 근거 검사, 문서 링크 검사는 통과했다.
- 전체 Hub 회귀 검사: 931개 실행, 930개 통과, 테스트 자료 오류 1개. 건너뜀·누락 없음.
- 오류는 다른 프로젝트의 알림 테스트가 `metadata` 등 실제 Run 필드가 없는
  `SimpleNamespace`를 넘기던 자료에서 발생했다. 공개 `Run`과 `AgentBinding`을
  사용하는 자료로 고쳤으며 기존 알림 누락·중복 검증은 유지했다.
- 자료 수정 후 해당 모듈 6개 검사 모두 통과. 제품 코드는 전체 검사 이후 변경하지 않았다.
- 두 번째 전체 검사는 제품 코드 변경 없이 중복 실행한 것으로 판단해 중단했다.
  전체 단일 실행이 931/931 통과했다고 표기하지 않는다. 첫 전체 결과와 수정 후
  집중 재검사 결과를 함께 보존한다.

공유 감사 자료는 변경한 Hub 소유자와 직접 테스트의 해시·검토 근거만 갱신했다.
전체 저장소의 기존 미검토 파일 67개를 임의로 검토 완료로 바꾸지 않았다.
현재 감사 지표는 오래된 해시 0, 계약 위반 0, 불완전 계약 0이다. 미분류 후보는
4,742개에서 4,749개로 바뀌었으며, 기존 미검토 소유자 내부의 새 표시 처리 리터럴도
전체 파일 검토를 대신해 일괄 면제하지 않았다. 이 검사를 전체 저장소의 계약 감사
완료로 해석하지 않는다.

## 전후 계측 결과

최종 소스의 변경 전/후/전/후 두 차례 반복 결과다. 서버 응답은 로컬 합성이므로
아래 호출 준비 시간에 실제 모델 추론 시간은 포함되지 않는다.

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| 대화 1,000개·Tool 기록 500개 변경 렌더링, 각 실행 중앙값 | 5.28 / 5.57ms | 3.13 / 3.02ms |
| 같은 렌더링의 각 실행 p95 | 7.78 / 7.34ms | 4.69 / 5.28ms |
| 60,000줄 팝업 검색 중 출력 화면 변경 표시 | 408 / 410ms | 25 / 21ms |
| 60,000줄 팝업 준비 중 출력 화면 변경 표시 | 101 / 93ms | 51 / 14ms |
| 첫 인사 요청 → HTTP 도착, 두 반복 중앙값 | 1.384초 | 1.420초 |
| 다음 인사 요청 → HTTP 도착, 두 반복 중앙값 | 1.552초 | 1.448초 |
| 첫 파일 조회 요청 → HTTP 도착, 두 반복 중앙값 | 1.974초 | 1.932초 |
| 긴 입력 요청 → HTTP 도착, 두 반복 중앙값 | 2.628초 | 2.371초 |

렌더링 전후 4,517줄의 최종 셀 해시는 동일했다. 긴 검색의 전체 작업 시간은
약 422~425ms에서 382~399ms이고, 출력 표시는 작업 완료까지 기다리지 않게 됐다.
분할 준비 중 렌더 대기 슬롯 최고 사용은 2개로, 기존 상한 4개를 유지했다.

큰 실행 메타데이터(180개 Tool 정의)를 사용한 별도 표시 투영에서는 중앙값
약 16ms가 약 0.003ms로 줄었다. 이는 실행 설정 복사를 없앤 합성 사례의 결과이며,
모든 실제 요청에서 16ms가 절약된다는 의미는 아니다.

가벼운 요청의 호출 준비 시간이 크게 개선되었다고 볼 근거는 없다. 최종 첫 인사의
접수 확인은 약 0.197초, Run 시작 통지는 0.403초, 첫 HTTP 도착은 1.420초였다.
그 전에 fsync 4회의 개별 소요 시간 합은 약 0.276초였다. 공개 조회와 실행 준비는 겹쳐 진행되므로
개별 호출 시간을 더해서 나머지 비용을 설명할 수 없다. 첫 모델 호출 전 최신 Run
목록·대화 조회와 backend 준비 구간의 경합은 여전히 추가 검토 후보다.

첫 인사의 화면 조회 취소는 반복당 2회에서 0회로 줄었지만, 저장·실행 계약에 필요한
작업을 생략하지 않았다. 첫 답변 표시 시간은 일부 시나리오에서 오히려 늘었으며,
샘플 수가 작아 작은 차이를 확정적인 개선/회귀로 주장하지 않는다. 1초 이내 준비를
보장하지 않는다. 이번 변경의 뚜렷한 효과는 긴 이력 렌더링과 다른 화면 준비가
겹쳤을 때의 응답성이다.
