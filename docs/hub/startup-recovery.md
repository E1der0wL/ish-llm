# Hub 시작 로딩과 명시적 복구

## 시작 로딩 팝업

백엔드 첫 연결을 시작할 때 맞춤형 크기의 `HUB 로딩` 팝업을 표시한다. 공통 팝업의
실제 내용 크기 계산을 사용하며 터미널보다 커지지 않는다. 중앙에 HUB ASCII 아트,
Rich 진행 바, 단계와 퍼센트를 표시한다. 퍼센트는 백엔드가 보고한 현재 단계의
완료 수/전체 수이며 전체 수를 모르는 단계는 `—%`와 진행 중 바를 사용한다.
시간 경과를 완료율로 꾸미지 않는다.

버튼은 재시도·초기화·최소화다. 로딩 중에는 앞의 두 버튼을 비활성화하고 키보드와
마우스 실행을 모두 막는다. 실패하면 ASCII 아트·진행 바·단계/퍼센트 표시를 모두 숨기고
같은 자리에 원인·대상·복구 안내를 왼쪽 정렬로 표시하며 안전한 복구 경로만 활성화된다.
실패 상태에서는 최하단 상태 내용도 표시하지 않는다. 재시도 중에는 중앙 정렬된 로딩
화면으로 돌아간다. 버튼 위·아래 공백 한 줄과 최하단 상태 한 줄은 공통 팝업이
소유한다. 시작 진행 상황은 별도의 진행 모델을 사용하여 홈 하단에 중복 표시하지 않는다.

팝업이 있는 동안 홈 조작과 일반 재시작을 막고 최소화는 허용한다. 최소화는 작업을
취소하지 않으며 다시 열면 같은 진행 상태를 보여준다. 최초 화면 자료가 준비되면
팝업을 닫는다. 일반 작업의 진행 바·팝업 상태 경로는 유지한다.

홈 프로젝트 카테고리의 편집 버튼과 같은 `e` 동작은 선택 프로젝트의 **프로젝트 · 일반**
설정으로 이동한다. 새 이름을 묻는 팝업을 만들지 않으며, 이름 변경은 기존 프로젝트 제목
설정·저장 경로를 사용한다. 프로젝트 생성·복제·삭제 동작은 유지한다.

## 실패 대상과 복구 소유권

| 실패 경로 | 안내·처리 |
|---|---|
| Hub preferences/sidebar-width JSON 및 필드 검증 | 실패한 파일을 명시한다. 사용자가 선택하면 그 파일만 백업 후 초기화한다. |
| 최초 프로젝트 생성에 쓰는 프리셋 JSON/선택 기록 | 실패한 정의 또는 선택 파일을 명시한다. 선택 기록만 초기화하면 다른 프리셋은 보존한다. |
| 설치된 기본 스킬·프롬프트 파일 누락/문법 문제 | 설치 원본 경로와 원인을 표시하고 재설치 후 재시도를 안내한다. 없는 원본을 설정 초기화로 복원하지 않는다. |
| Provider 준비·Engine/Component 구성·저장소 연결 | 원래 오류와 대상을 표시한다. 경로/권한/의존성/잠금 문제 해결 후 수동 재시도한다. |
| Project/Session/컴포넌트의 저장 자료 검증·실행 기록 읽기 | 기존 공개 API의 오류를 보존한다. Hub가 백엔드 디렉터리나 manifest를 직접 지우지 않는다. |
| 실패 후 자원 정리도 실패 | 재시도·초기화를 제공하지 않고 ish 종료 후 확인을 안내한다. 두 오류를 진단에 보존한다. |

`StartupFailure`는 기존 `ErrorInfo`에 시작 단계·대상·소유자가 제공한 복구 동작을 붙이는
UI 관찰값이다. 백엔드 오류 분류, 재시도 정책, 승인 또는 체크포인트 집행을 대체하지 않는다.
일반적인 “로그 확인” 안내 대신 팝업에서 원인 문구를 읽을 수 있으며 원래 traceback은
기존 조작 진단 경로에 보존한다.

## 초기 설정과 기본 자산

설정 파일을 읽지 못해도 기본 모양으로 오류 화면을 만들 수 있다. 이때 기본값은 복구 UI에만
사용한다. 설정을 자동으로 보충·저장하거나 새 backend/Project를 열지 않는다. 사용자가
문제를 고친 뒤 재시도하거나 백업·초기화를 명시해야 정상 시작 절차로 돌아간다.

기본 스킬은 이름이 명시된 Hub 생성 자산이다. UI import 때 디렉터리를 탐색하거나 모든
`SKILL.md`를 읽지 않는다. 새 프로젝트를 저장하기 전에 실제 기본 스킬 파일을 검사하며,
기존 프로젝트를 열 때 기본 스킬이나 사용자 설정을 다시 주입하지 않는다. 등록 중 오류는
해당 원본 경로와 함께 전달하며 기존 생성 실패 롤백을 유지한다.

## 백업과 초기화

- 설정 소유자가 지정한 `.hub` 파일만 대상이며 오류 메시지의 경로를 삭제 대상으로 사용하지 않는다.
- 별도 확인 창에서 초기화 범위와 백업 위치를 안내한다. 프로젝트·세션 초기화 기능이 아니다.
- 파일이 읽을 수 있는 일반 파일인지, 심볼릭 링크를 따라가지 않는지 확인한다.
- 실패 시점과 초기화 시점의 내용 해시가 다르면 초기화를 거절한다.
- `.hub/recovery-backups/<UTC시각-임의ID>/`로 원본을 원자적으로 옮기고 원래 경로·해시를
  manifest에 기록한다. 백업은 원래 내용을 보존하고 비밀 값이 포함될 수 있어 접근 권한을 제한한다.
- 이동 중 내용이 바뀌면 기존 값을 덮어쓰지 않는 방식으로 복원을 시도하며 백업도 보존한다.
- 파일 부재에 대한 기존 소유자의 초기값을 사용한다. 자동 마이그레이션·옛 필드 호환 코드는 없다.

시작 실패한 worker는 먼저 공개 종료 경로로 backend·구독·자원을 정리한다. 재시도는 사용자가
선택했을 때 설치를 다시 시작하는 동작이며, 실패 Run의 자동 재실행이나 승인·체크포인트 우회가
아니다. 정상 재시작의 중단/정리 동작과 첫 연결 실패의 정리는 구분한다.

백엔드는 손상된 Skill 카탈로그 등의 **부분 원본 백업·초기화** API를 제공하지 않는다.
Project backup도 원본 검증을 요구하므로 손상된 자료에는 실패할 수 있다. 이 범위까지
지원하려면 백엔드 소유자의 명시적 백업·수선 계약이 필요하며 이번 작업에서 `llm/`은 변경하지 않는다.

## 확인 상태

2026-11-05 실제 PTK 화면을 확인하고 사용자가 UI를 확정했다. Linux Python 3.12.14와
해시를 기록한 Linux 소스 사본에서 집중 검사와 전체 Hub 회귀를 실행했다. 실제 사용자
워크스페이스·클립보드·모델 API는 사용하지 않았다. 초기 파일 손상·백업 실패·동시 변경·심볼릭 링크,
기본 스킬 누락의 생성 전 실패, 시작 실패 자원 정리, 재시작·정상 설정 로딩과 프로젝트 이동을 검증했다.
보고서는 `tests/hub/reports/startup-recovery-20261105/`에 보존하며 최초 실패 결과도 삭제하지 않는다.

- `focused-02`: 30/30 통과. 시작 팝업·홈 편집·격리 X11 클립보드 포함.
- `focused-03`: 11/11 통과. 실제 ish 호스트의 초기화 확인 → 원본 백업 → 재설치 → 연결과 셸 입력 보존 포함.
- `full-01`: 전체 1,134개 실행, 1,129개 통과·오류 5개. 누락·중복·skip 0개, 2,808초.
- 전체 검사에서 이전 프로젝트 이름 변경 팝업을 기대하던 마우스 검사와 로딩 중 설정
  단축키를 보내던 두 검사를 현행 UI에 맞췄다. 전역 설정 검사는 별도 사용량 조회의
  완료도 기다리도록 했다. `focused-04`의 마우스 검사, `focused-05`의 설정 검사,
  최종 `focused-06` 6/6 통과로 재검증했다. 구현 코드에는 추가 변경이 없다.
- 자동완성 검사에서는 RAG 팝업의 후보 표시를 기다리다 한 차례 시간 초과가 발생했다.
  해당 코드·기한을 바꾸지 않은 `focused-04`·`focused-05`·`focused-06`에서 모두 통과했다.
  최초 시간 초과의 원인은 확정하지 않았으며 재현되지 않은 결과로 기록한다.
- 아래 백엔드 오류는 `full-01`과 `focused-04`에서 동일하게 재현됐다. 따라서 이번
  **전체 회귀를 전부 통과했다고 보고하지 않는다.** 실패 검사를 제외하거나 성공으로 바꾸지 않았다.

### 백엔드 작업자에게 전달할 조회 오류

`tests.hub.test_tool_advice.ToolAdviceTests.test_policy_approved_queued_resume_does_not_report_snapshot_error`
에서 자동 승인 응답과 재개 요청은 저장되었지만 새 Run이 아직 생성되지 않은 시점을 고정한다.
이때 Hub의 `snapshot()` → 공개 `run.ainteraction_views()` 조회가 실패한다.

```text
llm/services/runtime/interactions.py:424
else RunStatus.QUEUED.value if resume_message else self.NO_RESUME
AttributeError: type object 'RunStatus' has no attribute 'QUEUED'
```

`llm/core/models.py`의 `RunStatus`에는 QUEUED가 없고, 이 구간은 아직 Message의 예약
단계다. 재개 요청과 생성된 Run을 구분하여 공개 InteractionView에 어떤 상태를 반환할지는
백엔드가 수정해야 한다. Hub가 상태를 조작하거나 오류를 잡아서 승인 요청이 없다고
간주하는 우회 처리는 넣지 않았다. `llm/`은 변경하지 않았다.

수정 후 기대 결과는 같은 테스트에서 예약 중 snapshot 조회가 성공하고, 해결된 승인
질문이 다시 노출되지 않으며, 예약 해제 후 원래 도구가 한 번 실행되고 답변이 완료되는 것이다.
Linux Python 3.12.14의 격리 소스에서 아래 공개 검사 진입점으로 재현할 수 있다.

```sh
.venv-linux312/bin/python -m unittest -v \
  tests.hub.test_tool_advice.ToolAdviceTests.test_policy_approved_queued_resume_does_not_report_snapshot_error
```
