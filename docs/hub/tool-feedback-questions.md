# Tool 실패 피드백과 영속 질문

기준 계약은 [llm Tool 결과 처리와 질문](../llm/tool-feedback.md)이다.
llm은 검증·저장·승인·재개·전달 접수를 소유한다. Hub는 생성 프리셋과 표시,
질문 방식, 사용자가 선택한 답변 전달 시점만 소유한다.

## 생성 프리셋과 실패

새 프로젝트의 사용자용 Loop 등록에는 `parameters.engines[등록 이름].policy.tool_feedback`에
`failure: true`, `declined: true`, `remaining_calls: "defer"`를 기록한다.
명시한 사용자 값이 우선하며 기존 프로젝트를 열 때는 재주입하지 않는다.
설정의 Loop 정책에서 세 항목을 바꿀 수 있다. `continue`는 아직 실행하지 않은 독립 호출을
계속하는 명시적 선택이며, Tool 자체 재시도 정책과 다르다.

백엔드가 효과 없음으로 확인한 실패만 모델에게 피드백된다. 실패한 Step은 그대로 남는다.
Step 실패만으로 Run 전체를 실패로 바꾸지 않는다. 일반 `PermissionError`, 저장 오류,
효과가 불확실한 실패를 Hub가 잡아서 정상 Tool 결과로 변환하지 않는다.
이런 Tool까지 모델이 다루려면 Tool 소유자가 공개 no-effect 오류 계약을 제공해야 한다.
Hub 프롬프트는 실패 결과를 읽고 다른 허용된 방법·질문·설명을 선택하도록 안내한다.
사용자 거절의 우회, 같은 동작 재요청, 완료된 작업 재실행을 지시하지 않는다.

## 승인 거절과 중단

승인 폼은 **승인·비슷한 요청 승인·거절**을 표시한다. 비슷한 요청 승인은 조건 확인 창에서
동일 작업 또는 지원되는 명령 범위와 세션/프로젝트 범위를 명시적으로 선택한다.
기억 규칙을 지원하지 않는 승인에는 비슷한 요청 승인을 표시하지 않는다.
거절은 거절 응답을 저장한 뒤 공개 interaction view와 `resume_plan`을 확인하고,
`resume_on_denial` 등 백엔드 조건이 허용할 때 명시적으로 `resume()`한다.
불확실한 효과를 다시 실행하는 노드는 자동 선택하지 않는다.
중단은 기존 입력창 보조 버튼과 Ctrl+D를 사용하며 승인 폼에는 중단 선택지를 추가하지 않는다.
중단 요청은 재개하지 않는다. 응답 저장 성공과 재개 성공은 별도로 표시한다.

## 질문과 답변

`QuestionTool`이 동일한 질문 스키마를 사용해 `QuestionHandler`를 두 번 등록한다.
등록 시 mode와 revision을 명시한다.

| Tool | 실행 방식 | UI |
|---|---|---|
| `ask_user` | blocking, PAUSED와 체크포인트 | 기존 질문 입력창. 저장 후 명시적 재개 |
| `ask_user_async` | nonblocking, 작업 계속 | 같은 입력창에서 질문·답변 표시, 일반 입력으로 전환 가능 |

비차단 질문은 별도 팝업 없이 기존 입력창에 표시한다. 질문이 여러 개면 제목 옆의
**이전 아이콘 · 현재/전체 · 다음 아이콘**으로 이동한다. 첫 질문과 마지막 질문에서는 목록을 순환하지 않는다.
질문 전환과 화면 갱신에도 선택과 답변 초안을 유지한다.
**나중에 답변**으로 돌아가면 기존 일반 초안이 복원되며 질문별 답변 초안도 유지한다.
홈 보조 버튼의 `?`/`` 또는 질문 안내의 답변 버튼으로 다시 표시한다.
재접속 시 실행 중·일시 정지한 원래 Run의 질문을 `run.aquestions()`로 조회한다.
질문 목록 열기도 활성/일시 정지 Run과 이미 표시한 원본 Run만 재조회하며 전체 실행 이력을
읽지 않는다. 질문·답변의 원본은 llm이고 UI는 초안·선택·포커스만 보관한다.
질문 Tool의 Future나 별도 영속 질문 저장소를 만들지 않는다.

Enter 또는 **답변 전송**은 답변 저장 후 원래 Run의 공개 전달 대상을 조회한다.
동일 Run의 accepting/consume 대상이 하나면 그 대상으로 명시적으로 전달한다.
여러 개면 입력창 안에서 대상을 선택하고 **답변 전송**으로 확정한다.
Graph도 공개 `ainstruction_targets()`를 사용하며 임의 노드·다른 Run·전체 노드로 방송하지 않는다.
조회 실패나 일시적 수신 불가는 종료로 단정하지 않는다. 원래 Run이 completed/interrupted/
cancelled/failed임을 공개 상태에서 확인하면 질문 입력을 닫고 일반 입력창으로 돌아간다.
PAUSED는 답변 후 명시적으로 재개할 수 있으므로 질문 입력을 유지한다.
질문 입력을 닫아도 질문·답변 기록을 취소하거나 삭제하지 않으며, 늦게 도착한 저장/전달
결과로 종료한 질문을 다시 열지 않는다. 이후 답변은 사용자가 일반 메시지로 직접 보낸다.
작성 중인 답변은 질문 제목과 함께 일반 초안으로 옮긴다. 이미 다른 입력이 있으면 덮어쓰지
않고 기존 입력 히스토리에 보관한다. 빈 일반 입력창에서 ↑로 다시 불러올 수 있다.
버튼은 **답변 전송·나중에 답변**뿐이며 더 보기·저장만 하기·새 요청·질문 취소 메뉴는 없다.
저장된 답변은 수정하지 않는다. 답변 저장과 전달은 별도 API이며 저장만으로 실행되지 않는다.
처음 질문을 표시할 때는 입력창에 포커스를 둔다(열린 팝업·설정 화면의 포커스는 빼앗지 않는다).
입력창의 Tab은 이전/다음 버튼 영역으로 이동한다. 그 영역의 ←/→는 바로 질문을 바꾸고
Tab/Space/Enter는 입력창으로 돌아간다. 마우스로 이전·다음을 클릭할 수도 있다.
이전·다음 아이콘 버튼은 클릭 전용으로 포커스를 받지 않으며 번호 영역이 키보드 포커스를
받는다. 번호의 배경은 질문 헤더와 동일하고 영역 포커스 시 번호 글자만 강조 색 2로 바뀐다.
질문 번호는 버튼이 아닌 위치 표시다. 답변 전송·나중에 답변 버튼은 기존 Ctrl+S로 접근하며
해당 실행 버튼 줄과 Graph 대상 선택의 명시적 전달 조작은 유지한다.
추천 선택지, 무응답, 시간이 지난 사실을 사용자 답변으로 사용하지 않는다.

`aanswer_question()`과 `deliver_answer()`를 분리한다. `get_delivery()`로 저장된 접수
영수증을 조회하며 접수를 반영 완료로 표시하지 않는다. 실제 반영은 기존 추가 지시·요청
상태로 관찰한다. 질문 revision별 중복 방지는 백엔드 intake가 집행한다.
플러그인용 `acancel_question()`은 미응답 질문만 취소하며 승인 취소 API와 구분한다.
플러그인 공개 API의 명시적 저장·취소·submit 전달 기능은 유지하고 홈 질문 UI만 단순화한다.

플러그인 API도 같은 영속 경로를 사용한다. blocking 질문은 `respond` → `resume_plan` →
`resume`, nonblocking 질문은 `questions` → `answer_question` → 명시적 `deliver_answer`이다.
옛 live Future 전용 `answer_live`/`live_questions` 경로를 유지하지 않는다.

## 확인 상태

승인 입력창은 Tool 이름을 강조 색 1, 위험도를 강조 색 3, 인자·설명은 주석 색 1로
표시한다. 상세 설명·전체 인자는 최대 4줄 높이의 테두리 없는 읽기 전용 텍스트 영역으로 보여준다.
전체 내용 조립은 백엔드 읽기 작업, 줄 렌더링은 기존 렌더 worker에서 수행한다.
입력창에 포커스를 유지하며 Alt+이동키와 상세 영역 마우스 휠로 스크롤한다.
Ctrl+O 상세 팝업과 키는 제거했으며 번호 입력 즉시 승인·조건 확인·거절을 선택한다.
위험도는 상세 내용 스크롤과 분리해 승인 선택지 바로 위에 고정하며 본문에는 중복 표시하지 않는다.
하단은 번호 선택·스크롤·승인 관리 안내 한 줄이다. UI 단순화는 저장·전달 API를 합치거나
승인·재개 권한을 변경하지 않는다. 차단 질문의 나중에 답변은 PAUSED를 자동 재개하지 않는다.

Memory의 새 실패 처리 계약에 따라 STEP_HANDLED 이벤트에서도 Step 관찰 캐시를
무효화한다. 실패 상태를 성공으로 바꾸지 않고 백엔드에 저장된 처리 근거를 다시 읽는다.
continue의 좁아진 범위는 설정 도움말과 기본값 문서에 반영했다.

MCP의 새 연결·인증·권한·timeout·원격 실행 오류는 코드별 안내를 제공하되 재분류하거나
재시도 권한을 만들지 않는다. 기본 표준 connector와 명시적 발견·Agent 선택 UI는
[MCP 연결·Memory 처리](mcp-memory-integration.md)를 따른다. 생략/null/명시 timeout 계약을
유지한다. resources/templates 탐색·OAuth·서버 elicitation UI는 별도 범위다. 서버 질문은
영속 일반 질문으로 변환하거나 연결 종료 후 재개할 수 없다.

질문 UI는 사용자 확정 완료다. 실제 PTK 레이아웃에 예시 질문을 넣은 화면과, 격리 프로젝트의 공개
스키마로 만든 설정 화면을 캡처했다. 모델/API 호출과 사용자 workspace 변경은 하지 않았다.
MCP UI도 사용자 확정 완료이며 함께 검사한다. 확인 범위:

- no-effect 실패 후 모델 응답과 실패 Step 보존, 거절·중단·중복 실행 방지
- blocking 재개와 nonblocking 스트리밍/일반 입력 유지
- Run 종료 시 입력 닫기·기록 보존·초안 복원, 재접속 조회, 저장만으로 실행되지 않음
- 이전/다음 선택·초안 유지, 늦은 콜백과 질문 전환/종료 경합, 플러그인 답변/취소 경합
- 중복 전달·종료 대상·타 Session·잘못된 Graph 대상 거부
- 기존 승인·재개 집중 테스트 후 전체 Hub 회귀

질문 Tool은 파일/프로세스용 output·path scope wrapper에 넣지 않고 native
`QuestionHandler` 객체를 유지한다. 선택된 Tool과 binding revision은 그대로 보존한다.
이를 통해 일반 함수 호출이 아닌 백엔드의 resumable event 경로가 차단 질문의
체크포인트와 비차단 질문의 영속 발행을 소유한다.

## 2026-11-05 검증 결과

사용자 UI 확정 후 Linux Python 3.12.14와 해시 기록된 Linux 파일시스템 스냅샷으로
집중 검사와 Hub 전체 회귀를 실행했다. 실제 모델·MCP 서버 및 사용자 workspace를
사용하지 않았으며, X11 연동 검사는 별도 namespace의 Xvfb와 clipboard에서 실행했다.

- 질문·승인·플러그인 집중 검사: 75개 통과.
- MCP·Memory·Tool 실패 피드백·팝업 크기·클립보드 집중 검사: 51개 통과.
- Hub 전체 회귀: 1,122개 실행, 최초 결과 1,110개 통과·12개 실패, 건너뜀 없음.
- 발견한 항목을 수정한 뒤 관련 12개 모듈의 114개를 재검사했다. 113개 통과 후 남은
  질문 이벤트 테스트의 필수 Step ID 누락을 수정하고 해당 모듈 12개를 다시 통과했다.

현재 테스트 ID별 최신 결과는 모두 통과다. 이는 전체 실행과 수정 후 집중 재검사를
합친 결과이며, 최종 소스로 전체 검사를 한 번 더 실행했다는 뜻은 아니다.
전체 실행 후 제품 코드 변경은 기존 길이 예산을 유지하기 위한 기본 지침 축약이며,
관련 지침·요청 분류·프로젝트 생성·셸 환경 검사도 재검사에 포함했다.
그 외 실패는 새 공개 질문 계약과 Hub 생성 프리셋에 맞지 않던 테스트 자료·기대값을
수정했다. Tool retry 검사에서는 실패 피드백 정책을 명시하여 두 동작을 분리 검증한다.

집중 검사에서 발견한 native QuestionHandler 바인딩 손실도 수정했다. 질문을 일반
파일·출력 wrapper로 감싸지 않아 백엔드가 차단·비차단 질문의 실행 계약을 유지한다.
실패 Step·완료 Run의 공존, 저장과 전달 분리, 재개·승인·중복 실행 방지 검사가 통과했다.

실행 로그·테스트 ID별 결과·스냅샷 해시는 로컬 검증 자료
`tests/hub/reports/durable-questions-20261105/`에 보관한다. `llm/` 전체 회귀는 별도로
실행하지 않았으며, 해당 폴더의 작업 전 파일 406개는 해시 비교로 변경 없음을 확인했다.
