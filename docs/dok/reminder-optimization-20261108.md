# 알림 등록 UI와 표시 수요별 최적화

사용자 요청에 따라 `dok/`, `docs/dok`, `tests/dok` 범위에 구현했다. ish 본체·llm·hub, 개인 WSL 설치본과 설정, Windows Terminal 설정은 변경하지 않았다. 이전 입력 폭주 진단과 이번 최적화는 별개다.

## UI 확인 단계

실제 CalendarPage/PopupSurface 렌더러와 합성 일정으로 PNG를 생성했다. 개인 일정 파일·실제 알림 실행·날씨 네트워크 요청은 사용하지 않았다. 사용자가 좌우 여백을 적용한 네 번째 시안을 확정한 뒤 테스트를 실행했다. 확정 이후 UI 모양은 바꾸지 않았다.

- [일정 영역 안쪽 여백과 3행 목록](../../tests/dok/reports/reminder-ui-20261108-v4/reminders-minutes.png)
- [일정 시작 시간 선택과 비활성 숫자](../../tests/dok/reports/reminder-ui-20261108-v4/reminders-start.png)
- [알림 단위 드롭다운](../../tests/dok/reports/reminder-ui-20261108-v4/reminders-dropdown.png)
- [아래로 스크롤한 목록](../../tests/dok/reports/reminder-ui-20261108-v4/reminders-scrolled.png)

후속 요청으로 등록 행 아래 빈 줄 한 줄, 3행 목록의 배경·스크롤 위치 표시, 목록 위 휠 처리와 PageUp/PageDown 이동을 반영했다. 오늘 날짜는 달력 상단 오른쪽에 YYYY-MM-DD 전체 숫자로 표시한다. 첫 번째 미리보기 파일은 수정하지 않고 이전 상태로 보존했다.

세 번째 시안에서는 스크롤바의 세로 레일 선을 지우고 현재 위치 블록만 유지했다. 앞선 시안 파일들은 그대로 보존했다.

네 번째 시안은 일정 영역 배경을 전체 너비로 유지하면서 내부 위젯·라벨·구분선에 좌우 한 칸씩 여백을 추가했다. 알림의 선택 표시용 앞 두 칸은 유지한다. 드롭다운 기준점과 목록 휠 영역에도 동일한 여백을 반영했다.

수동 미리보기 스크립트는 `tests/dok/manual/calendar_reminders_preview.py`다. 테스트 자동 탐색과 배포에 포함하지 않는다.

## 적용 내용

| 상태 | 동작 |
| --- | --- |
| 다음 알림이 있음 | 실제 알림 시각에 맞춰 대기. 반복·여러 사전 알림을 개별 처리 |
| 대기할 알림이 없음 | 매초 시계 확인 중단. 외부 파일 변경 확인만 유지 |
| 캘린더 닫힘 | 외부 파일 확인 기본 30초. 알려진 알림 기한은 유지 |
| 캘린더 열림 | 외부 파일 확인 기본 1초. 열기·저장·삭제 시 즉시 계획 확인 |
| 미래 알림 대기 중 시간 변경 | 기본 1초의 가벼운 시계 확인. 이때 파일 조회·전체 일정 순회 없음 |
| 일반 팝업 포커스 | dock의 audio/media 수집 중지. 팝업에 필요한 날씨·시계와 예약 알림 유지 |
| dock 숨김 또는 일반 팝업 포커스 | 하단 시스템 수집 기본 3초. 펼친 dock에서는 1초로 복원 |
| 측정 간격 전환 | 카운터 기준값·그래프 이력·작업 유지. 실제 경과 시간으로 전송률 계산 |
| 같은 화면 다시 그리기 | 마지막 월 달력 행·날씨 그래프 재사용. 날짜·데이터·크기·스타일 관련 입력 변경 시 다시 생성 |

외부 일정 파일은 수정 시각이나 크기만 믿지 않고 기존과 같이 잠금 안에서 실제 내용을 확인한다. 다음 알림 계획은 Store에 한 건만 유지하며 일정·처리 기록·시계 역행·시간대 해석 환경·알림 활성 상태가 바뀌면 다시 계산한다. 소스와 알림 기록이 같은 경우만 재사용한다.

기존 단일 알림 일정은 v1 읽기 경로로 보존한다. 저장할 때 v2의 복수 상대 알림 형식을 사용하며 이미 처리한 회차 기록을 유지한다. 중복 방지를 위한 기록 선행 저장, 프로세스 간 잠금, 원자적 파일 교체와 실패 시 재시도 계약은 유지한다. 기존 설정 이름의 별칭·자동 설정 변환은 추가하지 않았다.

상세 설정과 사용법은 [캘린더](calendar.md), [하단 바](toolbar.md), [기본 설정](config.example.jsonc)에 있다. 날씨 API 요청을 요약·상세로 분리하는 변경은 이번 범위에 포함하지 않았다. 기존 성공 캐시·갱신 주기·재시도 규칙을 유지한다.

## 확정 후 검증 결과

Linux Python 3.12.14와 해시 검증된 Linux 파일시스템 스냅샷에서 **dok 테스트 296개 전부 통과**했다. 실행기 기준 63.550초, unittest 기준 62.343초이며 건너뛴 검사는 없다. [전체 로그](../../tests/dok/reports/dok-t73cabsb/dok.txt), [소스 해시](../../tests/dok/reports/dok-t73cabsb/snapshot.json), [실행 결과](../../tests/dok/reports/dok-t73cabsb/results.json).

등록·삭제·동일 시각 중복·시작 시간 선택 시 숫자 무효화, 여러 알림의 저장·재시작·처리 기록, 반복·DST·시계 변경, 알림 없는 동안의 파일 조회 억제, 저장 후 즉시 깨우기, 외부 수정 감지, 유휴 수집 간격·CPU/NET 기준값·그래프 이력 보존, 일반 팝업 중 수집 중지와 복원, 3행 목록·휠·키보드·좁은 화면을 확인했다. 기존 기본 JSONC·Owner/schema 일치 검사도 통과했다.

ESC 입력 파이프 응답은 **106.2ms**, 실제 PTY 합성 입력은 캘린더 **112.4ms**, 날씨 **114.9ms**였다. 사용자 Windows Terminal의 실제 물리 마우스 동작을 재현한 측정은 아니며 이전 입력 폭주 문제의 해결을 의미하지 않는다.

첫 실행은 알림 종료 대기에서 멈췄다. 반복 진단에서 타이머 만료의 내부 취소와 종료 요청이 겹치면 TaskSlot이 이미 취소 중인 작업으로 보고 추가 취소를 생략하고, 실행기는 타이머 만료를 처리한 뒤 다시 대기하는 상황을 확인했다. CalendarRuntime이 Owner의 종료·활성 설정 키를 직접 확인하고 종료·설정 변경 시 대기도 깨우도록 수정했다. SystemRuntime도 종료 직후 추가 수집을 하지 않도록 같은 수명 규칙을 적용했다. 만료 순간 종료·비활성화가 겹치도록 만든 회귀 검사가 통과했다. [초기 실행](../../tests/dok/reports/dok-dm7iuhy3/dok.txt), [작업 스택 진단](../../tests/dok/reports/dok-dm7iuhy3/shutdown-diagnostic.txt).

두 번째 실행의 UI 검사 3개는 목록 외 드롭다운 문구까지 집계하거나 달력의 날짜 숫자를 입력 값으로 선택했다. 검사 대상을 등록 행·삭제 버튼이 있는 목록 행으로 한정했으며 제품의 확정된 화면은 그대로 유지했다. [중간 실패 기록](../../tests/dok/reports/dok-rf54y013/dok.txt).

선택적 Hub 연결 검사도 최종 전체 실행에 포함했다. 의존성은 커밋 `d775c5d009fdd08988278da207b1c93a7a759ac9`의 llm/hub 소스를 별도 임시 폴더에 읽기 전용 입력으로 복사해 제공했다. [의존성 해시](../../tests/dok/reports/dok-rf54y013/optional-dependencies.json). llm/hub 전체 회귀 테스트, ish 본체·llm·hub 코드 수정, 개인 WSL 설치본·설정·일정 변경, Git 커밋·업로드는 하지 않았다.
