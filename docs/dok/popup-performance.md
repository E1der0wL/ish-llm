# 일반 팝업 마우스와 성능 검토 (2026-11-07)

일반 팝업의 포커스 상태는 `PopupHost.modal`이 소유한다. 컨트롤러는 이 공개 상태와 `MouseConfig.enabled`를 조합하고, 기존 `DockMouse`가 호스트 필터·클릭 범위·복원을 처리한다. 별도 플래그나 개인 설정 변경 없이 일반 팝업에서 마우스를 켜며, 작은 알림과 독은 기존 설정을 따른다. 시간 범위 아이콘은 `CalendarPage.TIME_ARROW`에 한 번 선언한다.

Linux Python 3.12.14에서 dok 테스트 **252개 통과**(61.407초). 마우스 설정이 꺼진 상태의 일반·캘린더·날씨 팝업, 마우스로 일정 입력·저장·닫기, 팝업 밖 클릭 차단, 기존 호스트 마우스 활성 상태 보존, 알림과 외부 UI 포커스, 좁은 화면과 아이콘 폭을 확인했다. ESC는 pipe 104.7ms, 실제 PTY의 캘린더 116.0ms·날씨 112.1ms였다. [테스트 로그](../../tests/dok/reports/dok-mdg0ov2h/dok.txt), [소스 해시](../../tests/dok/reports/dok-mdg0ov2h/snapshot.json).

이후 팝업 설정 항목의 영문 설명까지 새 정책으로 맞추고 Owner에서 기본 JSONC를 재생성했다. 설명 수정 후 [설정 테스트 34개](../../tests/dok/reports/dok-mdg0ov2h/settings-followup.txt)를 추가 실행해 모두 통과했다. 런타임 로직은 전체 테스트 이후 변경하지 않았다.

## 측정 결과

실제 `CalendarPage.draw_body()`를 사용한 합성 일정 측정이다. 저장소·네트워크·개인 일정은 사용하지 않았다. 매주 반복하는 일정, 2026년 11월, 캐시 예열 후 3회 중앙값이다. 전체 터미널 렌더링 시간이 아닌 **달력 본문을 만드는 시간**이며, 환경과 일정 구성에 따라 달라진다. 프로파일링을 켠 실행은 시간 중앙값에 포함하지 않았다.

| 반복 일정 수 | 넓은 화면 132칸 | 좁은 편집 화면 35칸 |
| --- | ---: | ---: |
| 0 | 9.2ms | 5.2ms |
| 25 | 210.1ms | 230.7ms |
| 100 | 858.4ms | 854.9ms |

모든 경우 날짜 30개에 `CalendarSnapshot.on_day()`를 **151번** 호출했다. 월의 각 날짜를 숫자 1행과 일정 4행에서 반복 조회하고, 편집 영역에서도 선택 날짜를 조회한다. 100개 일정의 넓은 화면 프로파일에서 일별 조회가 누적 렌더링 시간의 약 98%를 차지했다. 이 비율은 프로파일링 오버헤드가 포함된 진단값이다.

[측정 원본 및 소스 해시](../../tests/dok/reports/dok-mdg0ov2h/calendar-performance.json). 재현 스크립트는 `tests/dok/manual/calendar_performance.py`이며 자동 테스트 탐색에 들어가지 않는다.

## 권장 순서 — 아직 적용하지 않음

1. **같은 화면의 일별 조회 결과 재사용.** 우선 한 번 그리는 동안 같은 날짜는 한 번만 조회한다. 반복 일정 해석은 계속 `CalendarEvent`와 `CalendarSnapshot`의 공개 API에 맡긴다. 이후 필요하면 조회 Owner에 범위 조회 API와 현재 월 하나에 한정한 캐시를 두고 일정 변경·조회 월 변경 시 갱신한다. UI에 반복 규칙을 복제하거나 무제한 캐시를 만들지 않는다.
2. **숨겨진 영역 생성 생략.** 현재 좁은 화면에서 편집 영역만 보여도 월 전체를 계산한다. 표시할 영역만 만들되 드롭다운 좌표·포커스·편집 중 입력과 화면 확대 복원을 함께 검증한다.
3. **알림 저장소 폴링은 별도 측정 후 판단.** `CalendarRuntime`은 설정된 주기마다 저장소를 읽지만 내용이 같으면 화면을 무효화하지 않으며 I/O도 작업 스레드로 분리되어 있다. 디스크 조회 최적화가 필요하면 `CalendarStore`가 변경 감지와 알림 기한을 소유하도록 해야 한다. 파일 변경·다중 프로세스·알림 처리 기록을 보존해야 하므로 이번에는 변경하지 않았다.

이번 구현은 마우스 정책과 화살표만 바꿨다. 최적화는 탐색·측정 단계이며 ish 본체·llm·hub 수정과 llm/hub 전체 회귀 테스트는 수행하지 않았다.

## 반복 조회 최적화 적용 (2026-11-07)

후속 요청으로 위 개선 사항을 적용했다. 앞의 수치는 최초 검토 기록이며 이 절이 적용 후 상태다.

- 월 화면에서 같은 날짜를 행마다 다시 조회하지 않는다. CalendarSnapshot은 현재 조회 월만 캐시하고, 날짜 조회 결과는 재렌더링에도 재사용한다. 월·일정·시스템 시간 해석 환경이 바뀌면 다시 계산한다.
- 좁은 편집 화면에서는 숨겨진 월 달력을 계산하지 않는다. 편집 초안이 있으면 쓰지 않는 미리보기 일정도 조회하지 않는다.
- CalendarStore는 잠금 아래 파일 내용 확인을 유지하되 동일한 내용의 JSON을 다시 해석하지 않는다. 알림 기록 복사·원자적 저장·외부 수정 감지를 보존한다. CalendarRuntime은 변경 없는 스냅샷 교체와 화면 갱신을 생략한다.
- 날씨 상세는 한 번 그리는 동안 스냅샷과 일별 예보를 한 번씩 가져온다. 상태 안내만 필요할 때 전체 PopupContent를 다시 만들지 않으며, 시간별 예보가 바뀐 경우에만 선택 시각을 재탐색한다.
- 일반 팝업 렌더러는 InteractivePopup이 사용하지 않는 일반 텍스트 본문 줄바꿈을 생략한다.

시스템 사용률과 재생 위치의 정기 조회, 날씨 갱신 주기, 일정 파일의 외부 변경 확인 및 알림 기한 확인은 최신 상태를 얻는 데 필요하므로 유지했다. 최적화는 내부 동작이며 사용자 설정이나 공개 호출 형식을 바꾸지 않는다.

동일한 Python·합성 일정·측정 스크립트로 변경 전후를 순서대로 측정했다. 아래는 반복 일정 **100개**, 예열 후 **5회 중앙값**이며 전체 터미널 반응 시간이 아닌 달력 본문 생성 시간이다.

| 조건 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 넓은 월 화면 재렌더링 | 769.9ms | 9.2ms |
| 좁은 편집 화면 재렌더링 | 777.4ms | 2.3ms |
| 넓은 월 화면 최초 렌더링, 1회 참고값 | 764.3ms | 156.7ms |

넓은 화면의 날짜 조회는 151회에서 30회로 줄고, 캐시가 채워진 뒤 실제 반복 일정 계산은 15,100회에서 0회가 됐다. 좁은 편집 화면은 날짜 조회 자체가 0회다. 새 월·새 데이터의 최초 계산 비용은 남아 있다. [변경 전 측정](../../tests/dok/reports/dok-tprjpbc4/calendar-before.json), [변경 후 측정](../../tests/dok/reports/dok-tprjpbc4/calendar-after.json).
