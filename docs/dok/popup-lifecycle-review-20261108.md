# 팝업 닫힘 후 입력과 숨김 상태 수집 검토

2026-11-08 검토만 수행했다. 제품 코드, ish 본체·llm·hub, WSL 설치본과 개인 설정은 변경하지 않았다. 진단 스크립트와 결과는 Git 제외 대상인 `tests/dok/manual`, `tests/dok/reports`에 두었다. llm/hub 전체 회귀 테스트는 실행하지 않았다.

## 사용자 관측과 현재 결론

아래의 초기 판단 뒤 개인 환경·실제 Windows Terminal 진단을 추가했다.
**현재는 실제 입력 먹통과 제어 입력 대량 유입을 기록으로 확인했으며,
Windows Terminal의 `experimental.repositionCursorWithMouse` 설정을 유력한
발생원으로 좁혔다. Shift 우회 비교에서는 증상과 새 방향키 CSI·`[` 입력이
사라졌다.** 마지막 절의 관측과 비교 결과를 우선한다.

처음에는 Alt+C/Alt+W 직후 ESC 닫기가 동작하지 않는다고 보고했지만 재시도에서는 빠르게 닫혔다. 이어 반복 조작 후, 주로 팝업을 닫고 마우스를 움직이거나 드래그할 때 키 입력·단축키가 반응하지 않는 현상이 보고됐다. 화면 갱신은 계속되고 때로 프롬프트에 `[`가 반복되며, 항상 대괄호가 먼저 나타나는 것은 아니다.

전체 이벤트 루프 정지나 일반적인 CPU 과부하로 단정하지 않는다. **팝업 종료 전후의 터미널 마우스 보고 상태와 입력 제어 문자열 처리**가 우선 조사 대상이다. 마우스 보고가 실제로 계속 유입되는지, 완성된 보고가 잘못 전달되는지, 일부가 분리되거나 입력 대기 타이머가 연장되는지는 실제 장애 시점의 기록이 필요하다. `[`를 무조건 무시하는 처리는 정상 사용자 입력을 훼손하므로 해결책으로 취급하지 않는다.

WSL 설정은 `dock.mouse.enabled: false`, `popups.input.escape_s: 0.05`였다. 관련 팝업·컨트롤러 코드도 작업 트리와 일치했다. 따라서 다른 호스트 기능이 마우스를 요구하지 않는다면 팝업 종료 후 마우스 보고가 해제되어야 한다. 현재 실행 중인 프로세스가 디스크와 같은 코드를 사용한다는 것까지 해시 비교로 증명되는 것은 아니다.

## 재현 범위와 한계

- Linux Python 3.12.14, 해시를 기록한 Linux 파일시스템 스냅샷을 사용했다. 개인 일정·설정은 테스트에 사용하지 않았다.
- 캘린더·날씨 열기와 ESC를 같은 입력 묶음 또는 0–200ms 간격으로 전달한 16가지 경우는 모두 닫혔다. 추가로 연속 ESC 입력 6가지도 닫혔다.
- 실제 설치된 ish 실행기를 별도 PTY·임시 홈에서 실행한 경우와 Hub를 함께 등록한 경우 각각 8가지도 닫혔다.
- 독·하단 바·Hub를 함께 둔 반복 시험은 캘린더 40회, 날씨 40회 모두 닫혔다. 닫힌 시점의 전체 asyncio 작업 수는 8–11개였고 입력으로 분류된 `[`는 0개였다. 장시간 누수나 실제 Windows Terminal에서의 문제 부재를 보장하는 결과는 아니다. 오디오·MPRIS와 실제 날씨 조회는 껐다.
- 닫힘 시 `1000l`, `1015l`, `1006l`, `1003l` 마우스 해제 출력이 관측됐다. 닫힌 뒤 완성된 SGR 이동·드래그·버튼 해제 보고를 넣었을 때 프롬프트는 비어 있었다.
- 반면 `ESC[I`·`ESC[O` 포커스 보고를 넣으면 프롬프트에 `[I[O`가 남았다. 이는 확인된 별도 제어 문자열 처리 경로다. 사용자 장애의 실제 패킷이 이 포커스 보고라는 증거는 없다.

## 권장 개선 순서

1. **닫힘 후 입력 문제를 별도로 추적한다.** 일반 텍스트를 저장하지 않고 종료 직전/직후의 모달·포커스, Application/Renderer 마우스 필터, 실제 보고 모드 출력, CSI 종류, 파서 flush와 키 대기 상태만 제한된 버퍼로 기록한다. 마우스 패킷 유입·파싱 문제와 터미널 자체 선택 처리를 구분한 뒤 소유 계층에서 수정한다. 단순 갱신 주기 변경을 입력 문제의 해결로 간주하지 않는다.
2. **팝업 뒤 독의 수집을 줄인다.** 비주얼라이저가 가려진 동안 PCM/FFT를 멈추거나 낮은 빈도로 전환하고, 재생 정보는 필요한 최소 상태만 유지한다. 오디오 앱 이름만 쓰는 경우에는 PCM 분석과 앱 조회를 분리할 수 있다. 표시 재개 시 최신 상태를 한 번 요청한다.
3. **숨김 상태의 일정 감시와 알림 기한을 분리한다.** 팝업이 닫혔을 때 외부 파일 변경 확인 간격은 늘릴 수 있지만 알림 시각을 함께 늦추면 안 된다. Calendar Owner가 다음 알림 기한을 계산하고, 외부 변경 감시·알림 기한·사용자 저장/삭제·재열기 중 가장 이른 시점에 깨우는 방식이 적절하다. 기존 잠금·충돌·알림 처리 기록과 시스템 시각 변경 처리를 보존한다.
4. **날씨 요약과 상세 자료의 수요를 나눈다.** 최대화 독은 필요한 일별 요약을 받고 시간별 자료는 상세 팝업을 열 때 요청하는 방안을 검토한다. 현재 기온까지 쓰는 화면, 재열기 캐시, 실패 재시도, 단일 진행 요청, 요약 캐시와 상세 캐시의 완전성 구분을 Weather Owner가 책임져야 한다. 조회 횟수와 응답량의 절충이므로 단순히 요청을 두 배로 나누지 않는다.
5. **하단 바와 팝업 표시를 별도로 줄인다.** 시스템 수집은 하단 바가 계속 보이므로 무조건 멈추지 않는다. 필요하면 숨김 상태의 주기를 2–3초 등으로 설정할 수 있게 하고, 변화 없는 표시 결과의 무효화·본문 생성은 생략한다. 그래프 이력은 매 측정마다 변할 수 있으므로 숫자가 같다는 이유만으로 갱신을 생략하지 않는다. 날짜만 있는 화면은 분 단위보다 다음 날짜 변경 시각을 사용할 수 있다.

표시 상태의 판단은 기존 PopupHost/DockState 계약을 사용하고, 각 기능 Owner가 수집 주기·재시도·캐시·상태 전이를 제공해야 한다. 렌더러가 저장 JSON이나 다른 기능의 내부 상태를 해석하지 않으며, 여러 계층에 동일한 숨김 규칙이나 기본 주기를 복제하지 않는다. 설정을 추가할 경우 schema·검증·생성 JSONC도 같은 선언을 사용한다.

## 개인 환경 그대로 추가 확인

사용자의 요청으로 실제 실행 중인 ish의 환경 변수·작업 폴더·터미널 크기
(225×65)를 읽어 별도 PTY에 적용했다. 실제 설치된 Python 3.12.14 / ish /
prompt-toolkit 3.0.53과 `~/ish/.ishrc.py`, 개인 `config.jsonc`, Hub·dok,
사용자 프롬프트 및 Git 조회를 그대로 로드했다. 오디오·MPRIS·날씨 설정을
덮어쓰지 않았다. 원래 실행 중인 터미널에는 입력을 보내지 않았다.

`tests/dok/manual/trace_current_input.py`가 관측을 연결하고,
`probe_current_input.py`가 별도 PTY에서 ESC, 이동·드래그·버튼 해제 보고,
명령을 제출하지 않는 한 글자 입력을 보냈다. 개인 시작 설정·dok 설정·일정
파일은 시험 전후 SHA-256이 일치했다.

이 환경에서는 **마우스 필터가 꺼진 뒤에도 도착한 SGR 버튼 해제가 자동완성
메뉴를 선택하는 경로**가 재현됐다. 추가 관측 실행의 세 번째 팝업 종료 뒤
프롬프트가 1글자에서 7글자로 바뀌었고, 호출 경로는
`mouse.py → containers.mouse_handler → menus.mouse_handler →
buffer.go_to_completion → buffer.set_document`였다. 해당 시점의 Application과
Renderer 마우스 필터는 모두 false였고 마우스 모드 해제도 출력됐다. 입력한
명령 본문은 기록하지 않았다. 이는 팝업 종료 후 늦게 유입된 보고가 호스트
위젯에 전달될 수 있다는 확인이며, 터미널에서 보고 자체가 계속 발생한다는
증거는 아니다.

초기 실행의 중간 통과 판정은 버튼 해제 직전의 주기적 기록을 읽을 수 있어
엄밀한 전체 통과로 취급하지 않았다. 추가 실행은 해제 후 기록을 기다리도록
수정해 위 자동완성 선택 경로를 확인했다. 이때 정상 키와 Backspace는 처리됐고
키 큐 누적·리터럴 `[` 입력은 관측되지 않았다. 따라서 사용자의 입력 먹통
전체를 재현했다고 결론 내리지 않는다.

실제 Windows Terminal의 선택 동작·물리 마우스 신호·기존 실행 상태는 별도
PTY로 복제할 수 없다. 해당 탭에서 동일 진단기를 실행하는 방법은
[입력 진단 문서](input-diagnostics.md)에 기록했다. 일반 입력을 차단하거나
마우스/ESC 규칙을 고치는 제품 수정은 아직 하지 않았다.

## 실제 Windows Terminal 장애 기록

사용자가 같은 진단 실행기로 Windows Terminal에서 증상을 재현했다. 진단
프로세스는 기본 bash의 자식으로 실행되어 기존 ish 안에 중첩된 상태가
아니었다. 사용자는 오른쪽 방향키를 누르지 않고 마우스 이동·드래그만 했다고
확인했다.

- 65.7초 시점: CSI 제어 보고 누적 11,283개, SGR 마우스 441개, 일반 `[`로
  분류된 입력 12개. 마지막 기록에 `ESC[C`(오른쪽 방향키)가 대량 반복됐다.
  한 상태 샘플에서 키 대기 큐 268개, 처리 중 접두 키 1개가 관측됐다.
  CSI 총계가 전부 오른쪽 방향키라고 구분해 집계한 것은 아니다.
- 160.4초 시점: CSI 누적 24,036개, SGR 마우스는 여전히 441개, `[` 누적
  50개. 마우스를 멈춘 뒤 252초까지 새 입력은 없었고 큐는 비었지만 화면
  렌더 횟수는 계속 증가했다. 버퍼에는 이미 삽입된 `[`가 남았다.
- 팝업은 닫혔으며 Application/Renderer 마우스 필터와 관측된
  1000/1003/1015/1006 출력 모드는 모두 꺼져 있었다.

이는 단순 전체 화면 정지와 구분되는 **입력 폭주·대기·문자 오염**의 실측이다.
일반 `[`가 되는 정확한 파서/타임아웃 단계는 이 기록만으로 확정하지 않는다.
관측기 자체의 오버헤드도 있으므로 지연 수치를 그대로 제품 성능값으로
취급하지 않는다.

Windows Terminal 1.24.12741.0의 활성 프로필(`WT_PROFILE_ID` 대조)은
`Windows PowerShell`이며 그 안에서 WSL을 실행하고 있었다. 해당 프로필에
`experimental.repositionCursorWithMouse: true`가 설정되어 있다. 설치 버전의
[공식 구현](https://github.com/microsoft/terminal/blob/v1.24.12741.0/src/cascadia/TerminalControl/ControlCore.cpp#L2012)은
VT 마우스 모드 밖에서 클릭 위치까지의 셀 거리를 계산하고 그 수만큼 좌우
방향키 이벤트를 생성해 입력 연결로 보낸다. Shift 클릭은 이 경로를 우회한다.
팝업을 닫아 마우스 보고가 해제된 뒤 발생한다는 관측과 맞는다.

개인 설정을 바꾸지 않고 사용자가 **Shift를 누른 채 팝업 종료 후 클릭·드래그**를
비교했고 정상이라고 확인했다. 비교 구간의 기록 증가분도 일반 CSI 0개,
리터럴 `[` 0개였고, 팝업 조작 등의 SGR 마우스 보고는 1,309개 처리됐다.
마지막 키 큐와 접두 키는 모두 0개, 프롬프트의 `[`도 0개였다. 같은 기능을
우회하면 증상과 신호 폭주가 사라진다는 근거다. 설정 자체를 false로 바꾸는
최종 비교는 아직 하지 않았으며 Windows Terminal 설정은 읽기만 했다.

권장 우선 조치는 해당 프로필의 `experimental.repositionCursorWithMouse`를
false로 바꾸는 것이다. dok/ish에서 정상 방향키 입력을 임의로 버리는 것으로
우회하지 않는다. 별도 PTY에서 확인한 종료 후 늦은 마우스 보고의 자동완성
선택 경로는 이 터미널 옵션 문제와 구분해 다룬다.

증거는 `tests/dok/reports/current-profile-20261108`의 격리 PTY 결과와
`physical-terminal-first.json`, `physical-terminal-before-shift.json`,
`physical-terminal-after-shift.json`에 보관한다.
